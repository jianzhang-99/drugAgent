# Drug-Agent 项目详细落地计划书

## Project: Drug-Agent Agent 产品化落地

**Goal**: 将当前项目从“多模块原型 + 局部半成品”收敛为一个可演示、可联调、可逐步上线的医疗监管 Agent 产品，先打透“标书审查”主场景，再逐步补齐大模型路由、任务闭环和前端产品体验。  
**Timeline**: 6-8 周  
**Team**: 默认按 1 名全栈开发规划；如有多人协作，文末附分工建议  
**Constraints**:

- 当前项目已有较多代码和页面，但闭环不完整
- 前后端存在两套并行路径，需要先收敛
- 大模型已接入基础设施，但尚未真正成为核心能力层
- 需要优先做出“能讲清楚、能跑通、能继续迭代”的版本，而不是一次做全

---

## 1. 你当前项目的真实状态判断

### 已经具备的部分

- 有明确的三大业务场景定位
- 有 `SceneRouter + WorkflowRegistry + SceneWorkflow` 这一层 Agent 编排骨架
- 有标书审查的结构化解析、规则引擎、免责逻辑、风险融合、报告生成基础
- 有前端工作台、任务看板、任务详情等产品壳子
- 有 DashScope / 百炼 / 千问的接入配置

### 当前的主要问题

- 很多模块是“有骨架、没闭环”
- 前后端有多条并行路径，产品主链路不统一
- 前端大量页面仍是 demo、mock、真实逻辑混杂
- 大模型只接入了基础能力，还没真正进入核心业务流程
- 标书审查虽然是最成熟场景，但“任务创建 -> 解析 -> 审查 -> 结果 -> 复核”还没有完全打通

### 一句话结论

当前项目不是“没做起来”，而是“已经有架子，但还停在半产品、半原型、半技术验证状态”。

所以接下来最重要的不是继续发散做新功能，而是：

1. 收敛一条主链路  
2. 把这条链路打透  
3. 再让大模型进入正确位置  

---

## 2. 总体目标定义

本阶段建议只追一个核心结果：

**先把“标书审查 Agent”做成一个完整、可信、可展示的产品闭环。**

也就是说，你最终要做出来的不是一个“会聊几句的 AI 页面”，而是一个真正的任务型 Agent：

```text
工作台发起任务
-> 上传标书
-> 系统自动路由到标书审查 workflow
-> 创建任务
-> 自动解析文档
-> 自动执行审查
-> 输出风险结论、命中规则、证据链、建议动作
-> 用户在任务详情完成复核
```

达到这个状态后，再补：

- 百炼大模型进行 workflow 判别
- 合同预审
- 风险预警
- 更完整的流式对话体验

## Phase 1: 收敛产品主链路 (Week 1)

### 目标

停止继续发散，先明确整个项目到底以哪条路径为主。

### 你要做什么

#### Task 1.1 选定“标书审查”为第一主场景

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 确定当前版本只打透标书审查 | 2h | 你 | - | 明确其它场景先不深做 |
| 写清楚 V1 产品定位 | 2h | 你 | - | 文档中明确是“风险筛查与复核辅助” |

**怎么实现**

- 所有后续开发、演示、页面优化，都围绕 `TENDER_REVIEW`
- 合同预审和风险预警暂时保留骨架，不再优先投入大量时间
- 外部表达统一成：
  - 标书围标/陪标风险筛查
  - 证据化展示
  - 人工复核辅助

#### Task 1.2 统一标书审查主路径

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 梳理 Agent 上传入口与专用任务入口 | 4h | 你 | Task 1.1 | 明确最终唯一主链路 |
| 统一成“工作台发起 -> 任务详情承接” | 4h | 你 | 路径梳理 | 不再出现两套并行叙事 |

**怎么实现**

建议最终统一为：

```text
前端工作台上传文件
-> 后端统一入口 /agent/drug/submit
-> 内部自动识别 TENDER_REVIEW
-> 创建 case
-> 自动解析
-> 自动执行审查
-> 返回 caseId
-> 前端跳转任务详情页
```

也就是说：

- `DrugAgentController` 保留为统一外部入口
- `TenderReviewController` 可以保留为内部调试/专项接口
- 对前端用户来说，不再暴露两种不同故事

#### Task 1.3 明确大模型在 V1 中的职责边界

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 列出哪些环节必须规则完成 | 2h | 你 | Task 1.1 | 有明确能力边界 |
| 列出哪些环节可以由大模型辅助 | 2h | 你 | 规则边界明确 | 不再模糊“大模型到底做什么” |

**怎么实现**

V1 建议这样分工：

- 必须规则做：
  - 标书风险核心判定
  - 联系方式/报价/团队/模板痕迹等命中
  - 风险分数和等级

- 可以 LLM 做：
  - workflow 模糊路由判别
  - 审查报告润色
  - 结果解释说明
  - 用户追问时的自然语言回答

## Phase 2: 打通标书审查闭环 (Week 2-3)

### 目标

把“创建任务 -> 解析 -> 审查 -> 结果”做成一条稳定流水线。

### 你要做什么

#### Task 2.1 统一后端标书审查执行链

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 明确审查执行只基于真实解析结果 | 4h | 你 | Phase 1 | 审查输入不再是空的 `TenderReviewData` |
| 让 case 保存或可恢复真实 `TenderReviewData` | 6h | 你 | 上一项 | 任意 case 可重新查看或复跑 |
| 把 executeReview 接到真实数据链路 | 6h | 你 | 数据可恢复 | `/execute` 真正执行有效审查 |

**怎么实现**

当前问题是：

- 创建任务和解析有了
- 但专用审查执行链没有稳定地吃到前面解析产物

建议方案：

1. 在任务创建/解析完成后，把以下数据存下来：
   - `caseId`
   - 文档列表
   - parse result
   - blocks / fields / extractionMeta

2. 增加一个“根据 caseId 恢复 TenderReviewData”的服务

3. `executeReview(caseId)` 时：
   - 从 store 或 DB 恢复解析结果
   - 组装 `TenderReviewData`
   - 再交给规则引擎和 workflow

4. 最终保证：
   - 任务详情页看到的解析内容
   - 后端执行审查时用的数据
   - 最终返回的报告
   是同一条链路

#### Task 2.2 让统一入口真正走完整个标书审查 workflow

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 检查 `handleUploadedFiles` 的标书路径 | 4h | 你 | Task 2.1 | 上传标书后不再只是“半自动” |
| 补齐 caseId / documentIds / report 返回 | 4h | 你 | 上一项 | 前端可稳定承接 |

**怎么实现**

你现在已经在 `hydrateTenderMetadata()` 中做了很多工作，这很好。下一步不是重写，而是把它产品化：

- 保证 `DrugAgentResp` 一定返回：
  - `caseId`
  - `documentIds`
  - `scene`
  - `riskLevel`
  - `report`
  - `steps`
  - `evidenceList`

- 如果是标书审查场景，响应里最好统一有：
  - `taskStatus`
  - `parseStatus`
  - `reviewStatus`

这样前端不用猜。

#### Task 2.3 建立“任务状态机”

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 设计任务状态字段 | 2h | 你 | Phase 1 | 状态含义明确 |
| 设计文档状态字段 | 2h | 你 | 上一项 | 解析态和任务态不混淆 |
| 在后端执行链里维护状态流转 | 6h | 你 | 状态定义完成 | 看板和详情可真实显示 |

**怎么实现**

建议至少分三类状态：

- 任务状态：
  - `PENDING`
  - `RUNNING`
  - `REVIEWING`
  - `COMPLETED`
  - `FAILED`

- 文档状态：
  - `PENDING`
  - `PARSING`
  - `PARSED`
  - `FAILED`

- 风险状态：
  - `HIGH`
  - `MEDIUM`
  - `LOW`
  - `UNKNOWN`

注意：

- “任务完成”不等于“高风险”
- “文档解析完成”不等于“审查完成”

## Phase 3: 前端产品化闭环 (Week 3-4)

### 目标

让前端从“演示页面集合”变成“任务型 Agent 产品”。

### 你要做什么

#### Task 3.1 工作台只做任务发起器

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 精简工作台的职责 | 4h | 你 | Phase 2 | 工作台不再承担过多结果展示 |
| 上传成功后跳到任务详情 | 2h | 你 | 上一项 | 用户连续性提升 |

**怎么实现**

工作台保留：

- 场景说明
- 文件上传
- 输入补充说明
- 最近一次任务摘要

工作台弱化：

- 复杂审查结果承接
- 大篇幅报告展示
- 任务详情级别内容

一旦创建成功，直接：

```text
router.push(`/agent/tasks/${caseId}?autostart=1`)
```

或统一到你的正式路由上。

#### Task 3.2 重构任务详情页为“审查结果页”

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 重构详情页信息架构 | 4h | 你 | Phase 2 | 页面结构围绕“结果与证据” |
| 接入真实审查结果接口 | 6h | 你 | 上一项 | 页面显示真实 report |
| 接入执行日志和关键步骤 | 4h | 你 | 审查结果接入 | 用户可理解处理过程 |

**怎么实现**

详情页建议固定结构：

1. 顶部概览
   - caseId
   - 状态
   - 风险等级
   - 提交时间
   - 文档数量

2. 风险总览
   - 综合结论
   - 风险分数
   - 建议动作

3. 命中规则
   - 规则名称
   - 风险等级
   - 命中原因

4. 关键证据
   - 对应文档
   - 对应片段
   - 对应锚点

5. 解析情况
   - 每个文档解析状态
   - 字段提取简要信息

6. 执行日志
   - 创建任务
   - 解析完成
   - 审查开始
   - 报告生成

## Phase 4: 百炼接入 workflow 路由 (Week 4-5)

### 目标

让大模型真正进入系统，但只放在最适合它的位置，不要一上来让它取代全部规则。

### 你要做什么

#### Task 4.1 重构路由决策层

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 新增 `WorkflowRouteDecision` | 2h | 你 | Phase 1 | 路由不再只返回枚举 |
| 拆出 `RuleBasedRouteDecider` | 4h | 你 | 上一项 | 规则路由可单测 |
| 让 `SceneRouter` 变成编排层 | 4h | 你 | 上一项 | 可接入 LLM 判别 |

**怎么实现**

把路由改成：

```text
sceneHint
-> 高置信规则
-> 百炼分类
-> 低置信回退
-> UNKNOWN
```

#### Task 4.2 新增百炼分类器

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 新建 `WorkflowRouteClassifier` | 4h | 你 | Task 4.1 | 可调用百炼判场景 |
| 设计 Prompt 和 JSON 输出格式 | 4h | 你 | 上一项 | 输出结构稳定 |
| 加异常处理和置信度阈值 | 4h | 你 | 上一项 | 分类失败可回退 |

**怎么实现**

模型只做一件事：

- 判断这次请求应该走哪个 workflow

输出：

```json
{
  "scene": "TENDER_REVIEW",
  "confidence": 0.91,
  "reason": "用户上传了多份标书并要求比对雷同风险",
  "requiresClarification": false,
  "clarificationQuestion": ""
}
```

不要让模型直接做：

- 最终风险判定
- 替代规则引擎
- 自创 workflow

#### Task 4.3 让大模型承担“解释层”而不是“裁决层”

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 报告文案交给 LLM 做润色 | 4h | 你 | Phase 2 | 报告更自然易懂 |
| 追问时由 LLM 解释结构化结果 | 4h | 你 | 上一项 | 用户可自然语言追问 |

**怎么实现**

理想结构：

- 规则引擎给出事实和分数
- 大模型把事实组织成“人能看懂”的解释

这才是大模型最适合帮你的地方。

## Dependencies Map

```text
统一主链路
  -> 打通标书闭环
      -> 前端任务化承接
          -> 百炼接入路由
              -> 测试与稳定性
                  -> 演示版打磨
```

关键理解：

- 不先统一主链路，前端和后端会持续各做各的
- 不先打通标书闭环，大模型接入也只会变成“更花哨的半成品”
- 不先完成任务化承接，前端永远像 demo

## 3. 你具体应该怎么实现

下面这部分更直接，是给你少走弯路用的。

### A. 先别做的事情

为了少走弯路，下面这些先不要扩展：

- 不要同时深做三个场景
- 不要先追求复杂多 agent 编排
- 不要把大模型放到最终裁决层
- 不要继续堆更多前端页面
- 不要先追求炫酷流式效果和花哨 UI

这些都会分散你的注意力。

### B. 现在立刻该做的第一批事情

你接下来最优先要做的 5 件事：

1. 确认标书审查是当前唯一打透场景  
2. 统一产品主链路  
3. 让解析结果真正喂给审查执行  
4. 让前端任务详情真正展示真实审查结果  
5. 再接百炼做 workflow 判别  

### C. 你的技术实现顺序建议

建议严格按这个顺序：

1. 先改后端链路
2. 再改前端承接
3. 再补大模型路由
4. 再补测试
5. 最后再打磨视觉和演示

原因很简单：

- 后端没打通，前端越改越乱
- 前端没承接，后端再强也讲不清
- 大模型太早接，只会把问题藏起来

## Risks & Mitigation

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| 同时做三个场景，精力被分散 | High | High | 当前阶段只打透标书审查 |
| 前后端继续各走各的路径 | High | High | 先统一主链路和状态定义 |
| 大模型过早介入核心判定 | High | Medium | 先让规则负责裁决，LLM 负责分类和解释 |
| 前端继续堆页面但闭环不通 | High | High | 所有页面改动围绕任务闭环展开 |
| 演示预期高于真实能力 | Medium | High | 主动收敛文案，只承诺 V1 能力边界 |
| 后续难以回归测试 | High | Medium | 尽快建立样例集和关键链路测试 |

## Resource Allocation

### 单人推进建议

| Role | Hours/Week | Key Responsibilities |
|------|------------|---------------------|
| 你自己 | 30-40h | 后端链路收敛、前端承接、LLM 路由、测试、演示打磨 |

### 如果有 2 人协作

| Role | Hours/Week | Key Responsibilities |
|------|------------|---------------------|
| 后端负责人 | 25-35h | 任务链路、审查执行、路由、测试 |
| 前端负责人 | 25-35h | 工作台、看板、详情页、状态承接 |

建议分工：

- 后端先把 case / parse / review / result 真正串起来
- 前端基于稳定接口重构任务详情和看板
- 大模型路由等后端稳定后再补

## 4. 你的“完成定义”

当你做到下面这些，就说明这个项目已经从半成品进入“真正可用的 V1”了：

- 用户可以从工作台上传标书并发起任务
- 系统能稳定识别为标书审查场景
- 后端自动创建任务、解析文档、执行审查
- 前端能展示真实任务状态、风险总览、命中规则、证据链
- 用户能理解为什么被判高风险或中风险
- 大模型能参与模糊场景路由或报告解释
- 核心流程有基本测试保障

---

## 5. 最后给你的路线建议

你现在最应该做的，不是“再想一个更大的架构”，而是：

**用 2 到 4 周，把标书审查这一个场景做成真正像产品的 Agent。**

只要你把这一件事打透，后面的合同预审、风险预警、百炼路由、多 agent 扩展，都会容易很多。

如果反过来继续发散，你会一直停留在“每个模块都像有点样子，但没有一个地方真正完成”的状态。

# 演示版对话记忆改造计划

## 1. 改造目标

当前项目是演示版，目标不是做一套完整的长期记忆系统，而是优先保证：

1. 页面上可以看到历史对话
2. 当前运行中的多轮对话还能保留上下文
3. 实现简单，维护成本低
4. 不为了演示版引入过多复杂度

因此这次对话记忆改造的目标是：

**聊天记录持久化到数据库，上下文记忆只保存在内存。**

也就是说：

- 聊天记录可以长期保存
- 系统运行期间模型还能记住最近上下文
- 服务重启后，上下文记忆丢失
- 但历史聊天记录仍然可以查看

这个方案是当前阶段最轻量、最实用的做法。

---

## 2. 改造原则

这次改造遵守下面几个原则：

### 2.1 历史记录和上下文记忆分开

这两者不是同一个概念：

1. 聊天记录
   用于页面展示、历史回看、会话管理

2. 上下文记忆
   用于模型多轮对话时保留最近上下文

数据库负责保存聊天记录。

内存负责保存上下文记忆。

### 2.2 演示版不做持久化上下文恢复

当前阶段不做下面这些能力：

- Spring AI 的 JDBC ChatMemory 持久化
- 服务重启后自动恢复上下文记忆
- 从历史消息自动重建多轮上下文

这些能力以后可以做，但现在不做。

### 2.3 优先简单稳定

如果一个方案虽然更完整，但实现复杂、调试麻烦、收益不高，那么当前阶段就不采用。

演示版优先考虑：

- 易实现
- 易解释
- 易演示

## 3. 当前问题说明

当前 [AiConfiguration.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/app/config/AiConfiguration.java) 中的配置是：

```java
@Bean
public ChatMemory chatMemory() {
    return new SimpleJdbcChatMemory();
}
```

这个方案当前存在几个问题：

1. 对话记忆被设计成直接持久化到数据库，超出演示版当前需要
2. 自定义 `SimpleJdbcChatMemory` 会增加调试成本
3. `ChatMemory` 与业务聊天记录存储容易混在一起
4. 后续如果实现不完整，很容易出现上下文行为异常

因此当前不建议继续走“自定义 JDBC ChatMemory 持久化”这条路。

---

## 4. 推荐方案

推荐采用下面这套简单方案：

### 4.1 上下文记忆

使用 Spring AI 的内存型 `ChatMemory`。

例如使用：

- `MessageWindowChatMemory`

它负责：

- 在当前服务运行期间保存最近几轮上下文
- 给模型提供最近 N 条消息

它不负责：

- 长期持久化
- 重启恢复

### 4.2 聊天历史

继续使用现有数据库表和服务来保存历史消息。

当前已有：

- [ChatSessionService.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/scene/qa/service/ChatSessionService.java)
- [ChatMessageService.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/scene/qa/service/ChatMessageService.java)
- [ChatSession.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/thirdparty/db/entity/ChatSession.java)
- [ChatMessage.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/thirdparty/db/entity/ChatMessage.java)

这些继续承担：

- 创建会话
- 保存用户消息
- 保存 AI 回复
- 查询历史消息
- 展示历史会话

## 5. 改造后的职责划分

改造后要明确两套能力的职责边界。

### 5.1 `ChatMemory`

职责：

- 只负责当前运行期的上下文记忆
- 给模型提供最近几轮上下文

不负责：

- 历史会话展示
- 会话列表管理
- 长期数据存储

### 5.2 `ChatSession` / `ChatMessage`

职责：

- 持久化聊天记录
- 支持会话列表
- 支持历史查看
- 支持页面展示

不负责：

- 直接作为 Spring AI 的实时上下文记忆容器

## 6. 改造步骤

修改 [AiConfiguration.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/app/config/AiConfiguration.java)

### Step 3：保留数据库聊天记录逻辑

### Step 4：检查主链路中的 `ChatMemory` 使用点

重点检查下面这些类：

### Step 5：确认系统重启后的行为

改造完成后，系统重启后的行为应该明确为：

1. 历史会话仍然存在
2. 历史消息仍然能查看
3. 模型上下文不会自动恢复
4. 同一个旧会话再次提问时，模型可能表现得像“重新开始”

这是当前方案的预期行为，不算缺陷。

### Step 6：补充说明文档

建议在项目文档里明确写清楚：

**当前演示版只持久化聊天记录，不持久化模型上下文记忆。服务重启后历史消息可查看，但不会自动恢复上下文连续性。**

## 7. 风险和取舍

这个方案虽然简单，但要接受以下取舍：

### 7.1 优点

1. 实现简单
2. 调试容易
3. 逻辑边界清晰
4. 演示效果已经足够

### 7.2 代价

1. 服务重启后模型会失去上下文
2. 页面上的历史记录和模型当前记忆不是完全一致的
3. 使用旧 `sessionId` 再次提问时，可能出现“页面有历史，但模型不记得”的情况

这个代价在演示版阶段是可以接受的。

---

## 8. 当前不建议做的事情

当前阶段不建议继续做下面这些事情：

1. 不建议继续实现复杂的自定义 JDBC ChatMemory
2. 不建议把数据库聊天记录直接强行当作 Spring AI 上下文记忆
3. 不建议为了恢复上下文而在每次请求前重新组装完整历史消息
4. 不建议在演示版阶段引入完整的长期记忆恢复机制

这些能力都可以作为后续增强项，但现在没必要。

---

## 9. 后续升级方向

如果以后项目从演示版升级为正式版，可以再考虑以下方向：

### 9.1 方案一：使用 Spring AI 官方持久化记忆

例如：

- `MessageWindowChatMemory + JdbcChatMemoryRepository`

适合继续沿用 Spring AI 的记忆体系。

### 9.2 方案二：基于业务历史消息手动重建上下文

做法是：

- 从 `ChatMessage` 中取最近 N 轮历史
- 在调用模型前手动组装上下文消息

适合更强的可控性需求。

---

## 10. 最终结论

当前演示版最适合采用下面这套方案：

**数据库保存聊天记录，内存保存当前上下文，服务重启后不恢复模型记忆。**

这套方案实现成本低、稳定性高、演示效果足够，最适合你当前项目阶段。

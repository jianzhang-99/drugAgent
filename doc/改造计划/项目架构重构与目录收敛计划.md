# 项目架构重构与目录收敛计划

## 1. 背景与目标

当前 `drug-agent` 项目已经具备一定的 Agent 调度、场景 Workflow、知识库、任务管理和前端工作台能力，但整体代码结构存在明显的历史叠加问题：

- 存在多套并行入口，接口边界不统一
- `controller` 层承载了过多业务编排职责
- 会话体系、任务体系、标书审查体系存在重复实现
- 命名风格不一致，目录归属不清晰
- 前后端都存在“功能可用但结构混乱”的过渡代码

本次改造的目标不是局部修修补补，而是将项目收敛为一套整洁、优雅、可持续演进的架构体系，并把“上层 Agent 理解用户意图，再分发到场景 Workflow”确立为唯一主链路。

本计划要求：

- `doc/` 目录保持不动，不纳入重构
- 除 `doc/` 外，其他目录均按新架构收敛
- 统一命名规范
- 删除重复与冗余代码
- 删除历史残留入口和过渡实现

---

## 2. 改造原则

### 2.1 单一主入口

用户自然语言请求必须统一进入 Agent 主入口，不允许多套平行聊天主链路并存。

### 2.2 单一职责

- `controller` 只负责入参与出参
- `application` 负责用例编排
- `domain` 负责业务规则与业务模型
- `workflow` 负责场景执行骨架
- `infrastructure` 负责技术实现细节

### 2.3 业务优先于技术

目录设计必须围绕业务域组织，而不是围绕“谁先写出来”“哪个页面先出现”“哪个 SDK 先接入”来组织。

### 2.4 一次收口，不保留长期过渡层

旧接口、旧会话体系、旧任务体系不能长期并存。每个阶段完成后，应及时删除废弃实现，而不是继续积累历史负担。

### 2.5 命名必须统一

同类职责使用同类命名，不允许出现：

- 一个控制器叫 `XxxController`，另一个同级却叫 `XxxApi`
- 一个服务叫 `XxxService`，另一个做同类事情却叫 `XxxManager`
- 一个 DTO 叫 `XxxReq`，另一个叫 `XxxRequest`

本次改造后，命名规范必须完全一致。

---

## 3. 目标架构说明

项目最终必须收敛为如下主线：

`用户请求 -> AgentController -> AgentApplicationService -> 意图理解 -> Workflow 分发 -> Domain -> Infrastructure`

其中：

- `AgentController` 是唯一自然语言入口
- `AgentApplicationService` 是总编排层
- 上层 Agent 负责理解用户意图、澄清意图、路由场景
- `Workflow` 层负责将不同场景的执行链条结构化
- `Domain` 层负责表达业务模型和业务规则
- `Infrastructure` 层负责数据库、LLM、向量库、文件存储等技术接入

## 5. 命名规范

### 5.1 类命名规范

- 控制器统一使用 `*Controller`
- 应用服务统一使用 `*ApplicationService`
- 领域服务统一使用 `*DomainService`
- 仓储接口统一使用 `*Repository`
- 仓储实现统一使用 `*RepositoryImpl`
- 持久化实体统一使用 `*Entity`
- MyBatis 接口统一使用 `*Mapper`
- 请求 DTO 统一使用 `*RequestDto`
- 响应 DTO 统一使用 `*ResponseDto`
- 工作流统一使用 `*Workflow`
- 工作流上下文统一使用 `*WorkflowContext`
- 转换器统一使用 `*Assembler` 或 `*Converter`
- 校验器统一使用 `*Validator`

### 5.2 目录命名规范

- 后端目录按职责与业务域组织
- 同类文件必须归入同类目录
- 不允许同一种职责散落在多个不相关目录中
- 前端目录按业务域组织，而不是按页面历史堆叠

### 5.3 接口路径命名规范

最终统一为以下资源风格：

- `/api/agent/*`
- `/api/tender/*`
- `/api/task-board/*`
- `/api/knowledge/*`

不再保留多套风格并存的路径体系。

## 6. 最终职责边界

### 6.1 controller 层职责

只负责：

- 接收请求
- 参数校验
- 调用应用服务
- 返回统一响应 DTO

禁止承担：

- 业务编排
- 文件处理细节
- 模型调用细节
- 复杂对象组装
- 持久化细节

### 6.2 application 层职责

负责：

- 组织用例执行
- 串联多个领域能力
- 控制流程主线
- 触发 workflow
- 统一组合结果

### 6.3 domain 层职责

负责：

- 核心业务模型
- 业务规则
- 状态流转
- 领域服务
- repository 抽象

### 6.4 workflow 层职责

负责：

- 场景执行骨架
- 场景 step 编排
- 场景上下文传递
- 场景间标准化执行协议

### 6.5 infrastructure 层职责

负责：

- 数据库接入
- LLM provider 接入
- 向量库接入
- 文件存储接入
- 内存与会话存储
- 外部系统对接

## 8. 必须删除的重复与冗余代码

以下内容应被明确删除、合并或重构，不允许以“暂时保留”形式长期存在。

### 8.1 删除旧会话体系

必须删除：

- `SessionController`
- 旧 `domain.Session`
- 旧 `SessionService`
- 所有依赖 `legacy/sessions` 的前后端调用链

### 8.2 合并新会话体系

需要合并：

- `ChatSessionController`
- `ChatMessageController`

最终收敛为：

- `AgentSessionController`

### 8.3 收敛 Agent 入口

保留统一 Agent 主入口，但统一命名与职责：

- `DrugAgentController` 重命名为 `AgentController`

### 8.4 收敛 Tender 任务体系

当前存在任务创建、标书解析、任务进度、看板展示多套表达，必须拆清并收敛。

建议：

- `TenderReviewController` 拆为：
  - `TenderTaskController`
  - `TenderCaseController`
- `TaskCenterController` 中与 Tender 主流程重复的能力删除或吸收
- `TaskBoardController` 仅保留看板展示职责

### 8.5 删除 controller 中的冗余模式

必须删除：

- 在 controller 中直接使用 `Map<String, Object>` 作为正式请求或响应
- 在 controller 中直接编排复杂业务流程
- 在 controller 中直接处理文件存储流程
- 在 controller 中重复拼装领域对象
- 同类接口之间复制粘贴的错误处理分支

## 9. 分阶段改造计划

## Phase 1：接口入口收口

### 目标

消灭多套平行入口，建立唯一主线。

### 任务

1. 保留 Agent 主入口，统一为 `AgentController`
2. 删除旧会话体系及 `legacy/sessions` 相关代码
3. 合并 `ChatSessionController` 与 `ChatMessageController`
4. 收敛 Tender 任务相关入口
5. 所有接口返回 DTO 或统一响应对象

### 完成标准

- 不再存在旧会话接口
- 不再存在一类资源由多套 controller 并行暴露
- controller 命名全部规范化

---

## Phase 2：抽离应用编排层

### 目标

让 controller 瘦身，只承担接口职责。

### 任务

1. 新建 `application/agent`
2. 新建 `application/tender`
3. 新建 `application/task`
4. 将 controller 中的主流程编排逻辑迁出
5. 将 Agent 主流程统一进入 `AgentApplicationService`

### 完成标准

- controller 方法保持简短
- 应用流程都进入 `ApplicationService`
- controller 中不再有跨多个领域对象的编排代码

---

## Phase 3：重组 domain 层

### 目标

按业务域重组核心模型与规则。

### 任务

1. 按 `agent / tender / task / knowledge` 拆分 domain
2. 将领域模型移动到对应业务域
3. 将业务规则、状态流转、领域服务收口
4. 定义 repository 接口，隔离基础设施实现

### 完成标准

- domain 不依赖 controller
- domain 不依赖 mapper
- 核心业务模型位置清晰

---

## Phase 4：重组 infrastructure 层

### 目标

彻底隔离技术实现细节。

### 任务

1. 将 entity、mapper、repositoryImpl 迁入 `infrastructure/persistence`
2. 将多模型接入迁入 `infrastructure/llm`
3. 将文件存储迁入 `infrastructure/storage`
4. 将向量库迁入 `infrastructure/vectorstore`
5. 将会话记忆迁入 `infrastructure/memory`

### 完成标准

- 上层业务不直接依赖第三方 SDK
- LLM provider 可替换
- 数据存储方案可调整

---

## Phase 5：工作流归位

### 目标

让场景执行结构变得清晰且可扩展。

### 任务

1. 所有 workflow 收拢到 `workflow/`
2. 按场景分目录
3. 将复杂流程拆成 step
4. 使用统一 `WorkflowRegistry` 管理

### 完成标准

- workflow 层成为独立清晰的一层
- 上层 Agent 到场景执行路径唯一
- 业务逻辑不再散落在各类 service 中兼职 workflow

---

## Phase 6：前端目录收敛

### 目标

前端按业务域组织，删除重复视图和重复 API 调用层。

### 任务

1. 建立 `feature/agent`
2. 建立 `feature/tender`
3. 建立 `feature/task`
4. 建立 `feature/knowledge`
5. 公共 API 收入 `shared/api`
6. 公共组件收入 `shared/component`
7. 公共工具收入 `shared/util`
8. 删除重复页面与重复 store

### 完成标准

- 一种业务能力只保留一套主实现
- 页面只做组合，不做主逻辑堆叠
- 模型选择、会话、任务、工作台逻辑都有明确归属

## 10. 迁移与重命名建议

### 10.1 Controller 层

- `DrugAgentController` -> `AgentController`
- `ChatSessionController` + `ChatMessageController` -> `AgentSessionController`
- `KnowledgeController` -> `AgentKnowledgeController` 或 `KnowledgeController`
- `TenderReviewController` -> `TenderTaskController` + `TenderCaseController`
- `TaskBoardController` 保留
- `TaskCenterController` 拆解后删除原文件
- `SessionController` 删除

### 10.2 Service 层

- `DrugAgentService` -> `AgentApplicationService`
- `QwenService` 收敛为统一 LLM 接入能力的一部分
- `TenderCaseService` 按任务、解析、审查、报告拆分应用层职责

### 10.3 DTO 层

将当前混用的 `Req / Resp / Map / Entity` 出入参模式统一替换为：

- `*RequestDto`
- `*ResponseDto`

## 11. 硬性执行规则

改造期间必须严格遵守以下规则：

1. 新增代码必须进入目标目录
2. 不允许继续向旧目录追加新逻辑
3. 不允许新增第二套平行 controller
4. 不允许继续使用 `Map<String, Object>` 作为正式 API 模型
5. 不允许 controller 继续持有主业务编排逻辑
6. 不允许业务层直接依赖第三方 SDK
7. 每完成一个阶段，立即删除废弃实现

---

## 12. 建议执行顺序

推荐按以下顺序实施，风险最低：

1. 先统一接口与 controller 边界
2. 再抽 application service
3. 再重组 domain
4. 再重组 infrastructure
5. 最后重组前端目录
6. 每个阶段结束立即删除旧实现

---

## 13. 最终一句话定义

本项目最终应收敛为：

**以 Agent 为统一入口、以 Application 为编排核心、以 Domain 为业务中心、以 Workflow 为场景执行骨架、以 Infrastructure 承载技术实现。**

这条主线必须成为后续所有开发与重构的唯一基准。

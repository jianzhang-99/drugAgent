# 项目架构重构与目录收敛计划

## 1. 目标

本次重构的核心目标不是“整理文件夹”，而是把当前 `drug-agent` 从“多轮迭代叠加后的混合体”收敛为一套长期可维护的场景化 Agent 架构。

重构后需要同时满足以下目标：

1. 上层 Agent 成为唯一主入口
2. 场景 Workflow 成为真正的业务闭环骨架
3. 场景内实现内聚，跨场景能力明确复用
4. 外部依赖完全隔离
5. 目录结构稳定、命名统一、职责清晰
6. 删除重复代码、历史残留和无价值中间层

本计划中，`doc/` 保持不动，不纳入代码目录改造范围。

---

## 2. 设计理念

结合当前项目现状与目标产品形态，采用以下目录思想：

### 2.1 app 只负责启动与装配

这里不承载业务逻辑，只负责：

- 启动应用
- 加载配置
- 注册 Bean
- 装配依赖

### 2.2 interfaces 只负责对外接口

这里承载：

- HTTP Controller
- Request / Response DTO
- SSE 事件输出
- 定时任务入口

不允许在这一层堆积业务编排逻辑。

### 2.3 core 只放稳定的通用 Agent 内核

这里是项目的“中枢神经系统”，但必须保持克制，只保留跨场景稳定、长期不会频繁变化的能力。

例如：

- Agent 上下文
- 场景路由
- Workflow 注册
- 通用编排骨架
- 通用模型与契约
- 通用异常、trace、常量

### 2.4 scenes 才是业务真正发生的地方

每个场景单独成域，形成完整闭环：

- workflow
- application
- domain
- infrastructure
- tests

这比把所有业务逻辑扔在全局 `service/`、`workflow/`、`domain/` 里更适合长期演进。

### 2.5 shared_capabilities 只放“真正跨场景复用”的能力

不是“看起来通用就往这里放”，而是必须满足：

- 至少 2 个场景以上共享
- 与具体场景无直接绑定
- 抽离后不会让场景理解变差

### 2.6 integrations 只放外部系统接入

所有第三方依赖必须进入 integrations，避免业务层直接依赖：

- 模型供应商
- 向量库
- 对象存储
- MQ
- 第三方平台

### 2.7 less is more

本次重构的重要原则是：

- 能删就删
- 能合并就合并
- 不为了“看起来高级”增加层级
- 不保留无价值抽象
- 不允许出现“双轨并存”的历史结构

## 3. 目标目录

结合你的项目，我建议最终目录采用下面这套结构。

```text
src/                              # 代码根目录，整个系统源码从这里开始组织
├── app/                          # 应用启动与装配层，只做启动、配置、Bean 装配，不写业务逻辑
│   ├── bootstrap/                # 启动初始化代码，例如启动器、初始化器、启动期检查
│   ├── config/                   # Spring / 中间件 / 全局参数配置类
│   └── dependency/               # 依赖装配与模块 wiring，例如手动装配、模块注册
│
├── interfaces/                   # 对外接口层，所有外部访问系统的入口都在这里
│   ├── http/                     # HTTP 接口层，面向前端或外部系统
│   │   ├── controller/           # 控制器，只接请求、调服务、回响应
│   │   │   ├── agent/            # Agent 主入口相关接口，如聊天、会话、知识问答入口
│   │   │   ├── tender_review/    # 标书审查场景对外接口
│   │   │   ├── task_board/       # 任务看板相关接口
```

## 4. 结合当前项目的适配说明

你这个项目目前已经具备以下核心能力：

- Agent 会话与消息链路
- 上层意图理解与场景分发
- 标书审查场景
- RAG 知识问答
- 任务看板
- 多模型接入

所以这个目标目录不是“从零设计”，而是要把当前代码映射进更稳定的结构。

## 5. 命名规范

### 5.1 Controller

所有控制器统一以 `Controller` 结尾。

例如：

- `AgentController`
- `AgentSessionController`
- `TenderReviewController`
- `TaskBoardController`

不允许混用：

- `*Api`
- `*Handler`
- `*Endpoint`

### 5.2 Service

要严格区分：

- `DrugAgentService` 这种内核服务，属于 `core/agent`
- 场景应用服务，统一放 `scenes/*/application/services`
- 领域服务，统一放 `scenes/*/domain/service`

不允许再把不同层级都统称为 `service/` 顶层目录。

### 5.3 Workflow

所有工作流统一使用 `*Workflow` 命名。

例如：

- `TenderReviewWorkflow`
- `ContractPrecheckWorkflow`
- `RiskAlertWorkflow`

### 5.4 Request / Response

接口模型全部进入：

- `interfaces/http/request`
- `interfaces/http/response`

不再放在 `domain/req`、`domain/resp` 这种混合目录里。

### 5.5 Domain Model

领域对象进入：

- `core/domain/model`
- `scenes/*/domain/model`

数据库实体不应再和领域模型混在一起。

## 6. 必须删除的内容

这次重构必须继续执行“减法优先”。

### 6.1 已确认应删除

以下内容属于历史残留或已被替代，必须持续清理：

- 旧会话体系
- 旧路由体系
- 无引用 DTO
- 无引用 repository 抽象
- 无价值中间层
- 与新主链路重复的 controller

### 6.2 后续改造中必须避免再次出现

不允许再新增：

- 顶层 `service/` 大杂烩目录
- 顶层 `dto/` 混放目录
- 同一类资源多套 controller 并存
- 一个功能两套入口
- 为了“看起来抽象”而新增的空包装层

## 7. 分阶段改造计划

## Phase 1：建立新主线

### 目标

让项目存在唯一清晰主线：

`interfaces -> core -> scenes -> shared_capabilities / integrations`

### 任务

1. 建立新目录骨架
2. 停止向旧目录追加新代码
3. 保留当前能跑的最小主链路
4. 明确每类代码未来应迁往哪里

### 完成标准

- 新代码只进入新目录
- 旧目录不再长新逻辑

---

## Phase 2：迁移 Agent 内核

### 目标

把上层 Agent 调度能力稳定放进 `core`。

### 任务

1. 将 `AgentContext`、`WorkflowRegistry`、`SceneWorkflow` 等迁入 `core/agent`
2. 将编排与事件能力迁入 `core/orchestration`
3. 把 `AgentApplicationService` 拆清：
   - 通用内核留 `core`
   - 场景相关逻辑下沉到 `scenes`

### 完成标准

- Agent 内核不再依赖具体场景实现细节
- `core` 层稳定且薄

---

## Phase 3：迁移 tender_review 场景

### 目标

让标书审查成为第一个完整闭环场景。

### 任务

1. 将 `TenderReviewWorkflow` 迁入 `scenes/tender_review/workflow`
2. 将解析、融合、证据、报告能力按职责拆入：
   - `application`
   - `domain`
   - `infrastructure`
3. 将解析器移入 `scenes/tender_review/infrastructure/parser`
4. 将规则融合能力移入 `scenes/tender_review/domain/service`

### 完成标准

- 标书审查不再依赖顶层 `service/tenderreview`
- 该场景形成独立闭环

---

## Phase 4：迁移 RAG 与共享能力

### 目标

把真正跨场景的能力从业务逻辑里抽出来。

### 任务

1. 将 LLM 门面与 provider 管理迁入 `shared_capabilities/llm` 和 `integrations/model_provider`
2. 将 RAG 检索、策略、索引迁入 `shared_capabilities/rag`
3. 将文档公共解析能力迁入 `shared_capabilities/document`
4. 将安全与审查类 advisor 能力迁入 `shared_capabilities/security`

### 完成标准

- 共享能力不再散落在顶层 `service`
- 具体场景只依赖共享契约

---

## Phase 5：迁移外部接入层

### 目标

把数据库、对象存储、向量库、模型接入统一隔离。

### 任务

1. MyBatis mapper / persistence 迁入 `integrations`
2. 向量库接入迁入 `integrations/vector_db`
3. 模型 provider 接入迁入 `integrations/model_provider`
4. 对象存储迁入 `integrations/storage`

### 完成标准

- 场景层不直接依赖外部实现
- 替换外部依赖不会影响内核目录结构

---

## Phase 6：删除旧目录

### 目标

彻底清理历史结构。

### 任务

1. 删除旧 `service/` 大杂烩目录
2. 删除旧 `controller/` 平铺目录
3. 删除旧 `dto/`、`domain/req`、`domain/resp`
4. 删除所有迁移后无引用旧文件

### 完成标准

- 旧目录不存在“影子实现”
- 项目结构只剩一套表达方式

- 在旧目录继续写新代码
- 保留双轨实现
- 新增“只多一层名字”的包装服务

## 9. 最终原则

重构完成后，项目必须满足一句话描述：

**外层通过 interfaces 接收请求，core 负责通用 Agent 内核，scenes 负责业务闭环，shared_capabilities 提供跨场景能力，integrations 隔离所有外部依赖。**

这套结构必须成为后续所有新增代码的唯一落点标准。

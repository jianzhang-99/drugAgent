# 项目架构重构与目录收敛计划

## 1. 改造目标

这次改造的目标不是把目录做复杂，而是把项目整理成一套：

1. 简单
2. 好懂
3. 好维护
4. 后续还能继续扩展

当前项目的主要问题是：

- 目录层级偏多
- 有些名字偏重，不够直观
- 有些目录是空的，或者只有概念没有实际承载
- 一个功能分散在很多地方，理解成本高

所以这次目录改造的总原则就是：

**少目录、少术语、少空壳，多内聚。**

---

## 2. 命名原则

为了适配中文团队，这次目录名不追求“架构术语高级”，而追求“一眼看懂”。

### 2.1 顶层目录统一使用简单词

最终统一为：

- `app`
- `controller`
- `agent`
- `scene`
- `shared`
- `thirdparty`

### 2.2 场景目录也尽量简单

建议统一为：

- `tender_review`
- `qa`
- `contract`
- `risk`

说明：

- `general_qa` 改为 `qa`
- `contract_precheck` 改为 `contract`
- `risk_alert` 改为 `risk`
- `tender_review` 保留

### 2.3 场景内部子目录统一

每个场景尽量只保留：

- `workflow`
- `service`
- `model`
- `support`

这样整个项目的结构会非常统一。

## 4. 目录职责说明

为了后面不再乱放代码，这里再把职责明确一下。

### 4.1 `app`

只做启动和配置。

可以放：

- 启动类
- Spring 配置
- 全局 Filter
- 基础装配

不要放：

- 业务逻辑
- 场景逻辑
- 数据库访问

### 4.2 `controller`

只做接口入口。

可以放：

- Controller
- Request DTO
- Response DTO

不要放：

- 复杂业务判断
- 跨场景编排逻辑

### 4.3 `agent`

只做 Agent 主链路。

可以放：

- 上下文
- 路由
- 工作流注册
- 主编排入口

不要放：

- 标书审查细节
- 某个场景专有规则

### 4.4 `scene`

是真正发生业务的地方。

可以放：

- 场景 workflow
- 场景 service
- 场景 model
- 场景专属 support

### 4.5 `shared`

只放多个场景都会复用的能力。

如果一个能力只在一个场景使用，就不要急着抽到这里。

### 4.6 `thirdparty`

只放第三方接入代码。

可以放：

- 模型供应商接入
- 数据库 Mapper 和 entity
- 向量库接入

不要放：

- 核心业务逻辑
- 场景编排逻辑

## 5. 当前目录映射建议

### 5.1 当前 `interfaces`

迁移为：

- `interfaces/http/controller/*` -> `controller/*`
- `interfaces/http/request/*` -> `controller/request/*`
- `interfaces/http/response/*` -> `controller/response/*`

### 5.2 当前 `core`

拆开迁移，不再保留大而全的 `core`。

迁移规则：

- 主链路相关 -> `agent`
- 通用复用能力 -> `shared`
- 场景相关逻辑 -> `scene`

### 5.3 当前 `scenes`

保留“按场景组织”的思路，但把命名和分层收轻。

迁移为：

- `scenes/tender_review/*` -> `scene/tender_review/*`
- `scenes/general_qa/*` -> `scene/qa/*`
- `scenes/contract_precheck/*` -> `scene/contract/*`
- `scenes/risk_alert/*` -> `scene/risk/*`

### 5.4 当前 `shared_capabilities`

迁移为：

- `shared_capabilities/llm` -> `shared/llm`
- `shared_capabilities/rag` -> `shared/rag`
- `shared_capabilities/security` -> `shared/security`

### 5.5 当前 `integrations`

迁移为：

- `integrations/model_provider` -> `thirdparty/llm`
- `integrations/storage` -> `thirdparty/db`
- `integrations/vector_db` -> `thirdparty/vector`

### 5.6 当前顶层 `config`

并入：

- `app/config`

不要保留两套配置目录表达。

## 6. 当前不建议继续保留的复杂层

下面这些目录或概念，在当前阶段建议逐步删掉或合并：

- `core/common`
- `core/contracts`
- `core/domain/request`
- `core/domain/response`
- `core/orchestration/planner`
- `core/orchestration/events`
- `scenes/*/application`
- `scenes/*/domain`
- `scenes/*/infrastructure`
- `tests/unit`
- `tests/integration`
- `tests/e2e`

原因不是它们不专业，而是：

1. 当前项目体量还没有大到需要这些层
2. 它们会让目录先复杂起来
3. 很容易出现空目录和半抽象目录

## 7. 分阶段改造计划

### Phase 1：先统一目录标准

从现在开始，新代码只允许进入：

- `app`
- `controller`
- `agent`
- `scene`
- `shared`
- `thirdparty`

同时停止往旧目录继续追加新逻辑。

### Phase 2：先迁接口和主链路

优先迁这些内容：

- `AgentController`
- `AgentSessionController`
- `AgentKnowledgeController`
- `AgentContext`
- `WorkflowRegistry`
- `DefaultUpperAgentOrchestrator`
- `AgentApplicationService`

目标：

- 接口统一到 `controller`
- 主流程统一到 `agent`

### Phase 3：先把 `tender_review` 做成样板场景

优先收敛：

- `scene/tender_review/workflow`
- `scene/tender_review/service`
- `scene/tender_review/model`
- `scene/tender_review/support`

### Phase 4：再迁 `qa / contract / risk`

这几个场景先保持轻量。

优先保留：

- `workflow`
- `service`

以后功能变多，再补 `model` 和 `support`。

### Phase 5：最后迁公共能力和第三方接入

最后再统一整理：

- `shared`
- `thirdparty`

这样可以避免一开始就抽象过度。

---

## 8. 删除原则

这次改造优先做减法。

优先删除：

1. 空目录
2. 无引用类
3. 重复入口
4. 历史遗留 DTO
5. 只有一层转发价值的包装类

一个类如果只是：

- 接参数
- 调下一个类
- 不做判断
- 不做转换
- 不做编排

那大概率可以删掉，或者直接并入上层类。

---

## 9. 最终结论

改造完成后，项目目录应该稳定成下面这套表达：

**`app` 管启动，`controller` 管接口，`agent` 管主链路，`scene` 管业务场景，`shared` 管公共能力，`thirdparty` 管第三方接入。**

这套结构足够轻，也足够支撑后续扩展。

先把目录变简单，项目才会真正变简单。

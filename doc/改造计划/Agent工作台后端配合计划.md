# Agent工作台后端配合计划

## 1. 改造背景

本次后端改造不以“立即重构所有业务架构”为目标，而是以支撑前端工作台体验为第一优先级。

前端已经明确要走统一 Agent 工作台模式，因此后端在这一阶段的职责应当从“自由返回业务字段”收敛为：

1. 提供稳定的契约接口
2. 返回可直接驱动前端渲染的消息结构
3. 让前端不再根据 `answer`、`summary`、`report` 猜测页面表现

本计划默认前提是：

1. 前端先完成原型还原
2. 后端分阶段补充契约接口
3. 在演示期优先保证接口稳定和结构清晰

本计划额外遵循两个约束：

1. 保持当前后端目录结构，不做大规模目录迁移
2. 尽量减少新增类文件，优先在现有 controller、service、response 结构中轻量扩展

---

## 2. 后端目标

后端本阶段的目标如下：

1. 为 Agent 工作台提供会话、消息、任务、报告四类基础接口
2. 统一响应协议，减少前端推断逻辑
3. 保持当前工作流能力可复用
4. 将“路由结果”和“前端展示消息”做适配隔离
5. 优先保证演示链路稳定，而不是一次性做完所有抽象

后端“完成”的定义是：

1. 前端可以拿到稳定的历史会话摘要
2. 前端可以拿到稳定的会话消息时间线
3. 前端发送消息后，能收到明确的消息类型
4. 顶部任务中心可以读取后台任务状态
5. 点击结果卡后可以拉取或展示结构化报告详情
6. 在满足上述目标时尽量压缩新增类数量

---

## 3. 后端设计原则

### 3.1 先契约，后重构

当前阶段不要求马上重做所有内部结构，但必须先把前端使用的契约稳定下来。

也就是说：

1. Controller 可以先适配现有服务
2. Service 可以先封装当前工作流返回
3. 但对前端暴露的数据结构必须统一

### 3.2 前端只接“展示协议”

后端返回给前端的内容不应再只是：

1. `answer`
2. `summary`
3. `report`
4. `riskLevel`

而应该直接返回“可渲染消息”：

1. `assistant_text`
2. `assistant_clarify`
3. `assistant_result_card`

### 3.3 业务执行和前端消息解耦

建议把后端逻辑分成两层：

1. 业务执行结果层
2. 前端消息适配层

即：

- 路由、工作流、报告生成继续返回业务对象
- 最后新增 adapter，将业务对象转换为前端消息协议

这里的“适配层”不代表一定新建一整套目录。

在当前项目里，建议优先采用轻量做法：

1. 先在现有 `AgentChatService` 内新增少量私有转换方法
2. 先在现有 response DTO 上轻量补字段
3. 只有当转换逻辑明显膨胀时，再考虑抽成单独 assembler

## 4. 后端接口规划

本阶段建议优先提供以下接口。

### 4.1 会话列表接口

接口：

```http
GET /api/agent/sessions
```

用途：

1. 左侧历史会话列表
2. 顶部标题显示当前会话名称

建议返回：

```json
[
  {
    "id": "sess_10293",
    "title": "年度设备采购标书比对",
    "scene": "TENDER",
    "dateGroup": "今天",
    "updatedAt": "2026-03-25T14:22:00"
  }
]
```

### 4.2 会话详情接口

接口：

```http
GET /api/agent/sessions/{id}
```

用途：

1. 中间聊天时间线
2. 历史会话切换后恢复完整上下文

建议返回：

```json
{
  "id": "sess_10293",
  "title": "年度设备采购标书比对",
  "scene": "TENDER",
  "messages": [
    {
      "id": "msg_1",
      "role": "user",
      "type": "user_text",
      "content": "帮我对比新上传的这几份标书文件",
      "attachments": ["投标人A_标书.md", "投标人B_标书.md"],
      "createdAt": "2026-03-25T14:20:00"
    },
    {
      "id": "msg_2",
      "role": "assistant",
      "type": "assistant_result_card",
      "content": "我已经为您完成了这两份标书文件的深度比对审查。",
      "result": {
        "traceId": "TRC-99281-A",
        "scene": "TENDER",

      },

    }
  ]
}
```

### 4.3 发送消息接口

接口：

```http
POST /api/agent/messages
```

用途：

1. 用户发送文本
2. 用户上传材料后发起任务

建议请求：

```json
{
  "sessionId": "sess_10293",
  "content": "帮我分析这几份标书文件",
  "attachments": ["file_1", "file_2"],
  "sceneHint": "TENDER"
}
```

建议响应：

```json
{
  "sessionId": "sess_10293",
  "message": {
    "id": "msg_2",
    "role": "assistant",
    "type": "assistant_result_card",
    "content": "审查已完成，发现高风险线索。",
    "result": {
      "traceId": "TRC-99281-A",
      "scene": "TENDER",
      "riskLevel": "High",
      "score": 87,
      "docCount": 2,
      "summary": "发现 87% 的语义重合度"
    },
    "createdAt": "2026-03-25T14:22:00"
  },
  "task": {
    "id": "T-001",
    "name": "年度设备采购标书分析",
    "scene": "TENDER",
    "status": "completed",
    "progress": 100
  }
}
```

这里最关键的是：

1. 返回的是标准消息
2. 前端不再自行判断是普通回复、澄清还是结果卡

### 4.4 任务中心接口

## 5. 后端内部改造建议

### 5.1 增加前端消息适配层

建议优先不新增独立 assembler 文件。

更符合当前项目的轻量方案是：

1. 在 `AgentChatService` 中增加 `buildAssistantMessageView(...)`
2. 在 `AgentController` 中增加最少量的接口 DTO 组装
3. 在 `TaskBoardController` 或现有任务相关 service 中返回前端需要的任务视图

只有当以下条件满足时，才建议新增独立 assembler 文件：

1. 单个类中转换逻辑超过 150 行
2. 多个 controller 开始重复拼装同类结构
3. 一个视图协议被多个场景重复使用

### 5.2 将会话消息持久化结构标准化

建议后端持久化时就区分消息类型，而不是只存 `role + content`。

建议至少补充：

1. `message_type`
2. `trace_id`
3. `result_snapshot`
4. `attachments_snapshot`

如果当前演示周期不允许改表，也可以采用过渡方案：

1. 短期先把 `result_snapshot` 放到现有 metadata/json 字段中
2. 中期再补正式字段或新表结构

这样历史会话恢复时就能稳定还原前端表现。

### 5.3 将路由结果转为展示意图

对于当前路由服务的结果，建议转换为三类展示结果：

1. 普通回复
2. 澄清问题
3. 结果卡

即：

- `UNKNOWN + requiresClarification=true` -> `assistant_clarify`
- `scene明确但无结构化结果` -> `assistant_text`
- `scene明确且有结构化结果` -> `assistant_result_card`

这一层建议优先放在现有 `AgentChatService` 中完成，不额外新增“消息路由服务”之类的文件。

### 5.4 任务中心不要依赖前端本地推导

任务中心最好由后端维护任务状态源，而不是让前端本地推断。

建议来源：

1. 文件审查任务
2. 报告生成任务
3. 异步解析任务

后端统一汇总返回任务状态。

## 6. 分阶段实施计划

### 阶段一：契约优先

目标：

1. 先定义好前端所需接口返回结构

任务：

1. 在现有 DTO 上补齐工作台所需字段
2. 明确消息类型字段
3. 明确报告摘要字段
4. 明确任务中心字段

完成标准：

1. 前后端对接口字段达成一致
2. 前端可以用 mock 契约先开发

### 阶段二：Controller 适配

目标：

1. 不动大量底层逻辑，先通过适配层输出新协议

任务：

1. `AgentController` 输出消息视图
2. 增加任务接口
3. 增加报告详情接口
4. 增加文件上传接口

这里建议优先保持现有 controller 数量不变，先在已有 controller 中扩展：

1. `AgentController`
2. `TaskBoardController`
3. 必要时复用现有 `TenderTaskController`

完成标准：

1. 前端联调不需要猜字段

### 阶段三：消息持久化与历史恢复

目标：

1. 历史会话可以恢复真实消息形态

任务：

1. 扩展消息表结构
2. 存储 message type
3. 存储 result snapshot
4. 存储 trace id

完成标准：

1. 历史会话恢复后，前端表现与首次生成时一致

### 阶段四：异步任务中心接入

目标：

1. 顶部任务中心可展示真实运行任务

任务：

1. 建立任务状态汇总服务
2. 输出活跃任务查询接口
3. 输出最近完成任务查询接口

完成标准：

1. 任务中心不再依赖前端 mock

---

## 7. 接口联调顺序建议

为了减少联调阻塞，建议按下面顺序进行：

1. 会话列表接口
2. 会话详情接口
3. 发送消息接口
4. 报告详情接口
5. 任务中心接口
6. 文件上传接口

原因：

1. 会话和消息是工作台主链
2. 报告详情是右侧抽屉所需
3. 任务中心属于增强能力
4. 文件上传放后一点可以减少初期联调复杂度

---

## 8. 风险与控制

### 风险一：后端仍然返回自由格式字段

影响：

1. 前端仍然要猜
2. 每个场景都要写分支

控制方式：

1. 统一消息契约
2. 统一报告契约

### 风险二：消息历史只保存纯文本

影响：

1. 历史会话无法恢复结果卡
2. 历史会话无法恢复右侧抽屉数据

控制方式：

1. 消息持久化增加快照字段

### 风险三：任务状态来源不统一

影响：

1. 顶部任务中心会失真
2. 前端显示与真实执行状态不一致

控制方式：

1. 后端统一任务状态聚合

---

## 9. 建议结论

当前阶段，后端最重要的工作不是继续扩展业务字段，而是把已有业务能力整理为前端可直接消费的工作台协议。

优先级建议如下：

1. 先定会话与消息契约
2. 再定报告详情契约
3. 再定任务中心契约
4. 最后再做更深层的内部重构

一句话总结：

**后端先在当前目录结构内，做一个轻量、稳定、少文件的工作台供给层，再逐步演进。**

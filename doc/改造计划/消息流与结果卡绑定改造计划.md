# 消息流与结果卡绑定改造计划

## 1. 文档目的

本文档用于解决当前工作台中“标书审查结果卡片与 AI 回复脱节”的问题，并给出一套消息流重构方案。

本次改造的目标是：

- 让结果卡片真正属于某一条 AI 回复
- 避免结果卡片漂浮在消息流底部成为独立页面块
- 让工作台更像真实的 Agent 对话产品，而不是“消息列表 + 页面结果面板”的拼接

## 2. 当前问题描述

从当前工作台表现来看，存在一个明显的问题：

- AI 回复是一条消息
- 标书审查结果卡片又被单独渲染在消息流后面
- 用户继续追问后，旧卡片仍停留在底部，和新的消息脱节

这会导致以下体验问题：

### 2.1 结果卡片失去上下文

用户看到卡片时，无法第一时间明确：

- 这张卡对应的是哪一轮提问
- 它是上一条 AI 回复的结构化结果，还是当前会话的全局结果

### 2.2 页面像“聊天区 + 独立结果面板”

当前展示方式更像：

```text
消息流
+
页面底部额外挂一张结果卡
```

而不是：

```text
每条 AI 消息
-> 自己的文本
-> 自己的结构化结果
```

### 2.3 后续对话会让历史结果卡片显得位置错乱

用户继续发送：

- “你好”
- “你是谁”

这种无关问题后，原来的标书结果卡仍然停留在消息流底部，视觉上会非常奇怪。

## 3. 正确的产品模型

建议将每条 AI 消息理解为两层内容：

### 第一层：自然语言回复

例如：

- 规则扫描后未保留高风险命中，当前结果显示该批标书在规则维度偏差较小。

### 第二层：结构化结果附件

例如：

- 风险等级
- 风险命中数
- 对比文件数
- 审查说明
- 查看完整报告

也就是说：

**结果卡不是页面级组件，而是消息级组件。**

## 4. 建议的交互原则

### 4.1 一条 assistant message 对应一个可选结果卡

如果某条 AI 回复包含结构化结果，则：

- 文本回复先展示
- 结果卡紧跟其后展示

如果不包含结构化结果，则：

- 只展示普通消息气泡

### 4.2 不再使用全局唯一 `aiResult` 概念

一旦系统中存在：

- 多次分析
- 多个任务
- 多轮追问

全局唯一结果卡会立刻失效。

因此建议：

- 每条消息自己带 `result`
- 页面不再维护一个全局独立结果卡作为主渲染源

### 4.3 历史消息保留历史结果

每轮分析对应的结果卡片，应该固定在对应历史消息下方。

这样用户回看聊天记录时，能自然理解：

- 这轮问了什么
- 这轮 AI 怎么答的
- 这轮结果是什么

### 4.4 页面级详情承接保留，但不替代消息级卡片

页面级仍可保留：

- 报告抽屉
- 任务详情页
- 证据详情页

但这些是“点击卡片后的深入承接”，不能替代消息流里的基础结果卡。

## 5. 当前实现的问题根源

从现有结构判断，当前问题大概率来自以下模式：

- 从消息列表里提取一个全局 `aiResult`
- 在消息列表外单独渲染结果卡

这种方式短期看似简单，但本质上会带来三个结构性问题：

1. 卡片脱离消息上下文  
2. 多轮结果无法共存  
3. 后续扩展多任务、多场景时会越来越乱  

## 6. 建议的数据结构

建议将消息对象统一成如下结构：

```js
{
  id: 'msg_001',
  role: 'assistant',
  content: '规则扫描后未保留高风险命中，当前结果显示该批标书在规则维度偏差较小。',
  timestamp: '2026-03-23T10:00:00Z',
  result: {
    scene: 'TENDER_REVIEW',
    caseId: 'xxx',
    riskLevel: 'LOW',
    score: 0,
    documentIds: ['doc1', 'doc2'],
    summary: '未发现高风险命中',
    evidenceList: [],
    report: {}
  }
}
```

重点是：

- `result` 属于消息对象本身
- 每条消息都可以有或没有 `result`

## 7. 推荐的渲染结构

建议消息流渲染方式改成：

```text
for each message:
  渲染消息气泡
  如果 message.result 存在:
    渲染结果卡
```

即：

```vue
<div v-for="message in messages" :key="message.id">
  <MessageBubble :message="message" />
  <ResultCard v-if="message.result" :result="message.result" />
</div>
```

而不是：

```vue
<div v-for="message in messages" />
<GlobalResultCard :result="aiResult" />
```

## 8. 建议的组件职责

### 8.1 MessageBubble

职责：

- 只负责展示用户或 AI 的文本消息

不负责：

- 展示结构化结果卡

### 8.2 ResultCard

职责：

- 展示该条 assistant message 的结构化审查结果

可展示内容：

- 风险等级
- 核心指标
- 审查说明
- 查看报告 / 查看详情

### 8.3 ReportDrawer / TaskDetail

职责：

- 承接点击卡片后的深层结果查看

## 9. 消息流重构目标

建议将消息流改造成如下模型：

```text
用户消息
-> AI 文本回复
-> AI 结果卡
-> 用户追问
-> AI 回复
-> 如有结构化结果，再显示新的结果卡
```

这样能支持：

- 一次会话中有多个分析结果
- 不同轮分析互不干扰
- 用户回看历史时有自然上下文

## 10. 跟任务体系的关系

结果卡虽然属于消息，但它仍然可以关联任务。

建议在 `result` 中保留：

- `caseId`
- `scene`
- `documentIds`

这样点击卡片时可以：

- 打开完整报告抽屉
- 跳转任务详情页
- 打开处理过程页

也就是说：

- 卡片归属于消息
- 深度数据归属于任务

这两者并不冲突。

## 11. 推荐改造步骤

### 第一阶段：数据结构改造

- 统一消息对象，允许 `message.result`
- 停止依赖全局唯一 `aiResult`

### 第二阶段：渲染结构改造

- 在消息循环内部渲染结果卡
- 删除消息流外部独立结果卡

### 第三阶段：交互承接改造

- 卡片点击打开报告抽屉
- 卡片点击跳任务详情
- 卡片与 `caseId` 建立稳定关联

### 第四阶段：多轮对话验证

验证以下场景：

- 标书分析完成后继续闲聊
- 连续两次发起标书分析
- 历史消息回看
- 同一会话中的不同结果卡共存

## 12. 验收标准

完成后应满足：

- 每张结果卡都紧跟在对应 AI 回复下方
- 用户继续提问后，旧卡片不会漂浮在消息流底部
- 同一会话可存在多张不同分析结果卡
- 每张卡都能打开对应任务详情或完整报告
- 页面结构更像真实 Agent 对话产品

## 13. 结论

当前“结果卡片一直在下面”的问题，本质上不是简单布局问题，而是：

- 消息模型设计有误
- 结果卡被当成页面级组件，而不是消息级组件

正确的改造方向应当是：

- 让每条 assistant message 自己携带 `result`
- 让结果卡片成为该消息的结构化附件
- 页面级组件只负责更深层的详情承接

这样工作台的体验才会真正自然，也更符合 Agent 产品的对话逻辑。

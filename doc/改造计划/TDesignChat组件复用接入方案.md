# TDesign Chat 组件复用接入方案

## 文档目标

本方案用于明确：

1. `@tdesign-vue-next/chat` 在当前项目中可以直接复用哪些能力
2. 哪些页面功能应优先基于该组件库实现
3. 哪些部分可以做薄封装，避免重复造轮子
4. 哪些能力当前组件库不能完全覆盖，仍需业务侧补充

本方案只描述功能与接入策略，不描述具体代码实现。

## 技术前提

前端统一基于以下技术栈开发：

- `Vue 3`
- `tdesign-vue-next`
- `@tdesign-vue-next/chat`

要求：

- 页面壳、按钮、抽屉、标签、表单、弹层等继续使用 `tdesign-vue-next`
- 对话相关基础能力统一使用 `@tdesign-vue-next/chat`
- 不再自行搭建第二套聊天基础组件

## 一、为什么要用这套组件库

对于当前项目来说，`@tdesign-vue-next/chat` 的价值不在于“做一个聊天页”，而在于它已经提供了：

- 对话列表容器
- 消息项展示
- 内容区渲染
- 发送输入区
- 推理区展示
- 消息动作栏
- 加载态
- 附件承载能力

这些都是我们当前 Agent 工作台必须有的通用能力。

如果继续全部自研，会浪费时间在基础交互和通用 UI 上，重复造轮子。

因此本项目应采用：

**“TDesign Chat 负责通用对话能力，业务层只负责监管审查场景的扩展表达。”**

## 二、当前项目最适合复用的组件能力

根据当前已安装包导出的组件能力，可以在本项目中优先复用以下部分。

### 1. `Chat` / `ChatList`

适合承接：

- 会话消息列表
- 自动滚动
- 流式消息追加
- 基础聊天布局

项目中的定位：

- 作为中间主工作区中的消息流容器
- 不再自己手写一套基础消息列表壳

### 2. `ChatItem`

适合承接：

- 单条消息的布局结构
- 用户消息与助手消息的基础区分
- 消息内容区与动作区组合
- 推理区和状态区承载

项目中的定位：

- 作为统一消息渲染骨架
- 用户消息、普通助手消息、错误消息都优先走这个组件体系

### 3. `ChatContent`

适合承接：

- 纯文本内容
- Markdown 内容
- 聊天气泡中的标准内容显示

项目中的定位：

- 普通文本型回复的标准承载组件
- 后续如果后端返回 markdown，可以直接接入

### 4. `ChatSender` / `ChatInput`

适合承接：

- 输入框
- 发送行为
- loading/stop 状态
- 底部输入区域
- 附件列表承载

项目中的定位：

- 作为首页底部输入区的基础组件
- 不再单独手搓一个基础输入条

### 5. `Attachments`

适合承接：

- 待上传附件列表
- 文件项展示
- 附件区域的标准化承载

项目中的定位：

- 用于上传区文件列表展示
- 用于用户消息中的附件展示

### 6. `ChatReasoning`

适合承接：

- “思考中”
- “推理过程”
- “展开/收起的分析说明”

项目中的定位：

- 很适合承接后续的“正在分析”“步骤说明”“过程摘要”
- 可作为后续增强版 Agent 过程可视化的轻量入口

### 7. `ChatAction` / `ChatActionbar`

适合承接：

- 复制
- 重试
- 点赞/点踩
- 分享

项目中的定位：

- 可用于助手回复后的标准操作区
- 先复用通用操作，不急着自定义复杂操作栏

### 8. `ChatLoading`

适合承接：

- 智能体回复 loading
- 流式生成中
- 临时占位态

项目中的定位：

- 替代我们自定义的“AI 正在回复...”卡片

## 三、项目首页应如何使用这套组件库

首页应分成“通用对话区”和“业务扩展区”两层。

### 通用对话区

这部分优先使用 `@tdesign-vue-next/chat`。

包括：

- 消息列表
- 单条消息
- 消息内容
- 输入框
- 发送器
- 加载态
- 消息动作栏
- 附件列表

### 业务扩展区

这部分由项目自行补充，但要挂接在聊天组件体系上。

包括：

- 风险结果卡片
- 报告详情抽屉
- 证据列表
- 审查步骤详情
- 场景快捷入口
- 会话侧边栏
- 顶部任务状态区

原则：

**基础聊天交给组件库，监管业务表达交给业务组件。**

## 四、首页具体复用策略

### 1. 欢迎态

欢迎态不是 `@tdesign-vue-next/chat` 的强项，建议保留业务自定义。

应保留：

- Agent 身份说明
- 三个快捷场景入口
- 上传与输入指引

结论：

- 欢迎态自定义实现
- 但进入消息流后统一切换到 TDesign Chat 组件体系

### 2. 消息流

消息流应作为本项目最重要的复用点。

建议：

- 消息列表容器使用 `Chat`
- 单条消息使用 `ChatItem`
- 普通文本内容使用 `ChatContent`
- loading 使用 `ChatLoading`

这样能直接减少大量基础消息渲染工作。

### 3. 输入区

输入区建议优先改为：

- `ChatSender` 作为底部输入主组件

原因：

- 这类组件本身就适配聊天产品形态
- 已经具备发送、loading、附件承载等能力
- 后续扩展上传也更顺畅

### 4. 附件上传区

上传动作本身仍然是业务逻辑，但附件展示可以优先复用。

建议：

- 文件选择和上传动作：业务自己控制
- 已选择文件列表展示：优先使用 `Attachments`

### 5. 普通回复

普通回复建议直接使用标准聊天组件承接。

建议：

- 纯文本回复：`ChatItem + ChatContent`
- Markdown 回复：`ChatContent`

### 6. 澄清回复

澄清回复本质上还是一条消息，只是语义特殊。

建议：

- 仍使用 `ChatItem + ChatContent`
- 外层增加澄清态样式或图标提示

不建议为澄清消息单独再造一套完整消息骨架。

### 7. 结果卡片回复

这部分组件库不能完全替代。

建议：

- 结果卡片本体继续由业务自定义
- 但挂在 `ChatItem` 的内容区中展示

这样能保证：

- 消息列表风格统一
- 结构化结果又不会被基础聊天组件限制

### 8. 审查详情抽屉

详情抽屉不属于聊天组件库范围。

建议：

- 继续使用 `tdesign-vue-next` 的 `Drawer`

## 五、哪些功能可以不再重复开发

如果采用这套方案，以下能力不建议再自研一遍：

### 1. 基础消息气泡容器

原因：

- 组件库已经提供消息项和内容区承载能力

### 2. 基础聊天输入框

原因：

- `ChatSender` / `ChatInput` 已经覆盖主要使用场景

### 3. 基础消息 loading 样式

原因：

- `ChatLoading` 已经可用

### 4. 基础消息动作栏

原因：

- `ChatAction` / `ChatActionbar` 已有标准能力

### 5. 附件列表基本展示

原因：

- `Attachments` 已提供承载能力

## 六、哪些部分仍然需要业务自定义

虽然这套组件库能复用很多，但以下部分仍然必须由项目自己实现。

### 1. 左侧历史会话栏

原因：

- 这是工作台结构的一部分
- 不是聊天组件库的职责

### 2. 欢迎态快捷场景入口

原因：

- 属于监管业务引导设计

### 3. 风险结果卡片

原因：

- 需要展示风险等级、分数、摘要、查看详情
- 明显属于业务结果组件

### 4. 结果详情抽屉

原因：

- 要承载报告、步骤、证据等结构化信息

### 5. 顶部任务状态区

原因：

- 属于工作台导航层，不是聊天层

### 6. 后端响应映射层

原因：

- 当前后端返回的是业务响应结构
- 需要前端把它映射为聊天组件可消费的数据格式

## 七、推荐的页面分层方式

建议采用以下分层：

### 第一层：页面壳

负责：

- 左侧会话栏
- 顶部状态区
- 中间工作区布局

技术：

- `tdesign-vue-next`

### 第二层：聊天基础层

负责：

- 消息流
- 输入区
- loading
- 动作栏
- 附件

技术：

- `@tdesign-vue-next/chat`

### 第三层：业务扩展层

负责：

- 风险结果卡片
- 结构化详情抽屉
- 场景快捷入口
- 上传逻辑
- 响应映射

技术：

- 项目自定义组件

## 八、推荐的组件使用分工

### 直接使用组件库

- `Chat`
- `ChatItem`
- `ChatContent`
- `ChatSender`
- `ChatLoading`
- `ChatReasoning`
- `ChatAction`
- `Attachments`

### 做薄封装后使用

- `AgentChatList`
  - 内部基于 `Chat`
  - 对外接项目消息格式

- `AgentMessageItem`
  - 内部基于 `ChatItem`
  - 增加 role / type 到展示风格的映射

- `AgentComposer`
  - 内部基于 `ChatSender`
  - 接入上传、发送、loading

### 继续自定义

- `SessionSidebar`
- `QuickActions`
- `ResultCard`
- `ResultDrawer`
- `UploadPanel`

## 九、MVP 阶段接入优先级

为了避免一次改太多，建议按以下顺序接入。

### 第一优先级

- 用 `Chat` 替换消息列表基础壳
- 用 `ChatItem` / `ChatContent` 承接普通消息
- 用 `ChatSender` 承接底部输入区

这是最核心的“去重复造轮子”动作。

### 第二优先级

- 用 `ChatLoading` 替代自定义 loading
- 用 `Attachments` 承接附件展示

### 第三优先级

- 引入 `ChatAction`
- 评估 `ChatReasoning` 是否用于过程说明

## 十、MVP 阶段不建议过度使用的能力

虽然包里还有更多能力，但本期不建议过度展开：

- `Chatbot`
- 更复杂的 `chat-engine hooks`
- 工具调用注册体系
- 复杂活动渲染器

原因：

- 当前项目的核心目标还是先把首页和主链路跑通
- 如果一开始就把复杂 AI engine 体系引入，会增加理解成本

本期应优先复用“UI 组件层”，不要急着引入“完整 agent engine 层”。

## 十一、最终建议

对于当前项目，最佳策略不是“全部自己写”，也不是“全盘交给组件库”。

而是：

**把 TDesign Chat 作为聊天基础设施层使用，把监管审查结果与工作台结构作为业务层自定义实现。**

一句话总结：

- 通用聊天能力：复用
- 工作台结构：自定义
- 结果表达：自定义
- 输入与消息基础壳：复用

## 十二、落地结论

本项目接下来应明确采用以下策略：

1. 对话区改用 `@tdesign-vue-next/chat` 作为基础组件层
2. 停止继续自研基础消息列表、输入条、加载态、附件展示
3. 把开发精力集中在：
   - 会话侧栏
   - 场景欢迎态
   - 风险结果卡片
   - 报告详情抽屉
   - 后端响应映射

这样可以在不牺牲业务表达的前提下，显著降低前端重复建设成本。

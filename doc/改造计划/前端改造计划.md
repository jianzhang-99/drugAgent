# Drug-Agent 前端改造计划

## 1. 项目目标

本计划用于指导 `drug-agent-web` 从“页面原型集合”升级为“可演示、可联调、可逐步产品化”的 Agent 前端。

当前项目的核心问题并不只是视觉效果不统一，而是前端同时存在多套页面实现、多套路由入口、多处静态数据和不完整的任务闭环，导致：

- 用户路径不清晰，不知道从哪里开始使用
- 聊天、任务、报告三类信息没有形成统一承接
- 新旧页面并存，后续开发容易重复劳动
- 页面虽然很多，但真正能跑通的业务闭环较少

本次改造的目标不是单纯“美化界面”，而是先完成产品骨架统一，再逐步完善真实业务闭环，最后再提升视觉与演示效果。

## 2. 成功标准

满足以下条件，可认为前端改造第一阶段成功：

- 工作台只有一套主入口和一套主布局
- 用户可以从工作台发起一次真实 Agent 请求
- 用户可以上传标书并成功创建任务
- 任务看板可以展示真实任务或前端承接的任务数据
- 用户可以进入任务详情查看解析状态和结果摘要
- 聊天、任务、报告三类页面的视觉风格和信息结构保持一致

## 3. 当前现状判断

结合当前代码结构，前端现状可概括为以下几个问题：

### 3.1 页面实现重复

- 新版工作台主路径为 `WorkspaceView`
- 旧版工作台仍保留在 `DrugAgentWorkbench`
- 两套路由和布局同时存在，容易导致后续维护分裂

### 3.2 数据来源不统一

- 会话数据部分来自本地 store
- 任务数据部分仍为 mock
- 顶层 `App.vue` 中仍注入演示 session 数据
- 任务详情页同时混合接口数据与本地状态数据

### 3.3 产品闭环不完整

- 聊天请求、流式输出、上传任务、任务看板、任务详情没有形成统一链路
- 文件上传后虽然已有部分承接，但整体导航和状态沉淀仍不稳定
- “结果展示”更多还是演示卡片，离“可复核的审查结果页”还有距离

### 3.4 视觉与交互风格未收敛

- 有些页面偏 Tailwind SaaS 风格
- 有些页面偏 Element Plus 管理后台风格
- 风格不统一，导致产品感不足
- 视觉重点没有围绕“风险、证据、状态、任务”展开

## 4. 规划原则

本次前端改造遵循以下原则：

- 先收敛结构，再优化样式
- 先打通闭环，再扩展页面
- 先保证一条主路径可用，再做更多入口
- 先让数据来源统一，再谈复杂交互
- 页面定位以“监管审查工作台”为主，而不是通用聊天机器人

## 5. 总体路线图

建议将改造分为 4 个阶段推进。

| 阶段 | 名称 | 周期建议 | 核心目标 |
|---|---|---:|---|
| Phase 1 | 骨架收敛 | 3-4 天 | 统一入口、路由、布局、状态来源 |
| Phase 2 | 最小闭环 | 4-6 天 | 打通聊天、上传、建任务、看板承接 |
| Phase 3 | 结果承接 | 4-6 天 | 任务详情、解析状态、结果展示完善 |
| Phase 4 | 视觉升级 | 3-5 天 | 统一视觉语言、优化演示效果和交互体验 |

总工期建议为 2 到 3 周，可根据人员投入并行推进。

## 6. 阶段拆解

## Phase 1：骨架收敛

### 目标

只保留一套主前端路径，消除新旧页面并存的问题，为后续联调和迭代建立稳定基础。

### 交付物

- 统一后的前端信息架构
- 精简后的路由表
- 统一的工作台主布局
- 统一的会话与任务状态来源

### 任务拆分

| 任务 | 预估 | 依赖 | 完成标准 |
|---|---:|---|---|
| 梳理现有页面入口与功能归属 | 2h | 无 | 输出“保留/废弃/待迁移”清单 |
| 确定主入口以 `/workspace` 为主 | 1h | 页面梳理 | 明确后续所有新能力基于新版工作台推进 |
| 下线或标记旧版 `DrugAgentWorkbench` 路由 | 2h | 主入口确认 | 不再出现双工作台并行开发 |
| 统一顶层布局与侧边栏导航 | 4h | 主入口确认 | 工作台、任务、知识库、设置使用一套布局逻辑 |
| 清理 `App.vue` 中的演示初始化数据 | 2h | 状态梳理 | 顶层不再自动注入 mock session |
| 统一 `session` 和 `task` 的本地承接策略 | 4h | 布局统一 | 前端状态有明确唯一来源 |
| 输出基础页面关系图 | 2h | 路由梳理 | 可用于后续对齐开发 |

### 本阶段重点决策

- 以新版 `WorkspaceView` 为唯一工作台主实现
- 旧版页面仅作参考，不再作为继续堆功能的主页面
- 任务看板、任务详情、知识库全部围绕统一布局重构

## Phase 2：最小闭环

### 目标

让用户真正能从“输入需求”走到“看到结果”或“创建任务”，形成第一条可用链路。

### 交付物

- 可用的工作台聊天区
- 可用的上传和创建任务能力
- 可用的任务看板承接

### 任务拆分

| 任务 | 预估 | 依赖 | 完成标准 |
|---|---:|---|---|
| 统一工作台输入区的请求参数结构 | 2h | Phase 1 | 文本与文件任务调用参数一致 |
| 打通非流式问答链路 | 3h | 参数统一 | 用户可看到真实回复 |
| 补齐消息气泡、加载态、失败态 | 4h | 非流式链路 | 聊天区具备基础可用性 |
| 接入 SSE 流式输出 | 6h | 非流式链路 | 回复可逐段展示并正确结束 |
| 增加上传前校验 | 3h | 输入区稳定 | 支持文件数量、格式、大小、重复校验 |
| 上传后保存 `caseId`、`docId`、场景信息 | 4h | 上传成功 | 前端能承接任务上下文 |
| 创建任务后跳转看板或任务详情 | 3h | 上下文保存 | 用户不会丢失任务路径 |
| 改造任务看板为真实数据 | 6h | 任务承接 | 看板展示真实任务或本地沉淀任务 |

### 本阶段完成后的用户路径

1. 用户进入工作台
2. 输入问题或上传材料
3. 系统返回聊天结果，或创建审查任务
4. 用户在任务看板中看到该任务
5. 用户可继续进入详情页

## Phase 3：结果承接

### 目标

让前端从“能发起任务”升级为“能承接任务结果”，构建真正有业务价值的结果页。

### 交付物

- 任务详情页
- 文档解析状态展示
- 风险摘要与证据链展示
- 基础日志或步骤展示

### 任务拆分

| 任务 | 预估 | 依赖 | 完成标准 |
|---|---:|---|---|
| 定义任务详情页信息架构 | 2h | Phase 2 | 明确每个区块展示什么 |
| 改造任务详情顶部概览区 | 3h | 信息架构 | 展示任务名、状态、时间、文档数 |
| 接入文档解析状态与解析动作 | 4h | 详情页骨架 | 用户能查看单文档或批量解析进度 |
| 展示解析结果摘要与统计 | 4h | 解析状态接入 | 用户能理解“解析出了什么” |
| 展示风险等级、问题摘要、建议动作 | 4h | 解析摘要 | 结果页具备业务判断价值 |
| 展示命中证据、规则、解释说明 | 6h | 风险摘要 | 用户可进行人工复核 |
| 增加状态刷新机制 | 4h | 详情页基础能力 | 任务处理中时页面可更新 |
| 串联看板到详情页跳转 | 2h | 看板真实化 | 形成稳定查看路径 |

### 任务详情页建议固定区块

- 基础信息
- 文档列表
- 解析进度
- 风险摘要
- 命中证据
- 建议动作
- 执行日志

## Phase 4：视觉升级

### 目标

在结构稳定后统一视觉语言，使前端看起来像“监管审查工作台”，而不是几套样式拼在一起。

### 交付物

- 统一色彩和组件风格
- 统一页面层级和留白系统
- 统一风险状态表达
- 更适合演示和汇报的产品视觉

### 任务拆分

| 任务 | 预估 | 依赖 | 完成标准 |
|---|---:|---|---|
| 制定视觉基线和设计 token | 3h | Phase 3 | 有统一的颜色、圆角、阴影、字号规范 |
| 统一主色和风险色体系 | 2h | 视觉基线 | 高中低风险表达一致 |
| 统一工作台、看板、详情页卡片样式 | 6h | 视觉基线 | 三类页面风格一致 |
| 调整输入区、消息区、结果区的层级关系 | 4h | 工作台稳定 | 聊天不再像 demo 页面 |
| 优化空状态、加载态、失败态 | 4h | 组件统一 | 所有核心页面有产品化兜底状态 |
| 优化移动端和常见窗口宽度适配 | 4h | 页面风格统一 | 演示时不容易布局崩坏 |

### 视觉方向建议

- 产品定位：医疗监管与合规审查工作台
- 气质关键词：专业、克制、清晰、可信
- 页面重心：任务、风险、证据、状态
- 避免方向：通用 AI 聊天风、过度炫光、无业务重心的卡片堆叠

## 7. 建议的信息架构

建议保留如下一级导航：

- 工作台
- 任务看板
- 合规知识库
- 系统设置

建议的主链路如下：

```text
工作台
  ├─ 文本问答
  ├─ 上传材料
  └─ 创建任务
       └─ 任务看板
            └─ 任务详情
                 ├─ 文档解析
                 ├─ 风险摘要
                 ├─ 命中证据
                 └─ 执行日志
```

## 8. 关键依赖关系

```text
骨架收敛
  -> 工作台请求统一
  -> 上传与任务承接
  -> 看板真实化
  -> 任务详情承接
  -> 视觉统一
```

说明：

- 若不先完成骨架收敛，后续在两套工作台上补功能会持续分裂
- 若看板仍为 mock，则任务详情和结果承接难以稳定
- 若没有稳定的任务详情页，聊天结果就只能停留在临时展示层

## 9. 风险与应对

| 风险 | 影响 | 概率 | 应对策略 |
|---|---|---|---|
| 新旧页面同时继续开发 | 高 | 高 | 先冻结旧页面，只保留一个主实现 |
| 后端接口暂未完全齐备 | 高 | 中 | 采用“真实接口优先，本地状态兜底”的策略 |
| 样式优化过早开始 | 中 | 高 | 明确先做结构和闭环，再做视觉升级 |
| 页面很多但职责不清 | 高 | 中 | 先输出页面职责表，再进入开发 |
| 任务状态来源不统一 | 高 | 高 | 将任务上下文统一沉淀到 store 或 local-state |

## 10. 资源建议

如果只有 1 名前端，建议顺序推进：

1. Phase 1 骨架收敛
2. Phase 2 最小闭环
3. Phase 3 结果承接
4. Phase 4 视觉升级

如果有 2 人协作，建议并行方式如下：

- 前端 A：主负责工作台、路由、状态、聊天链路
- 前端 B：主负责任务看板、任务详情、结果承接

共同约定：

- 先统一设计 token 和页面骨架
- 共享同一套任务数据结构
- 避免在旧版 `DrugAgentWorkbench` 上继续堆新功能

## 11. 第一周执行建议

建议第一周只做最关键的事情，不追求页面全面铺开。

### Day 1

- 梳理现有页面和路由
- 确定主入口和主布局
- 输出保留与废弃清单

### Day 2

- 清理顶层 mock 数据
- 统一会话和任务状态承接方式
- 整理工作台请求参数结构

### Day 3

- 打通工作台非流式问答
- 补齐消息展示、加载态、失败态

### Day 4

- 接入 SSE 流式输出
- 处理消息追加与异常中断

### Day 5

- 完成文件上传校验
- 创建任务后承接 `caseId/docId`
- 让看板显示真实任务

## 12. 建议优先调整的代码区域

建议优先处理以下文件：

- `drug-agent-web/src/router/index.js`
- `drug-agent-web/src/App.vue`
- `drug-agent-web/src/views/WorkspaceView.vue`
- `drug-agent-web/src/views/TaskBoardView.vue`
- `drug-agent-web/src/views/TaskDetail.vue`
- `drug-agent-web/src/stores/session.js`
- `drug-agent-web/src/api/drug-agent.js`

这些文件基本决定了：

- 用户从哪里进入产品
- 工作台是否是唯一入口
- 任务是否能真正被承接
- 结果页是否能形成闭环

## 13. 最终建议

当前阶段最重要的不是继续加页面，而是先完成这三件事：

- 收敛为一套工作台和一套路由
- 打通“提问/上传 -> 任务 -> 看板 -> 详情”的主闭环
- 用统一视觉语言表达风险、证据、状态和任务

只要这三件事完成，前端就会从“一团糟的原型集合”变成“有产品感的 Agent 审查平台”。

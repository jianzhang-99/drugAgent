# 03 检索层

很多同学做 Agent 时，一开始最容易陷入一个误区：

“模型已经很强了，为什么还要做检索层？”

这个问题很常见，而且很正常。

因为如果只是做一些泛化问答，单靠模型本身，很多时候确实已经能答得像模像样。

但如果你做的是业务 Agent，尤其是像医药监管、标书审查、合同预审、风险预警这种场景，那么只靠模型内部知识，通常是不够的。

原因很简单：

- 模型知识可能过期
- 模型不知道你的私域材料
- 模型不知道你当前组织内部的制度、模板、规范和样本
- 模型即使回答得像对的，也未必能给出可追溯证据

这时，检索层就变得非常关键。

它的本质，不是为了“让系统显得更高级”，而是为了让 Agent 在回答时，能够先找到证据，再基于证据说话。

这就是检索层存在的意义。

## 1. 什么是检索层

在这个项目里，检索层可以先理解成一句话：

在模型作答之前，先从知识库中找出和当前问题最相关的内容片段，再把这些片段作为证据提供给模型。

也就是说，检索层不直接替代模型，也不直接替代业务 Workflow。

它的职责更像一个资料员：

- 先帮系统找材料
- 再把材料整理给模型
- 最后由模型基于这些材料给出回答

如果没有这一层，模型就只能依赖自己参数里记住的知识。

如果有了这一层，模型就可以在回答前先看一遍“现场材料”。

这对业务 Agent 来说，价值非常大。

## 2. 为什么业务 Agent 一定要有检索层

这个问题我建议你一定要从业务角度来理解，而不是只从技术潮流角度理解。

### 2.1 模型不知道你的私域知识

例如在这个项目里，很多真正有价值的材料都不是公开知识，而是业务内部资料，比如：

- 标书样本
- 合同模板
- 审查口径
- 风险案例
- 监管制度文本
- 企业内部规范

这些内容，大模型天然是不知道的。

如果系统不做检索，模型即使很聪明，也只能做泛泛回答。

### 2.2 业务回答需要证据

对于普通聊天应用来说，“回答得像那么回事”有时就够了。

但对业务 Agent 来说，尤其是医药监管、招投标审查这类场景，回答通常不能只靠语气自信。

系统最好能说明：

- 依据是什么
- 证据来自哪里
- 哪一段内容支撑了这个判断

这时检索层就不只是“提高正确率”，还承担了“建立证据链”的作用。

### 2.3 模型知识有时间边界

模型训练语料不是实时更新的。

而业务系统往往非常依赖最新资料，比如：

- 新版本制度
- 新合同模板
- 新业务规范
- 新案例样本

如果不通过检索补充这些内容，模型回答会越来越脱离真实业务上下文。

### 2.4 检索层让系统更可控

没有检索层时，模型回答基本是“内部记忆驱动”。

有了检索层后，系统至少可以做到：

- 回答前先找依据
- 证据不足时提示人工复核
- 对引用内容进行回显

也就是说，检索层让整个 Agent 从“会聊天”向“会基于证据工作”迈了一步。

## 3. 检索层和知识库不是一回事

这也是很多初学者容易混淆的一点。

知识库是“存量材料”，  
检索层是“把这些材料找出来并组织给模型使用的那一层”。

你可以这样理解：

- 知识库解决“材料放在哪里”
- 检索层解决“当前问题该取哪几份材料”

如果只有知识库，没有检索层，那么系统只是把材料堆在那里。

只有当系统能够根据问题，从知识库中筛出相关片段，并把它们送到模型面前，这套知识才真正被用起来。

## 4. 简易 RAG 的主链路是什么

在当前项目阶段，我更推荐用一条简单、清晰、能快速跑通的检索主链路，而不是一开始就做很复杂的多路召回、重排、图谱增强。

最小可用的 RAG 主链路可以写成：

```text
上传文档
-> 文本提取
-> chunk 切分
-> embedding
-> 向量库存储

用户提问
-> query embedding
-> 向量检索 top-k
-> 拼装上下文
-> 交给模型回答
-> 返回答案 + 引用
```

这条链路看上去简单，但非常重要，因为它已经形成了一个完整闭环。

只要这条主链路跑通，你的系统就已经不是一个“纯靠模型内部知识聊天”的系统，而是一个真正具备检索增强能力的业务 Agent。

## 5. 我建议你怎么理解这条主链路

接下来我用更偏导师式的方式，把这条链路拆开讲一遍。

### 5.1 上传文档

第一步不是提问，而是先让系统拥有可检索的材料。

这些材料可以是：

- 制度文件
- 规范文本
- 合同模板
- 审查案例
- 风险样本

没有材料，RAG 就没有意义。

所以从工程角度看，RAG 的第一步不是“问”，而是“先建库”。

### 5.2 文本提取

文档上传后，系统要先把里面的文本提出来。

这个阶段的职责是：

- 识别文档内容
- 转成统一文本格式
- 保留必要的来源信息

它不需要在这个阶段做复杂判断。

因为这一步只是给后续切块和入库准备原始材料。

### 5.3 chunk 切分

提取出全文后，不能直接把一整篇文档塞给向量库。

原因很简单：

- 文档太长
- 相似度检索粒度太粗
- 后续引用不方便

所以要把文本切成若干块，也就是 chunk。

这里一定要有一个意识：

chunk 不是随便切的。

切得太大：

- 检索不准
- 噪音太多

切得太小：

- 语义不完整
- 模型读不出上下文

所以比较推荐的做法是：

- 优先按章节、标题、段落切
- 超长段落再按长度切
- 相邻 chunk 保留少量重叠

这是“结构优先，长度兜底”的思路。

### 5.4 embedding

切块完成后，系统要把每个 chunk 转成向量。

你可以把这一步理解成：

把一段文本转换成一个可以被相似度计算的数学表达。

之后用户提问时，问题也会被转成向量。

这样系统就能比较：

- 这个问题的向量
- 哪些 chunk 的向量最接近

这就是向量检索的基础。

### 5.5 向量库存储

每个 chunk 生成向量后，就要写入向量库。

除了文本本身，最好还要一起存 metadata，例如：

- `orgId`
- `scene`
- `subScene`
- `docType`
- `sourceId`
- `sourceTitle`
- `chunkId`

为什么要存这些？

因为业务检索不是全库裸搜。

比如你这个项目里，后面很可能同时存在：

- 标书审查知识
- 合同预审知识
- 风险预警知识

如果没有 metadata，系统后续检索时就很难先做范围收敛。

## 6. 用户提问后的查询链路

入库完成后，真正的 RAG 查询才开始。

### 6.1 query embedding

用户提问后，先把问题转成向量。

这一步和入库时对 chunk 做 embedding 是同一个逻辑，只不过：

- 入库时处理的是知识片段
- 查询时处理的是用户问题

这样两者才能在同一个向量空间里比较相似度。

### 6.2 向量检索 top-k

问题向量生成后，系统从向量库里找到最相近的几个 chunk。

这通常叫 `top-k` 检索。

例如：

- top-3
- top-5
- top-8

在简易版里，我更建议先从 `top-5` 这种较小值开始。

因为如果一开始检索太多：

- Prompt 会变长
- 噪音会增加
- 模型反而容易不聚焦

### 6.3 拼装上下文

把 top-k 取回来后，不要直接把几段文本随便拼一起扔给模型。

更稳的做法是，把它们组织成清晰的证据上下文，例如：

```text
问题：
xxx

检索证据：
[1] 来源：xxx
内容：xxx

[2] 来源：xxx
内容：xxx

要求：
1. 只能基于以上证据回答
2. 证据不足时要明确说明
```

这一步非常重要。

因为这决定了模型会把这些内容当作“真正证据”，还是只是“额外背景材料”。

### 6.4 交给模型回答

上下文拼装完成后，再把它交给模型。

注意这里的模型角色已经发生变化了。

在没有检索层时，模型是“凭内部记忆作答”。  
在有检索层时，模型更像“读完资料后再作答”。

这会显著提升回答的针对性和可解释性。

### 6.5 返回答案和引用

最后系统返回的结果，建议不要只是一段 `answer`。

至少还应该带上：

- `citations`
- `decision`
- `reason`

也就是说，系统不仅告诉前端“答案是什么”，还告诉前端：

- 我依据了哪些片段
- 我是正常命中还是证据不足
- 当前结果是否需要人工复核

这一步，才真正让 RAG 成为业务能力，而不是一个隐藏在内部的技术细节。

## 7. 为什么我建议你先做“简易 RAG”

这里我特别想强调一个工程观念：

RAG 并不是越复杂越好。

很多团队一开始做检索，就很容易上来就想做：

- 多路召回
- BM25 + 向量混合
- rerank
- query rewrite
- graph retrieval
- long context agent

这些能力当然都有价值。

但对于当前项目阶段，更重要的是先把主链路跑直。

也就是说，先保证：

- 文档能入库
- 问题能检索
- chunk 能被送给模型
- 模型能基于证据回答
- 结果能返回引用

只要这五件事稳定了，后面的增强能力都可以逐步加。

如果一开始就追求复杂，很容易出现一个情况：

技术名词很多，系统看起来很先进，但真正主链路并不稳定。

所以我更推荐你把当前检索层理解成：

先做一条简单、清晰、可维护的检索闭环。

这才是最重要的。

## 8. 检索层在这个项目里的边界

这部分一定要讲清楚，不然后面很容易越层。

### 8.1 检索层不负责场景路由

场景路由应该由上层编排层来做，比如：

- 这是标书审查
- 这是合同预审
- 这是风险预警

检索层只负责在已知业务范围内找资料。

它不应该代替 Agent 的路由层。

### 8.2 检索层不负责 Workflow 主执行

检索层可以给 Workflow 提供知识支持，但不应该直接替代 Workflow。

比如：

- 标书规则命中
- 风险融合
- 证据组装
- 审查报告生成

这些都仍然属于 Workflow 或场景执行层的职责。

检索层只是“增强信息输入”，不是“接管业务主流程”。

### 8.3 检索层不等于业务规则引擎

如果某些逻辑只是：

- 看 query 里有没有某个词
- 根据 focus 加减分
- 根据标签推断风险

这更像规则判断或策略评分。

它可以存在，但不要和“知识检索”混为一谈。

这点很重要。

因为：

- 检索层找的是知识证据
- 规则层做的是业务判断

两者都可能有价值，但职责不同。

## 9. 检索层最少应该返回什么

从教材角度，我建议你记住一个很实用的最小输出结构：

```json
{
  "decision": "ANSWERED",
  "reason": "HIT",
  "answer": "......",
  "citations": [
    {
      "chunkId": "DOC-001-0",
      "sourceTitle": "xxx",
      "snippet": "xxx",
      "score": 0.87
    }
  ]
}
```

这样设计的好处是：

- 前端能直接展示引用
- 上层编排能判断当前是否需要人工复核
- Workflow 能消费这个结果
- 会话层也能记录结构化状态

这会比“只返回一段回答文本”成熟很多。

## 10. 这一节最重要的结论

最后，把这一节收束成一句最核心的话：

检索层的价值，不是让模型看起来更聪明，而是让系统在回答前先找到证据。

对于当前项目来说，一个足够好的简易检索层，不需要一开始就很复杂，只要先跑通下面这条主链路就已经很有价值：

```text
上传文档
-> 文本提取
-> chunk 切分
-> embedding
-> 向量库存储

用户提问
-> query embedding
-> 向量检索 top-k
-> 拼装上下文
-> 交给模型回答
-> 返回答案 + 引用
```

如果再向前一步，更推荐补上业务 metadata 过滤：

- `orgId`
- `scene`
- `subScene`
- `docType`

这样你的检索层就不仅能“找到相似文本”，还能更稳定地服务业务 Agent 的真实场景。

一句话总结：

没有检索层，模型是在“凭记忆回答”；  
有了检索层，模型才是在“基于证据回答”。

这正是业务 Agent 走向工程化的关键一步。

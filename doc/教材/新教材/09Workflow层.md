# 06 Workflow层

在整个业务 Agent 架构里，Workflow 层通常是最容易被低估，但其实最关键的一层。

因为很多同学一开始做 Agent 时，注意力往往都在：

- 模型怎么接
- Prompt 怎么写
- Tool 怎么调
- 前端怎么展示

这些当然都重要。

但如果你做的是业务 Agent，真正决定系统能不能稳定工作的，往往不是模型那一层，而是 Workflow 这一层。

因为模型可以让系统看起来更聪明，  
但 Workflow 才决定系统做事是不是稳定、可控、可重复。

## 1. 什么是 Workflow 层

在这个项目里，Workflow 层可以先理解成一句话：

把一个业务场景真正跑完的确定性执行引擎。

这里最关键的词是：

- 业务场景
- 跑完
- 确定性

也就是说，Workflow 关心的不是“怎么聊天”，而是“这件业务到底怎么执行”。

例如在标书审查场景里，一个真正完整的 Workflow 可能包括：

- 文档解析
- 结构化提取
- 规则命中
- 豁免处理
- 风险融合
- 证据组装
- 报告生成

这些动作合在一起，才构成“业务执行主链路”。

这就是 Workflow 层的意义。

## 2. 为什么业务 Agent 一定要有 Workflow 层

很多时候，大家会误以为：

“只要模型够强，直接让模型判断不就好了？”

这个想法在泛化问答里可能还勉强成立。

但在业务 Agent 里，通常不够。

### 2.1 业务执行要稳定

业务系统需要的是：

- 同样输入，结果基本稳定
- 过程可复核
- 输出可解释

如果把完整执行链路都交给模型自由发挥，结果很容易随着表达方式、上下文、Prompt 细节而波动。

而 Workflow 的价值就是把真正关键的业务步骤固定下来。

### 2.2 业务规则不能全靠模型记忆

像标书审查、合同预审、风险预警这种场景，很多核心逻辑其实并不是“知识问答”，而是明确的业务判断链。

例如：

- 哪些规则算命中
- 哪些命中可豁免
- 不同风险因子如何融合
- 哪些证据必须出现在报告中

这些更适合交给确定性的 Workflow，而不是交给模型即兴发挥。

### 2.3 业务系统需要可拆分执行步骤

真实业务执行通常不是“一步到位”的。

它往往天然就是分阶段的：

- 准备数据
- 校验数据
- 运行规则
- 汇总结果
- 输出报告

Workflow 正好就是把这些步骤稳定地串起来。

## 3. 当前项目里的 Workflow 应该怎么理解

结合你当前项目的整体设计，Workflow 层的定位其实已经非常明确：

Workflow 是确定性业务执行引擎。

在标书审查场景里，底层的 [`TenderReviewWorkflow.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/scene/tender_review/workflow/TenderReviewWorkflow.java) 就代表这样一种角色。

它不是前端入口，也不是会话编排层，更不是通用路由层。

它的任务是：

一旦场景已经确定、数据已经准备好，就按既定业务链把审查真正执行下去。

这就是 Workflow 在这个项目里的核心地位。

## 4. Workflow 层到底负责什么

在你这个项目里，我建议始终把 Workflow 层理解成“业务执行主链路”，重点负责下面这些事情。

### 4.1 数据执行主链路

Workflow 要真正把业务跑起来。

例如标书审查里，至少要把：

- 输入文档
- 结构化数据
- 规则体系
- 风险结论

串成一条稳定链路。

### 4.2 规则命中

如果一个场景依赖明确业务规则，那么命中逻辑应尽量下沉到 Workflow。

因为规则命中本身就是业务执行的一部分，不属于上层聊天编排。

### 4.3 豁免处理

很多业务判断不是“命中就结束”，而是还要进一步判断：

- 有没有合理豁免
- 是否属于低风险同源
- 是否有上下文解释能消除风险

这类逻辑天然属于 Workflow。

### 4.4 风险融合

一个场景很少只看一条规则。

通常需要：

- 合并多个规则命中结果
- 形成最终风险等级
- 计算综合评分

这一步不适合放在上层 Service，更不适合放在 LLM 里自由总结。

### 4.5 证据组装与报告生成

业务 Agent 的结果不能只有一句“有风险”或“没风险”。

通常还要有：

- 命中证据
- 风险说明
- 核心结论
- 报告结构

这些也应该尽量在 Workflow 内形成稳定结果。

## 5. Workflow 层不应该负责什么

这一部分一定要讲清楚，因为 Workflow 很容易被误用。

### 5.1 不负责 HTTP 语义

Workflow 不应该关心：

- 请求是不是从 Controller 来的
- 是 JSON 还是 multipart
- 前端返回结构长什么样

这些都属于接入层和响应层。

### 5.2 不负责会话管理

Workflow 不应该直接关心：

- `sessionId`
- `chat_message`
- 会话标题
- summary
- session_state

这些属于会话层和编排层。

### 5.3 不负责通用场景路由

Workflow 不应该先判断：

- 这是不是标书审查
- 这是不是合同预审

这些判断应该在上层就做完。

Workflow 一旦开始执行，默认场景已经确定。

### 5.4 不负责前端展示文案

Workflow 可以输出结构化结论和报告对象，
但不要在里面塞太多面向前端的对话式包装文案。

否则它会逐渐承担本不属于自己的表现层职责。

## 6. Workflow 和 Tool 怎么区分

这个问题特别常见。

我建议你用一句最实用的话记住：

Tool 是标准化入口，Workflow 是真正执行引擎。

举个例子。

### Tool 负责

- 接收参数
- 做输入校验
- 整理请求
- 调 Workflow
- 返回结构化结果

### Workflow 负责

- 业务执行主链路
- 规则命中
- 豁免处理
- 风险融合
- 证据组装
- 报告生成

如果 Tool 越来越像 Workflow，那说明 Tool 过厚了。  
如果 Workflow 开始关心 HTTP、会话、前端，那说明 Workflow 越层了。

## 7. Workflow 和模型的关系

这也是很重要的一点。

很多人会把“模型”当成 Workflow 的替代品。

其实更好的理解应该是：

- Workflow 负责确定性业务执行
- 模型负责理解、补充、整理和表达

也就是说，在业务 Agent 里：

- 模型不是万能控制器
- Workflow 也不是模型附属品

两者更像分工协作关系。

例如：

- 模型可以帮助判断意图
- 模型可以基于结构化结果生成用户可读解释
- 但 Workflow 负责真正把规则和业务逻辑跑完

这才是比较稳的工程化做法。

## 8. 为什么 Workflow 要尽量确定性

这一点是我特别想强调的。

业务 Workflow 一旦不确定，后面整个系统都会变得不稳定。

确定性的价值包括：

- 便于测试
- 便于复现
- 便于调试
- 便于审计
- 便于报告解释

这对医药监管类场景尤其重要。

因为你面对的不是“随便聊一聊”的应用，而是可能需要：

- 给业务人员看
- 给管理人员看
- 给合规人员看
- 被进一步复核

这时，结果是否能稳定复现，比“偶尔显得更聪明”更重要。

## 9. 在当前项目里，Workflow 层最关键的边界

结合你整个项目的分层约束，我建议教材里始终强调一句话：

Workflow 是确定性业务执行引擎，不是前端会话编排器，也不是自由 Agent。

这句话看起来简单，但很重要。

只要守住它，后面很多架构问题都会自然变简单。

例如：

- AgentChatService 不会再直接堆业务逻辑
- Tool 层不会不断膨胀
- 路由层不会反过来做执行
- 模型也不会被迫承担不稳定的主业务判断

## 10. 这一节最重要的结论

最后把这一节收束成一句最核心的话：

业务 Agent 之所以能从“会聊天”走向“会做事”，靠的不是模型越来越自由，而是 Workflow 越来越稳定。

对当前项目来说，一个合格的 Workflow 层至少应该做到：

- 承担业务执行主链路
- 下沉规则命中与豁免处理
- 形成稳定风险融合逻辑
- 输出结构化证据和报告
- 不越层处理路由、会话和前端协议

一句话总结：

没有 Workflow，系统只是“会回答”；  
有了 Workflow，系统才真正开始“会执行”。

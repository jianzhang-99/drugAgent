# 05 模型层

很多同学做 Agent 项目时，一提到“模型层”，脑子里马上想到的就是：

- 接一个大模型
- 发一段 Prompt
- 拿一段回答

这当然是模型层最直观的样子。

但如果你做的是业务 Agent，那么模型层绝对不只是“调一下模型接口”这么简单。

它真正要解决的问题是：

- 系统应该什么时候用模型
- 模型负责做什么
- 模型不应该做什么
- 模型结果如何稳定地接入业务链路

所以在这个项目里，模型层也值得单独拆开讲。

## 1. 什么是模型层

在这个项目里，模型层可以先理解成一句话：

负责承接系统中的大模型调用能力，并把模型能力以稳定、可控的方式提供给上层使用。

这里最关键的词有两个：

- 模型调用能力
- 稳定、可控

也就是说，模型层不是一个“随手调一下 API”的工具函数，而是整个系统对 LLM 能力的统一封装层。

如果把整个 Agent 系统比作一个业务团队，那么模型层更像一个外部专家顾问系统：

- 有问题时可以向它咨询
- 它能给出理解、整理、表达能力
- 但它不是整个业务系统的唯一执行核心

这就是模型层的正确定位。

## 2. 为什么业务 Agent 一定要单独看模型层

很多项目一开始没把模型层单独抽出来，后面很快会遇到几个典型问题：

- 到处散落着模型调用代码
- 不同地方 Prompt 风格不一致
- provider 切换困难
- 调试和追踪很麻烦
- 模型开始承担本不该由它承担的业务职责

这背后的根本原因是：

模型层没有被当作一个独立层来治理。

而在业务 Agent 里，模型能力一定会被反复使用，例如：

- 意图理解
- 标题生成
- 对检索结果做回答整理
- 对 Tool 结果做用户可读总结
- 做澄清问题生成

如果这些调用没有统一入口，系统会越来越乱。

## 4. 模型层到底负责什么

在这个项目里，我建议始终把模型层的职责控制在下面几件事上。

### 4.1 提供统一模型调用入口

模型层首先要解决的是：

上层不需要关心底层到底接的是哪个 provider。

也就是说，上层更应该看到的是：

- 一个统一请求对象
- 一个统一响应对象
- 一个统一调用入口

而不是到处都是 provider-specific 的调用代码。

### 4.2 屏蔽底层 provider 差异

不同模型供应商之间，通常会有很多差异：

- 请求参数格式不同
- 流式响应格式不同
- 温度、模型名、token 配置方式不同
- 返回结构不同

这些差异应该尽量在模型层内部被吸收，而不是泄露到业务编排层。

### 4.3 承接 Prompt 输入与模型输出

模型层天然是 Prompt 和模型返回之间的桥梁。

它负责：

- 接收上层整理好的 Prompt
- 调用模型
- 返回统一模型结果

它不一定负责写 Prompt 本身，但必须负责把 Prompt 稳定地送达模型。

### 4.4 提供同步与流式能力

一个成熟的模型层，通常要同时支持：

- 同步调用
- 流式调用

因为不同场景对返回方式的要求不同。

例如：

- 标书审查结果卡片，通常更适合同步结构化返回
- 通用聊天场景，前端有时希望用流式打字机效果

所以模型层最好天然支持这两类能力。

## 5. 模型层不应该负责什么

### 5.1 不负责业务路由

模型层不能因为自己能理解语义，就直接开始承担：

- 场景路由
- 场景分发
- 业务链路决策

如果需要模型参与分类，也应该由路由层或编排层发起调用，而不是让模型层自己做路由。

### 5.2 不负责 Workflow 主执行

模型层可以辅助理解、总结、生成表达，但不应该直接替代：

- 规则命中
- 风险融合
- 报告生成主逻辑

这些仍然应该以确定性业务链路为主。

### 5.3 不负责会话状态管理

模型层不应该直接关心：

- `session_state`
- `chat_message`
- 会话标题持久化
- summary 回写

这些属于会话层和编排层。

### 5.4 不负责前端展示协议

模型层返回的应该是统一的模型结果，而不是直接拼前端最终响应对象。

否则模型层会和响应层混在一起。

## 6. 在业务 Agent 里，模型到底该做什么

这是我特别想讲清楚的一点。

在业务 Agent 里，模型最适合做的通常是四类事情：

### 6.1 理解

例如：

- 理解用户意图
- 理解 query 里的重点
- 理解上下文中哪些信息更关键

### 6.2 分类

例如：

- 规则层无法判断时，做轻量场景分类
- 对某些输入做初步语义归类

### 6.3 整理

例如：

- 把检索结果整理成自然语言回答
- 把 Tool/Workflow 结果整理成用户可读说明

### 6.4 表达

例如：

- 生成标题
- 生成澄清问题
- 生成总结性说明

你会发现，这四类事情有一个共同点：

它们都更偏“理解与表达”，而不是“底层业务执行”。

这正是模型层的优势所在。

## 7. 为什么模型层不能无限上升为“总控制器”

很多同学做 Agent 时，很容易被一种想法吸引：

“既然模型这么强，那不如让它全程自己决定怎么走。”

这种方案看上去很灵活，但在业务系统里通常有几个明显问题：

- 不稳定
- 难测试
- 难复现
- 难解释
- 成本不透明

尤其在你这个项目里，很多业务场景都要求：

- 结果可解释
- 链路可控
- 输出有证据

这就决定了模型层更适合作为“能力增强层”，而不是“自由总控制器”。

## 8. 模型层和检索层是什么关系

这两个层次很容易被混淆。

你可以这样理解：

- 检索层负责找证据
- 模型层负责基于证据组织回答

也就是说，在 RAG 链路里：

```text
用户问题
-> 检索层召回证据
-> 模型层基于证据回答
```

这里模型层不是凭记忆裸答，而是基于检索层提供的上下文来完成回答。

这就是业务 Agent 中“基于证据回答”的关键逻辑。

## 9. 模型层和 Tool / Workflow 的关系

这部分也很重要。

### 模型层更偏“理解与表达”

### Tool / Workflow 更偏“执行与结果生成”

所以在一个稳定的业务链路里，更常见的关系是：

```text
编排层
-> Tool / Workflow 得到结构化结果
-> 模型层把结构化结果整理成用户可读回复
```

这比让模型直接替代整个 Tool / Workflow 要稳得多。

## 10. 当前项目里，模型层最重要的边界

结合你当前项目的分层约束，我建议教材里始终强调一句话：

模型层提供的是“大模型能力”，不是“业务主逻辑本身”。

这句话非常关键。

只要守住它，后面很多架构问题都会自然简单很多：

- 编排层不会被模型绑架
- Workflow 不会被模型替代
- 会话层不会被模型调用细节污染
- 检索层也不会被模型自由发挥打乱

## 11. 这一节最重要的结论

最后把这一节收束成一句最核心的话：

在业务 Agent 里，模型层最重要的价值，不是让系统“显得智能”，而是把理解、分类、整理、表达这些能力，以稳定、可控的方式接入业务链路。

对当前项目来说，一个合格的模型层至少应该做到：

- 统一模型调用入口
- 屏蔽 provider 差异
- 支持同步与流式调用
- 承接 Prompt 和统一返回结果
- 不越层做业务路由、Workflow 执行和会话管理

一句话总结：

没有模型层，系统只是“零散地调用大模型”；  
有了模型层，系统才真正拥有“可治理的大模型能力”。

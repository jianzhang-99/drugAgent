# 04 路由层

很多业务 Agent 项目，真正开始变乱的第一个地方，往往不是模型，也不是 Workflow，而是路由层。

因为只要系统开始支持多个场景，入口层马上就会遇到一个问题：

“这次请求到底应该进哪个场景？”

如果这个问题没有被单独收口，而是散落在：

- Controller 里判断一点
- ChatService 里判断一点
- Tool 里再判断一点
- Workflow 里兜底一点

系统很快就会进入一种典型状态：

- 同一个请求，不同入口判断结果不一致
- 规则改一次，要改很多地方
- 新增场景时，不知道应该改哪里
- 路由原因说不清楚

所以在业务 Agent 里，路由层一定要单独看待。

## 1. 什么是路由层

在这个项目里，路由层的职责可以先理解成一句话：

根据当前请求内容，判断这次请求应该进入哪个业务场景。

注意这里有两个关键词：

- 判断
- 进入哪个场景

这意味着路由层只负责“选路”，不负责“走完整条路”。

如果把整个 Agent 系统比作一个医院导诊台，那么路由层更像分诊台：

- 它负责判断你该去哪个科室
- 但它不负责替医生看病

这个比喻非常重要。

因为一旦你让路由层开始直接做业务结果，它就不再是路由层了，而是半个业务服务。

## 2. 为什么路由层必须单独存在

很多同学一开始做 Agent，会觉得：

“反正场景也不多，我就在 `AgentChatService` 里写几个 if else 不就好了？”

这个想法在非常早期的 Demo 阶段没什么问题。

但一旦进入业务项目，它很快会遇到三个问题。

### 2.1 场景会越来越多

今天可能只有：

- 标书审查
- 默认对话

明天很可能就会变成：

- 标书审查
- 合同预审
- 风险预警
- 合规问答
- 知识检索

如果没有单独路由层，这些判断会越来越分散。

### 2.2 路由规则会持续变化

场景路由不是写一次就结束的。

它会不断变化，例如：

- 前端开始支持 `sceneHint`
- 文件上传默认推到文档场景
- 某些关键词要提高优先级
- 某些场景必须先澄清再进入

如果这些变化分散在多个类里，维护会很痛苦。

### 2.3 路由需要可解释

业务 Agent 和普通聊天机器人不一样。

系统很多时候需要告诉前端或者日志：

- 这次为什么进入这个场景
- 是规则命中的，还是用户显式指定的
- 置信度大概是多少

如果没有独立路由层，这些信息很容易丢失，或者根本没有被结构化表达出来。

## 3. 当前项目里的路由层长什么样

结合当前项目来看，路由逻辑当前主要收在 [`AgentSceneService.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentSceneService.java) 里。

它现在做的事情，本质上已经比较像一个轻量路由层了。

当前顺序大致是：

1. 先看 `sceneHint`
2. 再看 `metadata.sceneHint`
3. 再做关键词匹配
4. 再看是否有上传文件
5. 最后 fallback 到默认对话

从工程角度看，这已经比“到处散落的判断逻辑”好多了。

因为它至少做到了：

- 路由集中
- 路由顺序明确
- 能返回 `scene / source / reason / confidence`

这已经有了路由层的雏形。

## 4. 路由层到底负责什么

在你这个项目里，我建议始终把路由层的职责控制在下面四件事之内：

1. 读取请求中的路由线索  
   例如：
   - `sceneHint`
   - `metadata`
   - query 关键词
   - 是否上传文件

2. 做场景判断  
   例如：
   - `TENDER_REVIEW`
   - `CONTRACT_PRECHECK`
   - `RISK_ALERT`
   - `DEFAULT`

3. 生成路由决策对象  
   例如：
   - `scene`
   - `source`
   - `reason`
   - `confidence`

4. 返回给上层编排使用  
   路由层的输出，应该供编排层做后续分发。

除此之外，它最好不要继续承担更多职责。

## 5. 路由层不应该负责什么

这一部分特别关键。

### 5.1 不负责最终业务结果

路由层不能因为自己判断出是“标书审查”，就顺手开始直接生成审查结论。

这不是它的职责。

它最多只能说：

- “我认为应该进入标书审查”
- “原因是 query 命中了围标、串标、标书审查关键词”

真正的审查结果应该交给场景执行层和 Workflow。

### 5.2 不负责 Tool 调用细节

如果后面某个场景通过 Tool Calling 执行，那么：

- 路由层只负责说“该进哪个场景”
- 不负责说“注册哪些 Tool、按什么顺序调 Tool”

否则路由层会越来越厚。

### 5.3 不负责会话聚合状态

例如：

- 当前是否等待补文件
- 当前是否等待澄清
- 当前会话挂起在哪一步

这些属于会话层和编排层的职责，不属于路由层。

### 5.4 不负责 Workflow 内部规则

例如：

- 哪些规则命中高风险
- 哪些证据可以豁免
- 最终风险如何融合

这些都是 Workflow 该做的事，不应该回流到路由层。

## 6. 路由层应该怎么判断

在这个项目里，我建议把路由判断理解成一个分层顺序，而不是一堆无序规则。

最稳的思路通常是：

### 6.1 第一优先级：显式路由

如果前端已经明确传了：

- `sceneHint`

那就优先尊重显式指定。

这是因为：

- 用户端或前端界面有时已经知道自己在哪个工作区
- 这类信息比自然语言推断更稳定

所以显式信号优先，是一个非常稳的设计。

### 6.2 第二优先级：强规则路由

如果请求没有显式指定场景，就看强语义信号。

例如：

- query 命中“围标”“串标”“标书审查”
- 请求中有文件上传
- 某些路径本身就是特定场景入口

这类请求，优先走规则，不要先交给模型猜。

### 6.3 第三优先级：模型分类

当规则难以明确判断时，才考虑让模型参与分类。

例如用户说：

- “帮我看看这批材料风险大不大”
- “你觉得这类文件更适合哪个流程”

这种模糊请求，规则层可能不够稳，这时可以让模型做一层轻量分类。

但这里一定要注意：

模型分类是“选路”，不是“直接出结果”。

### 6.4 最后优先级：默认兜底

如果前面都不能明确判断，就进入默认场景或通用对话。

这能保证系统不会因为路由失败而完全不可用。

## 7. 为什么路由结果一定要结构化

这一点非常值得强调。

在业务 Agent 里，路由结果不要只用一个字符串，比如：

- `scene = tender_review`

这样虽然能用，但信息太少。

更推荐输出一个结构化路由决策对象，例如：

```json
{
  "scene": "TENDER_REVIEW",
  "source": "rule",
  "reason": "命中围标/串标相关关键词",
  "confidence": 0.9,
  "requiresClarification": false
}
```

这样做有三个好处：

1. 前端能展示路由结果
2. 日志能解释系统行为
3. 编排层能据此做后续决策

对于你这个项目来说，这种结构化输出尤其重要，因为你本来就希望整个 Agent 系统具备可解释性。

## 8. 路由层和编排层是什么关系

很多同学会把路由层和编排层混在一起。

其实它们关系很近，但不是一回事。

你可以这样理解：

- 路由层负责“决定走哪条路”
- 编排层负责“真的把这条路串起来”

也就是说：

- 路由层产出 `WorkflowRouteDecision`
- 编排层根据 `WorkflowRouteDecision` 把请求分发到对应场景入口

这就是两者最清晰的关系。

## 9. 路由层在这个项目里的推荐边界

结合你当前项目整体架构，我建议教材里始终强调下面这条边界：

### 路由层只负责“场景识别 + 路由决策”

不要让它：

- 直接产出最终业务结果
- 直接驱动底层 Workflow
- 持有场景专属 Tool 调用逻辑
- 接管会话状态管理

这条边界一旦守住，后面无论是新增场景，还是引入模型分类层，架构都会稳很多。

## 10. 这一节最重要的结论

最后把这一节收束成一句最核心的话：

路由层的职责，不是解决业务问题，而是决定业务问题应该交给谁解决。

对当前项目来说，一个合格的路由层至少要做到：

- 路由逻辑集中
- 路由顺序明确
- 路由原因可解释
- 路由结果结构化
- 不越层做场景执行

一句话总结：

没有独立路由层，系统只是“碰到什么就试着处理什么”；  
有了独立路由层，系统才开始像一个真正有分工的业务 Agent。

# 02 编排层

做业务 Agent，最容易失控的地方，不是模型接入，也不是工具调用，而是编排层。

很多项目一开始只有一个总入口：

- 收到请求
- 调模型
- 返回结果

前期看起来很快，甚至很顺。

但只要场景一变复杂，这种写法很快就会出问题：

- 路由逻辑越写越多
- 场景判断和业务执行混在一起
- 通用逻辑和场景逻辑互相污染
- 后续新增场景时越来越难扩展

所以在这个项目里，我们要把“编排层”单独讲清楚。

它不是一个可有可无的中间层，而是上层通用 Agent 能不能长期稳定演进的关键。

## 1. 什么是编排层

我先给一个比较稳的定义。

在这个项目里，编排层指的是：

接住前端会话请求后，负责组织执行顺序、做场景路由、选择执行入口、收敛结果返回的那一层。

它不负责底层业务细节，也不负责规则命中本身，而是负责回答下面这些问题：

- 这次请求应该进入哪个场景
- 当前请求是否需要补材料或澄清
- 应该交给哪个场景执行入口
- 执行结果怎么统一回写和返回

如果你把整个 Agent 系统比作一个业务团队，那么编排层更像项目经理：

- 不亲自写每个模块的代码
- 不亲自执行业务规则
- 但它负责把整个流程接起来

这就是为什么编排层一定要保持边界清晰。

## 2. 当前项目里的编排主链路

结合当前项目代码来看，核心入口在 [`AgentChatService.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentChatService.java)。

当前主流程大致是：

```text
AgentController
-> AgentChatService
-> AgentSessionService / AgentMessageService 构建会话上下文
-> AgentSceneService 做场景路由与分发
-> 场景服务执行
-> AgentResponseService 组装统一响应
-> 回写会话与消息
```

这条链路的意义在于：

- Controller 不直接碰业务流程
- AgentChatService 负责统一编排
- SceneService 负责路由和分发
- 场景服务负责进入具体执行流
- ResponseService 负责统一收口

从分层意识上看，这已经比“一个大 Service 全包”要好很多了。

## 3. 当前项目的编排顺序，到底是什么

很多同学在看这类项目时，容易把“目标架构”和“当前实现”混在一起。

所以这里我专门把当前项目的编排顺序拆开讲。

### 3.1 第一层：规则路由

这一层在当前项目里是明确存在的。

在 [`AgentSceneService.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentSceneService.java) 的 `decideRoute(...)` 中，当前顺序大致是：

1. 优先检查 `sceneHint`
2. 再检查 `metadata.sceneHint`
3. 再做 query 关键词匹配
4. 再检查是否上传了文件
5. 最后 fallback 到默认对话

这就是典型的规则路由。

它的特点是：

- 快
- 稳
- 成本低
- 可解释性强

例如：

- 用户显式传了 `sceneHint=tender_review`
- 用户 query 里明确出现“围标”“串标”“标书审查”
- 请求里已经带了文件

这种情况系统完全没必要再问模型“你觉得这是什么场景”，直接走固定判断更合理。

这就是业务 Agent 与通用聊天机器人的一个重要区别：

能确定的，不要再交给模型猜。

### 3.2 第二层：模型分类

这里要非常诚实地说一句：

从当前仓库实现来看，这一层还没有真正独立落地。

也就是说，当前项目还不是一个完整的：

- 规则先判断
- 规则看不出来时再走 LLM 分类
- 分类后再进入对应场景执行

的结构。

当前实际情况更接近：

- 规则能识别的，走对应场景
- 规则识别不了的，直接 fallback 到 `DEFAULT`
- `DEFAULT` 分支进入通用对话

这和“模型分类层”不是一回事。

为什么我要专门强调这一点？

因为教材里最忌讳的一件事，就是把“目标设计”写成“当前事实”。

如果按当前代码实话实说，你可以这样描述：

当前项目已经有规则路由和固定执行流，但“规则未命中后再由模型做意图分类”的独立层还没有正式建立，当前规则无法识别的请求会先落到默认通用对话。

这个表述会更准确，也更专业。

### 3.3 第三层：固定执行流

这一层在当前项目里是存在的，而且已经比较明确。

以标书审查场景为例，当前固定链路是：

```text
AgentChatService
-> AgentSceneService
-> TenderReviewSceneService
-> TenderReviewPreparationService
-> TenderReviewWorkflow
-> AgentExecutionResult
-> AgentResponseService
```

这里面有几个非常值得肯定的点。

第一，通用层不会直接调用底层 Workflow。

第二，场景执行前会先经过 `PreparationService` 补齐数据。

第三，真正的业务执行还是收敛在 `Workflow` 里。

这就保证了每类请求都有预定义执行流，而不是让模型自由发挥整条业务链。

这一点非常重要。

因为在业务 Agent 里，模型可以负责：

- 理解意图
- 生成解释
- 整理结果

但不应该随意决定底层核心业务流程怎么跑。

否则一旦场景变重，系统会越来越不可控。

## 4. 所以，当前项目是不是“三层编排”

如果用一句比较严谨的话来总结当前项目，我建议这样写：

当前项目的编排层已经形成了“规则路由 + 场景固定执行流”的基本结构，但“规则无法识别后再由模型做分类”的中间层还没有正式独立出来，因此目前还不能算完整的三层编排体系。

这句话背后有两个价值。

第一，它准确反映了当前状态。

第二，它自然引出了后续架构演进方向。

教材不是只用来描述“已经做完的东西”，更重要的是帮助读者理解：

- 现在做到哪一步了
- 还缺什么
- 为什么下一步要那样演进

## 5. 我建议的目标编排结构

如果从长期架构看，这个项目比较理想的编排顺序，确实可以收敛成下面三层：

### 5.1 第一层：规则路由

这一层处理高确定性请求。

适合走规则的情况包括：

- 前端显式传入 `sceneHint`
- query 中有强语义关键词
- 文件类型、数量、请求参数已经足够明显
- 某些路径本身就应该强约束进入固定场景

设计原则是：

能确定的，优先走规则，不要增加模型成本和不确定性。

### 5.2 第二层：模型分类

这一层只处理规则层无法明确判断的请求。

例如用户说：

- “帮我看一下这批材料有没有风险”
- “这两份文件你帮我做个专业判断”
- “这个内容更像审查还是预警”

这类请求，规则有时很难准确识别。

这时就可以让模型做一层轻量意图分类，但要注意两个边界：

第一，模型分类只负责“判断应该进哪个场景”，不负责直接给最终业务答案。

第二，模型分类输出必须结构化，例如：

```json
{
  "scene": "TENDER_REVIEW",
  "confidence": 0.82,
  "reason": "用户提到两份文件比对与风险判断，更符合标书审查场景"
}
```

只要这一层保持轻量和结构化，它就能很好地补足规则路由的盲区。

### 5.3 第三层：固定执行流

模型一旦分类完成，真正执行时仍然进入预定义流程。

例如：

- `TENDER_REVIEW -> TenderReviewSceneService -> Preparation -> Workflow`
- `CONTRACT_PRECHECK -> ContractSceneService -> Preparation -> Workflow`
- `RISK_ALERT -> RiskAlertSceneService -> Preparation -> Workflow`

也就是说：

- 模型可以帮我们“选路”
- 不能帮我们“随便造路”

这句话非常值得记住。

## 6. 为什么不能让模型直接从入口一路自由发挥

很多人一开始做 Agent，会很容易被一种“看上去很聪明”的方案吸引：

“让模型直接从用户请求开始，自主判断、自主选工具、自主控制流程，不是更高级吗？”

短期看，好像是这样。

但业务 Agent 一旦进真实场景，这种方案通常会出现四个问题。

### 6.1 可解释性差

你很难清楚解释：

- 为什么这次走了这个场景
- 为什么没走另一个场景
- 为什么这轮执行顺序和上轮不一样

### 6.2 稳定性差

同样的请求换个表达方式，模型可能就走出完全不同的链路。

### 6.3 成本不可控

每一轮都让模型做大量自由判断，推理成本和时延都会上升。

### 6.4 不利于工程化扩展

当你后面要接：

- 合同预审
- 风险预警
- 合规问答
- 任务看板

如果入口完全自由发挥，系统会越来越难维护。

所以真正成熟的业务 Agent，往往都不是“完全自由 Agent”，而是“有限自由 + 强编排边界”的系统。

## 7. 当前项目里，编排层应该坚持哪些边界

结合你当前项目的分层约束，我建议教材里一定强调下面这几个边界。

### 7.1 Controller 不做复杂编排

[`AgentController.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/controller/AgentController.java) 只负责：

- 接收 HTTP 请求
- 做参数协议转换
- 返回统一响应

不要把场景判断、Workflow 调用、复杂业务装配放进 Controller。

### 7.2 AgentChatService 只做统一会话编排

[`AgentChatService.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentChatService.java) 的定位应该始终是：

前端会话请求的统一应用编排器。

它负责：

- 接请求
- 建上下文
- 调路由
- 做分发
- 做降级
- 回写结果

它不应该长期持有：

- 场景专属业务规则
- Tool 细节
- Workflow 内部执行逻辑

### 7.3 场景层负责进入对应固定流程

比如标书审查当前已经通过 [`TenderReviewSceneService.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/scene/tender_review/facade/TenderReviewSceneService.java) 统一收口。

这是对的。

因为通用层不需要知道标书场景内部到底怎么准备数据、怎么命中规则、怎么融合风险。

这些都应该留在场景层和 Workflow 层内部。

### 7.4 Workflow 只负责确定性执行

Workflow 的价值不是“更智能”，而是“更稳定”。

它应该负责：

- 业务执行主链路
- 规则命中
- 豁免处理
- 风险融合
- 证据组装
- 报告生成

不要让 Workflow 负责前端协议、会话管理、HTTP 语义，也不要让它反过来控制上层编排。

## 8. 这一节最重要的结论

最后，把这一节收束成一句最值得记住的话：

业务 Agent 的编排层，不是为了让模型更自由，而是为了让系统更稳定。

对当前项目来说，可以这样理解：

- 已经实现的部分是“规则路由 + 固定执行流”
- 还未独立完成的是“规则未命中后的模型分类层”
- 后续演进方向不是让模型接管全部流程，而是在规则和固定执行流之间，补一层轻量、结构化、可控的模型分类

这套思路的核心不是“炫技”，而是工程化。

只有编排边界清楚，后面的 Tool 化、Workflow 收敛、场景扩展和前端工作台协同，才会越做越稳。

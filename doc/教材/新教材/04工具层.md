# 05 工具层

在很多 Agent 项目里，“工具层”是一个特别容易被误用的概念。

有些项目把 Tool 当成一个 HTTP 接口包装器。  
有些项目把 Tool 当成最终业务引擎。  
还有些项目把所有逻辑都塞进 Tool 里，结果 Tool 变成了另一个大而全 Service。

这些写法前期可能都能跑，但很难长期稳定。

所以在这个项目里，工具层一定要讲清楚。

## 1. 什么是工具层

在这个项目里，工具层可以先理解成一句话：

给模型或编排器调用的、具有明确输入输出的执行入口。

这里有三个关键词：

- 给调用方使用
- 明确输入输出
- 执行入口

注意，Tool 是入口，不是整个业务系统本身。

如果把 Workflow 比作真正干活的工厂，那么 Tool 更像一个标准化工单窗口：

- 外部把请求递进来
- Tool 做参数整理和合法性检查
- 再把请求交给底层业务引擎
- 最后返回结构化结果

这就是 Tool 的本质定位。

## 2. 为什么业务 Agent 需要工具层

很多同学第一次做 Agent，会有一个很自然的想法：

“既然最终都是调 Workflow，那为什么不让上层直接调 Workflow？”

这个问题问得很好。

理论上当然可以直接调。

但一旦你希望这个系统具备：

- Tool Calling
- Orchestrator 编排
- 多场景复用
- 标准化结构化输入输出

那 Tool 层就很有价值。

因为它能把“外部调用方式”和“内部业务实现”隔开。

## 3. Tool 层到底解决什么问题

### 3.1 统一调用协议

不同场景底层执行方式可能不同。

例如：

- 标书审查需要多份文件
- 合同预审可能需要条款文本
- 风险预警可能需要结构化指标

如果没有 Tool 层，上层编排每次都要直接了解底层接口细节。

有了 Tool 层之后，系统可以统一成：

- `ToolRequest`
- `ToolResult`

这样上层只管“怎么调用”，不用反复理解底层细节。

### 3.2 隔离参数整理逻辑

很多业务场景在真正执行前，都要先做参数补齐、合法性校验、格式整理。

这些逻辑既不适合放在 Controller，也不适合放在通用编排层。

放在 Tool 层反而最合适。

### 3.3 为 Orchestrator 提供标准执行点

后面如果你要做 Tool Calling 或场景 Orchestrator，那么 Tool 就是天然的注册单位。

例如：

- `reviewTenderTool`
- `precheckContractTool`
- `riskAlertTool`

这样 Orchestrator 可以清楚知道：

- 有哪些可调用能力
- 每个能力的输入输出是什么

这就是 Tool 层的重要价值。

## 4. 当前项目里，Tool 层应该怎么理解

结合你这个项目的整体架构约束，Tool 层的定位应该非常明确：

Tool 是“可调用执行入口”，不是最终业务引擎。

例如标书审查场景里，更理想的链路应当是：

```text
AgentChatService
-> TenderReviewToolOrchestrator
-> ReviewTenderTool
-> TenderReviewWorkflow
```

这里：

- Orchestrator 负责组织 Tool 调用
- Tool 负责承接一次标准调用
- Workflow 负责真正业务执行

这三个层次不要混。

## 5. Tool 层应该负责什么

在这个项目里，我建议 Tool 层只承担下面四类职责。

### 5.1 参数校验

Tool 的第一职责是检查输入是否合法。

例如：

- 文件列表是否为空
- 文档数量是否满足最低要求
- query 是否存在
- 某些关键字段是否缺失

这些校验放在 Tool 层很合理，因为它本来就是执行入口。

### 5.2 请求整理

Tool 可以负责把外部调用参数整理成底层更容易消费的请求结构。

例如：

- 补齐默认值
- 转换字段名
- 把文件信息整理为场景数据

这一步不属于通用编排层，也不属于 Workflow 核心业务，更适合放在 Tool 层。

### 5.3 调用底层 Workflow

Tool 负责把整理好的请求交给底层 Workflow 或底层场景执行引擎。

注意这里是“调用”，不是“重写 Workflow 逻辑”。

### 5.4 返回结构化结果

Tool 的输出应该尽量是结构化结果，例如：

- `success`
- `summary`
- `riskLevel`
- `score`
- `report`
- `evidenceList`

这样上层 LLM 或编排器才能更稳定地使用。

## 6. Tool 层不应该负责什么

### 6.1 不负责 HTTP 接入

Tool 不是 Controller。

它不应该关心：

- 请求是从 HTTP 来的
- 是 multipart 还是 JSON
- 返回给前端的包装结构是什么

这些都属于 Controller 和上层编排。

### 6.2 不负责通用路由

Tool 不应该判断：

- 当前是不是标书审查
- 当前是不是合同预审
- 当前应该走哪个场景

这是路由层和编排层的职责。

### 6.3 不负责前端响应组装

Tool 输出应该是结构化执行结果，而不是直接面向前端的最终展示对象。

如果 Tool 直接开始拼前端返回文案，它就会越层。

### 6.4 不负责 Workflow 内部业务细节

Tool 不应该在自己内部重新实现：

- 规则命中
- 风险融合
- 报告生成

否则 Workflow 就会被架空，Tool 会越来越胖。

## 7. Tool 和 Workflow 到底怎么区分

这是很多人最容易混淆的地方。

我建议你用一句很实用的话记住：

Tool 是“怎么接进来”，Workflow 是“进去之后怎么干”。

举个标书审查的例子：

### Tool 关心的是

- 这次调用参数是什么
- 文件够不够
- 请求对象怎么整理
- 返回哪个结构化结果对象

### Workflow 关心的是

- 文档怎么解析
- 规则怎么命中
- 哪些命中可以豁免
- 风险怎么融合
- 证据怎么组装
- 报告怎么生成

两者都重要，但关注点完全不同。

## 8. 为什么 Tool 层要尽量结构化

如果 Tool 的输入输出不结构化，后面会出现很多问题：

- 上层调用不稳定
- LLM 难以可靠调用
- 场景之间难以统一
- 后续不好测试

所以 Tool 层最好天然具备明确的：

- `ToolRequest`
- `ToolResult`

例如：

```json
{
  "query": "帮我看看这两份标书是否有围标风险",
  "fileIds": ["f1", "f2"]
}
```

对应返回：

```json
{
  "success": true,
  "riskLevel": "HIGH",
  "summary": "检测到明显围标风险",
  "score": 86
}
```

结构化输入输出，是 Tool 层长期可维护的基础。

## 9. Tool 层和 Orchestrator 的关系

Tool 层和 Orchestrator 关系很近，但不是同一层。

你可以这样理解：

- Orchestrator 负责“什么时候调哪个 Tool”
- Tool 负责“这次调用如何标准化执行”

也就是说：

- Orchestrator 是调度者
- Tool 是执行入口

如果一个场景比较简单，暂时没有 Orchestrator，也可以先由场景服务直接调用 Tool。

但只要场景开始进入 Tool Calling 模式，Tool 层就会变得非常关键。

## 10. 在当前项目里，Tool 层最重要的边界

结合你项目的整体约束，我建议教材里始终强调下面这句话：

Tool 是场景能力的标准化调用入口，不是业务逻辑的大仓库。

只要这条边界守住，Tool 层就会很稳。

一旦守不住，常见问题就会出现：

- Tool 越来越胖
- Workflow 被架空
- AgentChatService 又开始直接碰业务细节
- Orchestrator 变得没有存在价值

## 11. 这一节最重要的结论

最后把这一节收束成一句最核心的话：

业务 Agent 里的 Tool 层，不是为了多加一层抽象，而是为了给上层编排提供稳定、结构化、可调用的场景能力入口。

对当前项目来说，一个合格的 Tool 层至少应该做到：

- 输入输出明确
- 参数校验清晰
- 请求整理收口
- 调用底层 Workflow
- 返回结构化结果
- 不越层处理路由、HTTP 和前端响应

一句话总结：

没有 Tool 层，系统只有“场景代码”；  
有了 Tool 层，场景能力才真正变成“可编排、可调用、可复用”的能力单元。

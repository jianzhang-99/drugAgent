# 06 存储层

很多同学做 Agent 项目时，一开始会把注意力都放在：

- 模型
- Prompt
- Tool
- Workflow

然后默认觉得“存储层不就是数据库吗，好像没什么可讲的”。

但在业务 Agent 里，存储层其实非常关键。

因为只要系统开始真正承担业务功能，就一定会遇到这些问题：

- 会话和消息怎么存
- 文档和解析结果怎么存
- 检索知识块怎么存
- 任务状态怎么存
- 证据和报告怎么存

如果存储层没有单独设计，系统很快就会出现：

- 数据真假源混乱
- 不同层都在各自存一份状态
- 后续很难排查问题
- 业务结果难以复现

所以在这个项目里，存储层必须单独看。

## 1. 什么是存储层

在这个项目里，存储层可以先理解成一句话：

负责持久化系统运行过程中产生的业务事实、聚合状态和检索数据的基础层。

这里最关键的词是：

- 持久化
- 业务事实
- 聚合状态
- 检索数据

也就是说，存储层并不只是“存表”，而是负责回答：

- 哪些数据要长期保存
- 哪些数据是系统真相源
- 不同数据应该归属到哪一层存储

这就是存储层真正的价值。

## 2. 为什么业务 Agent 一定要有存储层意识

如果一个系统只是一次请求一次回答，那存储层确实不复杂。

但你这个项目明显不是这种轻量形态。

你后面会持续遇到这些需求：

- 用户希望保留会话历史
- 系统要恢复当前任务状态
- 上传的材料要反复使用
- 检索知识库要长期积累
- 规则命中结果和报告要能追溯

这些需求共同说明一件事：

系统不是一次性计算器，而是持续运行的业务系统。

既然如此，存储层就不能只被当成“技术细节”，而应该被当成架构层的一部分。

## 3. 在这个项目里，存储层主要存什么

结合你当前项目来看，存储层至少包含下面几类数据。

### 3.1 会话数据

例如：

- `chat_session`
- `chat_message`

这类数据负责记录：

- 会话聚合信息
- 原始消息事实
- 摘要、标题、最近场景等状态

它们支撑的是会话层。

### 3.2 场景业务数据

例如：

- 标书案例
- 任务卡片
- 审查报告
- 场景执行产物

这类数据支撑的是具体业务场景本身。

### 3.3 检索数据

例如：

- 知识 chunk
- 向量
- metadata
- 检索索引

这类数据支撑的是检索层。

### 3.4 系统运行辅助数据

例如：

- 日志追踪信息
- 指标统计
- 评测结果
- 运行轨迹

这类数据支撑的是监控评测层和系统治理能力。

## 4. 为什么“真相源”这个概念非常重要

这是存储层最值得讲清楚的一点。

一个业务系统最怕的，不是数据少，而是“同一类数据有多份真相源”。

比如：

- 会话状态一份存在 `chat_session`
- 另一份又散落在 message metadata
- 检索 chunk 一份存在向量库
- 另一份又存在本地索引文件

如果这些数据都被当成“主真相源”，后续很容易乱。

所以存储层设计时，一定要问清楚一个问题：

**这类数据的主真相源到底是哪一个？**

这个问题如果不先回答，后面会越来越难收敛。

## 5. 会话数据应该怎么存

在你这个项目里，会话层已经有比较清晰的存储结构了：

- `chat_session`
- `chat_message`

这个方向是对的。

因为：

- `Session` 适合存聚合状态
- `Message` 适合存原始事实明细

这就是一个典型的聚合根设计。

我建议你始终把这条边界记住：

- `chat_message` 存“发生过什么”
- `chat_session` 存“当前会话聚合状态”

这样系统才不会把所有状态都堆到消息表里。

## 6. 检索数据应该怎么存

对于简易 RAG 来说，检索数据通常至少包括：

- chunk 文本
- chunk metadata
- chunk embedding

理想情况下，这类数据应尽量围绕一条统一主链路存储。

也就是说，你最好尽量避免这种状态：

- 向量库存了一份
- 本地索引又存了一份
- 查询时再绕开其中一个

从存储层角度看，这会形成双真相源。

更稳的做法是：

- 明确向量库是不是检索主真相源
- 明确本地索引是否只是辅助结构

这条边界很重要。

## 7. 存储层不应该承担什么职责

### 7.1 不负责业务编排

存储层的任务是存数据，不是组织业务链路。

不要因为某个 mapper 很方便，就把业务流程塞进数据层。

### 7.2 不负责前端协议

存储层也不应该关心：

- 前端返回长什么样
- 哪些字段要展示

这是响应层的职责。

### 7.3 不负责业务判断

存储层可以保存规则命中结果，但不应该在自己内部做“规则命中”。

这仍然应该属于 Workflow 或业务服务层。

## 8. 为什么业务 Agent 的存储层不能只看数据库表

这个观点也很重要。

很多人一提存储层，脑子里就只剩“表设计”。

但在 Agent 项目里，存储层其实至少涉及三类存储形态：

- 关系型数据
- 文档/对象型数据
- 向量型数据

例如：

- 会话、任务、案例适合关系型结构
- 报告对象有时更偏文档型
- 检索知识块和向量属于向量/索引型

所以存储层不是一个单一数据库概念，而是整个系统的持久化底座。

## 9. 当前项目里，存储层最关键的边界

结合你当前项目整体架构，我建议教材里始终强调一句话：

存储层负责保存系统真相，不负责替代业务层做判断。

只要这句话守住，很多架构问题就会简单很多。

例如：

- 会话层知道该把状态写回哪里
- 检索层知道该从哪里查知识
- Workflow 知道哪些结果该持久化
- 上层不会把临时变量乱写进长期存储

## 10. 这一节最重要的结论

最后把这一节收束成一句最核心的话：

在业务 Agent 里，存储层最重要的价值，不只是“把数据存下来”，而是明确系统中每一类数据的长期归属和真相源。

对当前项目来说，一个合格的存储层至少应该做到：

- 明确会话数据的聚合结构
- 明确业务结果的持久化归属
- 明确检索数据的主真相源
- 避免多处重复保存同类状态
- 不越层承担编排和业务判断

一句话总结：

没有清晰存储层，系统只是“把东西到处写一份”；  
有了清晰存储层，系统才真正拥有“长期可维护的数据底座”。

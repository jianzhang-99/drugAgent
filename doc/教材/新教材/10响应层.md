# 07 响应层

很多同学做 Agent 项目时，往往把响应层理解得太简单。

好像只要最后 `return` 一段字符串，事情就结束了。

在普通聊天应用里，这种理解勉强还能工作。

但在业务 Agent 里，这通常是不够的。

因为业务 Agent 的返回结果，不只是“给用户看一句话”，而是要把整条执行链的结果，以稳定、统一、可消费的方式交给前端和上层系统。

这就是为什么响应层也值得单独讲。

## 1. 什么是响应层

在这个项目里，响应层可以先理解成一句话：

把底层执行结果，转换成前端和调用方可以稳定消费的统一响应结构。

这里的关键词是：

- 转换
- 统一
- 稳定消费

也就是说，响应层不是业务执行层，它更像一个总装车间。

底层可能已经有很多结果了：

- 路由结果
- 执行结果
- 风险等级
- 证据列表
- 报告对象
- 引用信息

响应层的任务，就是把这些内容收拢成一个统一的返回对象。

## 2. 为什么业务 Agent 一定要有统一响应层

很多同学一开始会说：

“那我让每个场景自己返回不就好了？”

这在 Demo 阶段确实能跑。

但场景一多，很快就会出问题。

### 2.1 前端很难接

如果每个场景返回格式都不一样，前端就要：

- 针对每个场景写不同解析逻辑
- 到处做判空兼容
- 很难做统一工作台和会话页

这会大大增加前后端协作成本。

### 2.2 通用能力很难沉淀

例如这些字段其实很多场景都想要：

- `traceId`
- `scene`
- `routeReason`
- `routeSource`
- `confidence`
- `answer`
- `summary`
- `riskLevel`
- `score`

如果没有响应层统一装配，这些字段很容易每个场景自己拼一套，长期会非常乱。

### 2.3 可解释信息容易丢失

如果最后只是返回一句自然语言，很多关键上下文会丢掉，例如：

- 为什么进入这个场景
- 系统判断置信度是多少
- 有没有证据列表
- 当前是否需要人工复核

这些信息对业务 Agent 很重要，不应该在最后一步被抹平。

## 4. 响应层到底负责什么

在这个项目里，我建议始终把响应层的职责控制在下面几件事之内。

### 4.1 统一返回结构

响应层最重要的事情，就是保证所有对话场景最终都回到统一返回对象。

这样前端和调用方就有稳定预期。

### 4.2 聚合不同层的结果

业务 Agent 的结果通常不是某一层单独产生的，而是多个层次共同组成的。

例如：

- 路由层提供 `scene / reason / source / confidence`
- 执行层提供 `answer / summary / riskLevel / score`
- 检索层提供 `citations`
- Workflow 提供 `report / evidenceList / steps`

响应层的价值就是把这些结果聚合到一起。

### 4.3 做统一降级表达

当系统遇到异常、证据不足、需要澄清时，响应层应该能统一表达这些状态。

例如：

- `requiresClarification`
- `clarificationQuestion`
- `riskLevel=UNKNOWN`

这样前端不用自己去猜异常状态。

### 4.4 面向前端收口

响应层输出应该偏“前端可消费”，而不是底层中间结构直接外露。

例如：

- 前端要显示什么
- 哪些字段适合直接展示
- 哪些结构需要统一包装

这些都应该在响应层收口。

## 5. 响应层不应该负责什么

### 5.1 不负责业务执行

响应层不能因为自己拿到了 `AgentExecutionResult`，就顺手开始：

- 重新判断风险
- 改写业务规则
- 决定 Workflow 怎么跑

那就越层了。

### 5.2 不负责场景路由

响应层可以展示路由结果，但不负责产生路由结果。

它只消费路由层产出的结构化信息。

### 5.3 不负责底层会话存储

响应层不应该直接管理：

- 消息保存
- 会话标题回写
- summary 更新

这些是会话层和编排层的职责。

### 5.4 不负责模型提示词设计

响应层的任务是收口结果，而不是决定模型该怎么推理。

这也是边界的一部分。

## 6. 为什么统一响应结构这么重要

你这个项目后面很可能会有：

- 聊天页
- 会话列表
- 工作台
- 审查结果卡片
- 任务中心

如果没有统一响应结构，这些地方都会越来越难做。

而一旦统一响应结构建立起来，你会发现很多能力都自然变简单了：

- 前端能统一展示 answer
- 前端能统一显示 riskLevel 和 score
- 前端能统一展示 evidenceList 和 report
- 会话层能统一记录摘要
- 日志层能统一落 trace 信息

所以从工程化角度看，统一响应层的收益非常大。

## 7. 在业务 Agent 里，为什么不能只返回一段 answer

这个问题其实很值得单独讲一下。

因为很多人会下意识觉得：

“用户最后不就是看一句回答吗？”

表面上是这样，但业务 Agent 里，光有 `answer` 通常不够。

至少你这个项目里，很多时候还需要：

- `scene`
- `routeReason`
- `routeSource`
- `confidence`
- `summary`
- `riskLevel`
- `score`
- `report`
- `evidenceList`
- `steps`

这是因为业务 Agent 输出的不只是“自然语言”，而是“结果对象”。

这和普通聊天应用有本质区别。

## 8. 响应层和会话层的关系

响应层和会话层关系很近，但职责不同。

你可以这样理解：

- 响应层负责“这次返回什么”
- 会话层负责“这次结果怎么写回会话”

例如：

- 响应层组装出 `answer / summary / report`
- 编排层决定哪些字段要回写 session/message

这条边界如果不清楚，常见问题就会出现：

- 响应层开始直接改会话
- 会话层开始反向拼前端对象

这都会让结构变乱。

## 9. 当前项目里，一个好的响应对象应该长什么样

结合你当前项目方向，一个比较好的统一响应对象，至少应尽量包含：

- `traceId`
- `sessionId`
- `scene`
- `routeReason`
- `routeSource`
- `confidence`
- `summary`
- `answer`
- `riskLevel`
- `score`
- `report`
- `evidenceList`
- `evidenceGroups`
- `steps`
- `requiresClarification`
- `clarificationQuestion`

这类结构的好处是：

- 对前端友好
- 对日志友好
- 对会话回写友好
- 对多场景扩展友好

当然，不是每次响应都必须把所有字段都填满。

关键是统一结构要在，具体字段可以按场景填充。

## 10. 响应层最重要的工程价值

如果从工程角度总结，响应层最大的价值不是“多加一层”，而是：

把系统内部复杂、分散、不一致的结果，收拢成一个统一对外协议。

这会让整个项目后续更容易：

- 接前端
- 接工作台
- 做测试
- 做日志追踪
- 做多场景扩展

所以别小看响应层。

它虽然不直接执行业务，但它决定了系统最终“对外说话”的方式。

## 11. 这一节最重要的结论

最后把这一节收束成一句最核心的话：

在业务 Agent 里，响应层不是简单的 `return`，而是系统对外输出协议的统一收口层。

对当前项目来说，一个合格的响应层至少应该做到：

- 统一返回结构
- 聚合路由与执行结果
- 保留可解释信息
- 支持异常与澄清场景
- 面向前端稳定输出
- 不越层做业务执行和会话管理

一句话总结：

没有响应层，系统只是“把结果吐出来”；  
有了响应层，系统才真正开始“稳定地对外输出结果”。

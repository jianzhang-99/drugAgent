# 07 监控评测层

很多 Agent 项目做到一定阶段，都会遇到一个非常现实的问题：

系统好像能跑，但你并不知道它到底跑得怎么样。

例如：

- 路由到底准不准
- 检索命中质量怎么样
- 模型回答稳定不稳定
- 哪个场景失败最多
- 哪个环节耗时最高

如果这些问题没有一套专门的监控和评测机制，系统就会进入一种典型状态：

- 能跑，但不可治理
- 出问题，只能靠猜
- 优化方向，全靠感觉

所以在业务 Agent 里，监控评测层一定不能缺。

## 1. 什么是监控评测层

在这个项目里，监控评测层可以先理解成一句话：

负责观察系统运行效果，并用指标、日志、样本和测试来判断系统是否在稳定地产生预期结果。

这里有两个核心方向：

- 监控：看系统现在运行得怎么样
- 评测：看系统整体能力到底好不好

这两个方向很接近，但不是一回事。

## 2. 为什么业务 Agent 一定要有监控评测层

因为业务 Agent 不是纯静态程序。

它里面至少包含这些不稳定因素：

- 模型输出存在波动
- 检索结果会随着知识库变化而变化
- 路由策略会不断调整
- Prompt 会迭代
- 场景规则会变化

如果没有监控评测层，你根本很难知道：

- 现在变好了还是变差了
- 是不是某个小改动引入了回归
- 用户为什么觉得系统不稳定

这就是为什么监控评测层非常重要。

## 3. 监控和评测有什么区别

我建议你先把这两个概念分清楚。

### 3.1 监控更关注运行中发生了什么

例如：

- 今天接口错误率是多少
- 哪个场景调用最多
- 平均耗时多长
- 哪个模型 provider 失败率高
- 哪个环节最慢

监控更偏线上运行观察。

### 3.2 评测更关注系统能力本身好不好

例如：

- 路由样本命中率
- 检索 top-k 命中率
- 回答质量是否符合预期
- 标书审查样本输出是否回归

评测更偏离线质量判断。

一个成熟的业务 Agent，通常两者都要有。

## 4. 当前项目里，为什么监控评测尤其重要

你这个项目的目标不是做开放式聊天，而是做：

- 标书审查
- 合同预审
- 风险预警

这些场景有一个共同特点：

系统输出会影响业务判断。

这就意味着，你不能只满足于：

- “大致能答”
- “看起来差不多”

你更需要知道：

- 路由是不是经常走错
- 检索是不是经常没命中
- Workflow 某个步骤是不是经常失败
- 某类样本是不是最近退化了

这就是监控评测层在这个项目里特别重要的原因。

## 5. 监控层应该看什么

在业务 Agent 里，我建议监控层至少关注四类东西。

### 5.1 链路监控

这类监控回答的问题是：

这次请求完整链路跑得通不通？

典型信息包括：

- `traceId`
- `sessionId`
- `scene`
- `routeSource`
- `routeReason`
- 关键步骤耗时

这类信息能帮助你快速定位问题在哪一层发生。

### 5.2 错误监控

这类监控关注：

- 哪个接口失败了
- 哪个 provider 调用异常
- 哪个 Workflow 执行失败
- 哪个场景降级最多

如果没有错误监控，很多问题只能靠用户反馈才知道。

### 5.3 性能监控

这类监控关注：

- 模型调用耗时
- 检索耗时
- Workflow 执行耗时
- 整体响应时间

因为业务 Agent 不只是“能不能答”，还要考虑“多快答出来”。

### 5.4 业务监控

这类监控最有业务价值。

例如：

- 每个场景的请求量
- 每个场景的成功率
- 需要人工复核的比例
- 澄清触发率
- 风险等级分布

这些指标往往比纯技术指标更能说明系统是否真的在创造价值。

## 6. 评测层应该评什么

这是很多项目最容易忽视的一点。

业务 Agent 的评测，不应该只看“模型感觉好不好”，而应该拆成分层评测。

### 6.1 路由评测

评测问题例如：

- 给定一批历史样本，场景是否能正确命中
- 规则层和模型分类层的命中率分别是多少
- 哪些样本最容易误路由

### 6.2 检索评测

评测问题例如：

- top-k 是否能召回目标证据
- metadata 过滤是否过松或过严
- 某些文档切块策略是否影响命中率

### 6.3 模型输出评测

评测问题例如：

- 回答是否基于证据
- 总结是否准确
- 澄清问题是否合理
- 标题生成是否稳定

### 6.4 Workflow 结果评测

评测问题例如：

- 对一组标准样本，规则命中是否符合预期
- 风险等级是否回归
- 报告结构是否稳定

对于你这个项目来说，这一层尤其重要。

因为很多核心价值不是聊天结果，而是业务执行结果。

## 7. 为什么监控评测层不能只靠人工体验

很多团队早期会默认一种做法：

“我自己问几轮，感觉差不多就行。”

这在非常早期可以接受，但后面一定不够。

原因很简单：

- 人工体验不可重复
- 不同人评价标准不同
- 很难覆盖边界样本
- 很难发现回归问题

所以系统只靠人工体验，是没办法长期稳定迭代的。

你一定要逐步建立：

- 指标
- 样本
- 基线
- 回归验证

这才是工程化。

## 8. 在这个项目里，最值得优先做的监控评测能力

如果按最小可用版本推进，我建议优先做下面这些。

### 8.1 链路日志

至少保证每次请求都能看到：

- `traceId`
- `sessionId`
- `scene`
- 路由来源
- 关键步骤耗时

这是最基础的运行观察能力。

### 8.2 场景级成功率统计

至少能回答：

- 标书审查成功率多少
- 默认对话成功率多少
- 哪类场景最容易失败

### 8.3 样本回归集

为关键场景准备一批固定样本，例如：

- 标书审查高危样本
- 合规低风险样本
- 检索命中样本

每次改动后都能再跑一遍，这样你才能知道系统是不是退化了。

### 8.4 检索命中观察

至少能看到：

- top-k 命中了什么
- 为什么没命中
- 哪些 query 经常召回不准

这对你当前正在收敛检索层尤其重要。

## 9. 监控评测层不应该做什么

### 9.1 不应该替代业务层修逻辑

监控评测层负责“发现问题”，不是自己在里面偷偷改业务逻辑。

### 9.2 不应该只做纯技术指标

如果只监控 CPU、内存、接口耗时，而没有业务质量指标，那对 Agent 项目是不够的。

### 9.3 不应该脱离真实样本

如果评测只用抽象问题，而不用真实业务样本，结论通常不够可靠。

## 10. 当前项目里，监控评测层最重要的边界

结合你当前项目整体架构，我建议教材里始终强调一句话：

监控评测层的职责，不是让系统运行，而是让团队知道系统运行得好不好。

这条边界一旦清楚，很多事情就会简单很多：

- 监控归监控
- 业务归业务
- 评测归评测

三者不会混成一团。

## 11. 这一节最重要的结论

最后把这一节收束成一句最核心的话：

在业务 Agent 里，监控评测层的价值，不是为了“多做点日志”，而是让系统从“能跑”走向“可观察、可验证、可持续优化”。

对当前项目来说，一个合格的监控评测层至少应该做到：

- 观察完整执行链路
- 统计关键错误和耗时
- 监控场景级业务指标
- 建立关键样本回归集
- 对路由、检索、模型、Workflow 做分层评测

一句话总结：

没有监控评测层，系统只是“勉强跑着”；  
有了监控评测层，系统才真正开始“可治理地进化”。

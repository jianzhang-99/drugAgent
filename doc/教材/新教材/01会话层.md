# 01 会话层

在很多 Agent 项目里，大家一开始设计会话系统，通常会先想到两张表：

- `chat_session`
- `chat_message`

这当然是对的，而且也是一个很稳的起点。

但如果我们做的不是一个“随便聊聊天”的机器人，而是一个有明确场景路由、有工作流、有结构化输出、有证据链的业务 Agent，那么只把会话理解为“消息列表”，通常是不够的。

原因很简单：

- 消息记录的是“发生过什么”
- 系统下一步真正需要知道的，往往是“现在进行到哪一步”

这两件事不是一回事。

在这个医药监管 Agent 项目里，会话层就不能只承担“聊天记录存储”的职责，它还需要承担一部分“会话聚合与编排状态承载”的职责。

## 1. 本项目里的会话层，不只是消息存储

先结合当前项目代码来看。

在 [`ChatSession.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/common/entity/ChatSession.java) 里，会话对象当前已经包含这些典型字段：

- `title`
- `summary`
- `lastScene`
- `messageCount`
- `lastMessageAt`

这说明这里的 `chat_session` 已经不是一个单纯的“会话目录表”，而是在承担“会话聚合根”的职责。

也就是说，它并不只是告诉我们“有这么一个会话”，还在告诉我们：

- 这个会话最近聊的主题是什么
- 最近命中了哪个场景
- 当前会话已经积累了多少消息
- 最近一次活跃是什么时候

再往 [`AgentChatService.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentChatService.java) 看，你会发现每轮对话结束后，系统还会继续更新这些聚合信息：

- 保存用户消息
- 保存助手消息
- `touchSession(...)`
- `increaseMessageCount(...)`
- `updateSessionSummary(...)`
- `updateSessionTitleIfNeeded(...)`

这一步很关键。

它说明当前项目中的 `AgentChatService` 并不是只把请求转给模型，然后把回答吐给前端，而是在做一次完整的“会话编排闭环”：

1. 获取或创建会话
2. 读取最近消息和摘要
3. 构建上下文
4. 路由并分发场景
5. 保存本轮消息
6. 回写会话聚合状态

所以，从架构上讲，这个项目的会话层已经具备了继续承接结构化状态的基础。

## 2. 为什么不能只靠历史消息判断当前状态

很多同学第一次做 Agent 时，会有一个很自然的想法：

“既然历史消息都在 `chat_message` 里，那下一轮重新读出来，不就知道上下文了吗？”

这句话只说对了一半。

因为历史消息当然很重要，但它更适合存“事实”，不适合直接承担“系统状态”。

这里有三个原因。

### 2.1 消息是自然语言，状态应该尽量结构化

例如用户可能说：

- “先帮我看看这份，另一份我等会再传”
- “我先传一个标书，你先看着，第二份稍后补”
- “先别开始，等我把另一家投标文件补齐”

这些表达的语义其实接近，系统都应该理解成：

- 当前会话与标书审查有关
- 当前材料未补齐
- 系统应该等待继续上传文件

如果每一轮都重新从自然语言里推断这个状态，模型虽然能理解，但结果未必稳定，而且会不断重复消耗推理成本。

### 2.2 消息是事实流，不是控制信号

`chat_message` 最适合做的事情，是把用户说过的话、系统返回过的话完整记录下来。

但对编排层来说，下一步往往更关心的是这类问题：

- 当前是不是在等用户补文件
- 当前是不是在等用户回答澄清问题
- 当前是不是已经命中了某个场景
- 当前有没有挂起任务

这些不是“事实文本”，而是“控制信号”。

控制信号如果不结构化，编排层就会不断依赖模型猜状态，导致链路不稳定。

### 2.3 消息越多，状态判断成本越高

在短对话里，读几条历史消息问题不大。

但一旦进入业务场景，多轮交互很快就会出现：

- 用户追问
- 文件补交
- 澄清来回
- 阶段性中断
- 重新进入执行

这时如果每轮都依赖历史消息回放来判断“系统现在卡在哪一步”，复杂度会越来越高。

所以，`chat_message` 必须保留，因为它是真实事实明细；但业务 Agent 通常还需要一个额外的结构化状态槽位，来记录“当前会话运行到哪一步”。

## 3. 为什么建议增加 `session_state`

在这个项目里，我建议在会话层增加 `session_state`。

但这里要注意，增加它的目的不是为了“多存点东西”，而是为了让会话编排更稳定。

你可以把它理解为：

`session_state` 是会话编排层的结构化状态快照。

它解决的问题不是“记住用户说过什么”，而是“让系统知道下一步该做什么”。

这和 `summary` 不是同一件事。

## 4. `summary` 和 `session_state` 的区别

这个区别非常重要。

### 4.1 `summary` 是语义压缩记忆

`summary` 的核心作用是：

- 压缩长对话
- 帮模型快速理解前文
- 降低上下文窗口压力

它本质上是给模型看的。

例如：

“用户当前正在进行两份医院信息化项目投标文件的围标风险审查，已上传一份投标文件，另一份待补充，前面已经确认需要重点关注技术方案雷同和商务条款配合风险。”

这是一段很典型的 `summary`。

它有语义，但不一定适合程序直接拿来做判断。

### 4.2 `session_state` 是结构化控制状态

`session_state` 更偏向给系统编排层看。

例如：

```json
{
  "stage": "WAITING_UPLOAD",
  "pendingScene": "TENDER_REVIEW",
  "pendingAction": "UPLOAD_FILES",
  "slots": {
    "requiredFileCount": 2,
    "uploadedFileCount": 1
  }
}
```

这个结构不是为了让模型读着更顺，而是为了让系统明确知道：

- 当前还没正式执行
- 当前挂起的是标书审查场景
- 下一步动作是等用户继续上传文件
- 还差一份文件

一句话总结：

- `summary` 解决“模型怎么理解前文”
- `session_state` 解决“系统怎么稳定控制下一步”

前者偏理解，后者偏控制。

## 5. 在本项目里，什么适合放进 `session_state`

如果要给这个项目设计 `session_state`，我建议一定要克制。

它应该只存三类信息：

- 跨轮次有效
- 结构化可机读
- 对通用会话编排有直接价值

比较适合放进去的内容包括：

- 当前阶段 `stage`
- 当前挂起场景 `pendingScene`
- 当前待执行动作 `pendingAction`
- 缺失槽位 `slots`
- 最近一次澄清类型 `clarificationType`

例如在标书审查场景里，用户说：

“帮我看看这两份标书是否有围标风险。”

如果系统已经识别出目标场景是 `TENDER_REVIEW`，但用户这时只上传了一份文件，那么系统就可以把会话状态写成：

```json
{
  "stage": "WAITING_UPLOAD",
  "pendingScene": "TENDER_REVIEW",
  "pendingAction": "UPLOAD_FILES",
  "slots": {
    "requiredFileCount": 2,
    "uploadedFileCount": 1
  }
}
```

这样做的价值非常直接。

下一轮用户回来时，系统不需要重新靠自然语言猜测：

- 他是不是还在做标书审查
- 是不是还差文件
- 现在该继续追问还是该正式执行

系统只需要读取 `session_state`，就能知道当前会话处于什么状态。

## 6. 什么不应该放进 `session_state`

这里是最容易失控的地方。

很多项目一旦有了 JSON 状态字段，就会开始不断往里面塞东西，最后把它塞成一个“万能缓存桶”。这是非常危险的。

在这个项目里，以下内容不建议放入 `session_state`：

- 标书审查规则命中明细
- 风险评分计算过程
- 证据链全文
- Tool 完整调用参数
- Workflow 中间结果
- 最近消息窗口内容

这些内容为什么不建议放？

因为它们不属于“会话编排状态”，而属于下面这些层次：

- `chat_message`：原始事实明细
- `summary`：压缩语义记忆
- Tool / Workflow Result：业务执行结果

如果把这些内容都塞进 `session_state`，会带来三个问题：

- 会话层职责膨胀
- 通用层被场景逻辑污染
- 状态结构越来越难维护

所以一定要记住一个边界：

`session_state` 只存“下一步编排要用的信息”，不存“业务执行过程的全部细节”。

## 7. 结合当前项目分层，谁来维护 `session_state`

按照本项目的分层约束，`session_state` 的职责边界应该这样划分。

### 7.1 `ChatSession`

`ChatSession` 负责承载持久化字段。

如果要落库，最自然的做法就是在 `chat_session` 表中增加 `session_state` 字段，并在 [`ChatSession.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/common/entity/ChatSession.java) 中增加对应属性。

### 7.2 `AgentSessionService`

[`AgentSessionService.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentSessionService.java) 应该负责：

- 读取 `session_state`
- 更新 `session_state`
- 封装会话级状态变更方法

因为 `session_state` 本质上属于“会话聚合管理”，不属于消息服务，也不属于 Workflow。

### 7.3 `AgentChatService`

[`AgentChatService.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentChatService.java) 作为统一应用编排器，可以在通用层消费和驱动状态变化，例如：

- 识别到当前缺文件时，把会话状态改成 `WAITING_UPLOAD`
- 需要用户补充信息时，把会话状态改成 `WAITING_CLARIFICATION`
- 正式执行完成后，把状态切回 `IDLE`

这类逻辑是对所有场景都可能成立的“通用编排规则”，可以放在会话编排层。

### 7.4 场景层 / Workflow

场景层可以产出“建议状态变化”，但不建议直接侵入会话层去写 `session_state`。

尤其不要让 Workflow 直接操作会话状态。

原因很简单：

- Workflow 是确定性业务执行引擎
- `session_state` 是会话编排状态

如果让 Workflow 反向控制会话层，分层边界会很快混乱。

这里一定要守住：

- Workflow 负责执行
- AgentChatService 负责编排
- AgentSessionService 负责会话聚合状态维护

## 8. 推荐的最小 `session_state` 设计

在项目早期，不建议一上来就设计很复杂的状态结构。

一个最小可用版本通常已经足够：

```json
{
  "stage": "IDLE",
  "pendingScene": null,
  "pendingAction": null,
  "slots": {}
}
```

当会话进入挂起阶段时，再根据需要更新：

```json
{
  "stage": "WAITING_CLARIFICATION",
  "pendingScene": "TENDER_REVIEW",
  "pendingAction": "PROVIDE_COMPARISON_SCOPE",
  "slots": {
    "missingField": "comparisonScope"
  }
}
```

或者：

```json
{
  "stage": "WAITING_UPLOAD",
  "pendingScene": "TENDER_REVIEW",
  "pendingAction": "UPLOAD_FILES",
  "slots": {
    "requiredFileCount": 2,
    "uploadedFileCount": 1
  }
}
```

这样的设计有几个好处：

- 结构足够轻
- 可读性强
- 前后端都容易消费
- 便于后续扩展
- 不会过早把会话层做成一个复杂状态机系统

这就是一个很典型的“先保证边界清晰，再逐步演进”的设计思路。

## 9. 为什么这一步对业务 Agent 很重要

如果系统只有单轮问答，或者始终是一问一答直接结束，那么 `session_state` 可以先不急。

但一旦进入下面这些情况，就值得正式引入：

- 有多轮澄清
- 有材料补交
- 有挂起任务
- 有阶段性执行
- 有工作台恢复需求
- 有“本轮先不执行，等待下一步输入”的交互

而这恰恰就是我们当前这个医药监管 Agent 项目的特点。

比如在标书审查场景中，经常会出现：

- 用户先发需求，再补材料
- 用户材料不完整，需要继续上传
- 系统需要澄清审查目标
- 前端工作台希望恢复当前任务进度

这时如果会话层只存消息，不存结构化状态，系统虽然能“回忆发生过什么”，但很难稳定知道“接下来该做什么”。

这就是为什么我会建议，在当前项目阶段，把 `session_state` 正式补进会话层设计里。

## 10. 这一节的结论

最后把这一节收束成一句最核心的话：

在本项目中：

- `chat_message` 负责记录对话事实
- `summary` 负责压缩上下文语义
- `session_state` 负责保存会话编排所需的结构化状态

三者分工不同，不能互相替代。

如果只靠消息历史，系统能知道“之前发生过什么”；  
如果补上 `session_state`，系统才能更稳定地知道“下一步该怎么编排”。

这正是业务 Agent 的会话层，和普通聊天机器人的会话层之间，一个非常重要的区别。

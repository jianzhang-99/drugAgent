# 药品监管 Agent 面试型教材思路

## 1. 教材定位

这套教材的目标不是单纯教学生“把 Agent 项目跑起来”，而是让学生在完成项目理解和实战开发之后，能够把自己的 Agent 开发能力清楚、有层次、有说服力地讲给面试官听。

因此，这套教材建议定位为：

**以真实项目为底座、以分层架构为主线、以面试表达为导向的 Agent 开发教材。**

教材最终要帮学生获得四种能力：

1. 能理解业务 Agent 和普通聊天机器人之间的区别
2. 能看懂并实现一个多层分工明确的 Agent 系统
3. 能发现项目中尚未完成的部分，并提出合理演进方案
4. 能围绕项目进行 Agent 开发面试表达

---

## 2. 教材总原则

如果这个项目是为了 Agent 开发面试服务，那么教材结构最适合保留原来的分层主线：

1. 用户入口
2. 会话层
3. 编排层
4. 检索层
5. 工具层
6. 模型层
7. 存储层
8. 监控评测层

这套分层非常适合面试，原因是它天然具备三个优点：

1. 容易讲清楚系统边界
2. 容易体现工程化能力
3. 容易让面试官快速判断你不是只会写 Prompt，而是真的理解 Agent 系统

因此，教材优化方向不是改掉这套分层，而是给每一层补充四类内容：

1. 这一层解决什么问题
2. 这一层在当前项目里的代码映射
3. 这一层的面试亮点怎么讲
4. 这一层项目里还可以怎么继续补齐

---

## 3. 项目主案例

教材统一围绕当前项目 `drug-agent` 展开，业务主案例优先使用“标书审查”场景。

贯穿案例建议固定为：

> 用户上传两份投标文件，提出“帮我看看这两份标书是否有围标风险”，系统接收请求，构建上下文，识别场景，准备文档数据，执行规则审查与风险融合，最终返回带证据链和评分的结构化结果。

这个案例适合作为面试讲解主线，因为它同时覆盖了：

1. 文件输入
2. 多轮对话
3. 场景识别
4. Tool / Workflow
5. 规则与模型协同
6. 结构化结果
7. 证据链
8. 业务可解释性

---

## 4. 教材结构

建议教材仍按八层展开，但每一章都固定讲四部分：

1. 本层职责
2. 项目映射
3. 面试表达
4. 可继续优化点

## 5. 八层教材主线

### 第 1 层：用户入口

这一层回答的问题：

1. 用户如何进入 Agent 系统
2. 系统如何接住普通对话和文件上传
3. 为什么业务 Agent 必须重视输入协议而不只是聊天文本

项目映射：

1. [AgentController.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/controller/AgentController.java)
2. [AgentChatReq.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/controller/domain/request/agent/AgentChatReq.java)

重点讲解：

1. `/agent/chat` 负责普通同步对话
2. `/agent/submit` 负责 `multipart/form-data` 文件上传对话
3. `reqJson + MultipartFile[] files` 的设计是为了兼容复杂业务输入

面试时可以这样讲：

“我项目的用户入口不是只有一个文本聊天接口，因为业务 Agent 需要接住结构化任务输入。在标书审查场景里，核心输入其实是文件，所以我把同步对话和文件上传对话分开设计，保证后端能稳定接收 query、sceneHint、sessionId 和多文件输入。”

这一层的亮点：

1. 不把 Agent 理解成纯聊天产品
2. 能处理复杂输入协议
3. 有明确的业务入口设计意识

这一层还可以继续补齐：

1. 上传接口的集成测试
2. 更明确的文件类型校验和错误码设计
3. 后续 SSE 或流式入口能力

适合出的面试题：

1. Agent 项目为什么不能只设计一个 `/chat` 接口
2. 业务 Agent 处理文件输入时要注意什么
3. `multipart/form-data` 相比 JSON 请求复杂在哪里

2. [AgentSessionService.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentSessionService.java)
3. [AgentMessageService.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentMessageService.java)
4. [ChatSession.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/common/entity/ChatSession.java)
5. [ChatMessage.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/common/entity/ChatMessage.java)

重点讲解：

1. `AgentChatService` 是对话主编排入口
2. `AgentSessionService` 负责会话聚合状态
3. `AgentMessageService` 负责消息明细持久化
4. 当前项目采取的是“摘要 + 最近窗口”的轻量记忆方案

面试时可以这样讲：

“我在会话层没有直接依赖重型记忆系统，而是先采用 chat_session 和 chat_message 两层结构。session 存聚合信息和摘要，message 存原始消息，模型上下文由摘要、最近消息窗口和当前请求共同组成，这样更容易控成本、控复杂度，也更符合当前业务阶段。”

这一层的亮点：

1. 有明确的会话与消息分层
2. 不是把全部历史消息无脑塞给模型
3. 体现对上下文窗口和系统成本的理解

这一层还可以继续补齐：

1. 摘要更新策略优化
2. 会话标题自动生成优化
3. 跨会话记忆能力

适合出的面试题：

1. Agent 为什么需要会话层
2. 你怎么控制多轮对话上下文长度
3. 为什么不直接把所有历史消息传给模型

### 第 3 层：编排层

这一层回答的问题：

1. 用户请求进入后如何判断场景
2. 为什么通用层不能直接写死具体业务规则
3. 如何从通用编排走向场景编排

项目映射：

1. [AgentSceneService.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentSceneService.java)
2. [TenderReviewSceneService.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/scene/tender_review/facade/TenderReviewSceneService.java)
3. [WorkflowRouteDecision.java](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/shared/model/WorkflowRouteDecision.java)
4. [上层通用Agent总体设计.md](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/doc/上层通用agent/技术文档/上层通用Agent总体设计.md)

重点讲解：

1. `AgentSceneService` 负责场景识别和分发
2. 当前通过 `sceneHint + 关键词规则 + fallback` 做路由
3. `TenderReviewSceneService` 是标书场景的统一入口
4. 当前实现是 MVP 版 facade 收口

面试时可以这样讲：

“我的编排层分成通用编排和场景编排两层。通用层只做上下文构建、场景路由和统一收口，不直接写业务细节；标书审查场景通过单独的 SceneService 进入，避免在 AgentChatService 里堆场景专属逻辑。”

这一层的亮点：

1. 有路由、有分发、有边界
2. 编排层不是业务逻辑堆积层
3. 能体现系统可扩展性

这一层还可以继续补齐：

1. 合同预审和风险预警的最小场景骨架
2. 路由策略进一步增强
3. 从 facade 演进到标准 `Orchestrator`

这一层最适合在面试里主动讲的“优化项”：

1. 当前标书审查已经通过 facade 收口
2. 下一步应该补齐 `TenderReviewToolOrchestrator`
3. 让主链进一步收敛到 `SceneService -> Orchestrator -> Tool -> Workflow`

适合出的面试题：

1. Agent 编排层和普通 Service 层有什么区别
2. 为什么不能在 Controller 或 ChatService 里直接执行业务 Workflow
3. 你怎么做场景路由

3. 能连接后续 Orchestrator 能力

这一层还可以继续补齐：

1. 新增 `ReviewTenderTool`
2. 补齐 Tool 单测
3. 标准化 Tool 输入输出结构

适合出的面试题：

## 6. 这套教材最该强调的面试价值

如果是为了面试，这套教材要帮助学生建立下面这套项目讲法：

### 6.1 先讲系统定位

不要一上来讲“我接了某个模型”，而是先讲：

1. 这是一个医药监管方向的业务 Agent 系统
2. 核心目标是做场景路由、结构化输出、证据链和可解释风险结果
3. 它不是普通聊天机器人

### 6.2 再讲八层架构

通过八层架构快速让面试官理解你有系统设计能力。

### 6.3 再讲主案例

用“上传两份标书 -> 围标审查 -> 输出报告”的链路把项目讲具体。

### 6.4 最后讲你做过的优化和还没做完但你知道怎么做的部分

这部分往往最加分。

你可以主动讲：

1. 当前标书审查已经通过 scene facade 收口
2. 下一步推荐补齐 `TenderReviewToolOrchestrator`
3. 当前已有 Tool DTO，下一步应补齐 `ReviewTenderTool`
4. 当前已有样本和测试基础，下一步应建立系统化回归评测

这类表达体现的是：

1. 你知道项目现状
2. 你知道架构目标
3. 你知道怎么从 MVP 演进到更稳定的系统

## 7. 最适合带学生一起补齐、也最适合拿去面试讲的项目缺口

下面这些不是“缺点”，而是非常适合设计成教材实战和面试亮点的内容。

### 7.1 补齐 `TenderReviewToolOrchestrator`

原因：

1. 当前设计文档已明确目标架构
2. 当前代码中 `orchestrator` 目录已存在但未真正落地
3. 这非常适合讲“从 MVP 到规范架构演进”

面试价值：

1. 能体现你会做架构收敛
2. 能讲清楚 facade、orchestrator、tool、workflow 的边界

### 7.2 补齐 `ReviewTenderTool`

原因：

1. 当前已有请求和结果 DTO
2. 但 Tool 主实现还没有真正形成完整教学案例

面试价值：

1. 能体现你理解 Tool 化设计
2. 能说明你不是只会把逻辑直接写进 Service

### 7.3 补齐上传链路端到端测试

原因：

1. 当前上传入口代码已具备
2. 但最能体现工程质量的是自动化验证

面试价值：

1. 能证明你关注闭环，不只是写接口
2. 能说明你有联调和回归意识

### 7.4 构建样本回归评测体系

原因：

1. 项目已有丰富样本
2. 这是最容易做成“教材作业 + 面试亮点”的部分

面试价值：

1. 能体现 Agent 工程能力
2. 能区别于只会调用 LLM API 的候选人

## 8. 教材写作建议

如果要把这份思路真正写成面试教材，建议每一章固定采用下面这个模板：

1. 本层解决的问题
2. 为什么业务 Agent 需要这一层
3. 当前项目中的代码位置
4. 这一层我会怎么向面试官解释
5. 当前项目这层做到了什么
6. 当前项目这层还缺什么
7. 如果让我继续迭代，我会怎么做
8. 本章面试题

这样写出来的教材会非常适合学生直接拿来做“项目讲稿”和“面试复盘”。

---

## 9. 一句话结论

如果这套项目学习的目标是 Agent 开发面试，那么最优教材思路不是弱化你原来的分层，而是：

**保留“用户入口、会话层、编排层、检索层、工具层、模型层、存储层、监控评测层”这八层主骨架，再把每一层都改造成“项目实现 + 面试表达 + 可继续优化点”的结构。**

这样学生最后得到的不是一份散乱的项目笔记，而是一套：

1. 能看懂项目
2. 能参与开发
3. 能发现问题
4. 能讲给面试官听

的完整 Agent 面试型教材。

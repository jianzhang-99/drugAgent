# 标书审查功能产品问题与改进建议

## 1. 文档目的

本文档用于整理当前“标书审查”功能在产品层面的主要问题、影响范围和改进方向，作为后续需求排期、前后端联调和产品迭代的参考依据。

本次评审基于当前项目的真实实现情况，包括：

- 工作台上传与 Agent 统一入口
- 标书审查专用任务接口
- 标书解析、规则审查、结果展示相关前后端代码
- 当前任务详情页与看板的实际承接方式

本文档不讨论理想化的大版本蓝图，重点聚焦“当前这版要先做什么”。

## 2. 当前产品目标判断

从现有设计文档和代码实现来看，当前“标书审查”功能的正确产品定位应当是：

- 面向围标、陪标、模板化痕迹等风险线索的自动筛查工具
- 输出可解释、可复核、可定位的风险证据
- 帮助监管、审计、采购、法务等角色更快完成初筛和复核

当前阶段不应被包装成：

- 直接认定违规的自动裁决系统
- 完整成熟的全文语义查重平台
- 可以替代人工调查和法务判断的最终决策系统

因此，产品改造的重点应围绕三件事展开：

- 统一任务链路
- 强化结果承接
- 突出证据价值

## 3. 当前流程概览

目前“标书审查”实际上存在两套并行流程。

### 3.1 Agent 统一入口流程

```text
工作台上传文件
-> /agent/drug/submit
-> 后端识别为 TENDER_REVIEW
-> 自动创建 case
-> 自动解析文档
-> 自动构造 TenderReviewData
-> 执行 TenderReviewWorkflow
-> 返回摘要/结果
```

特点：

- 用户操作简单
- 快速返回结果
- 更接近“智能助手”入口

问题：

- 用户不容易理解这是不是正式任务
- 与任务看板、任务详情的链路没有完全统一

### 3.2 标书专用任务流程

```text
创建任务
-> 解析文档
-> 执行审查
-> 查询结果
```

特点：

- 更接近正式业务任务流
- 更适合任务看板、结果页、人工复核

问题：

- 当前前端未完整接入
- 与 Agent 统一入口存在重复叙事

## 4. 核心问题清单

以下问题按产品优先级拆分为 `P0 / P1 / P2`。

## 5. P0 必须优先解决

P0 的目标是先让“标书审查”成为一条用户可理解、系统可闭环、结果可承接的主链路。

### 5.1 两套产品路径并存，用户心智混乱

#### 现象

当前同时存在：

- Agent 上传即审查
- 标书专用任务接口

用户从前端视角无法明确判断：

- 自己是在提一个聊天请求
- 还是在创建一个正式审查任务
- 还是已经进入了任务执行流程

#### 影响

- 产品入口认知混乱
- 前端后续功能容易重复开发
- 看板、详情、工作台之间缺乏统一故事线

#### 建议

统一成一条主链路：

```text
上传文件
-> 创建任务
-> 自动解析
-> 自动执行审查
-> 进入任务详情
```

其中工作台只作为“任务发起器”，不再和标书任务流平行存在。

### 5.2 解析和审查没有形成稳定闭环

#### 现象

当前专用任务流程虽然支持：

- 创建任务
- 解析文档
- 执行审查

但“执行审查”并未严格基于前面解析出的真实结果继续执行，存在产品语义不一致问题。

#### 影响

- 用户会误以为“解析成功 = 审查完成”
- 前端看到的解析结果和后端最终审查结果可能不是一条流水线
- 直接伤害产品可信度

#### 建议

需要明确：

- 解析结果是审查输入
- 审查结果必须基于已解析数据生成
- 任务详情页要显示“解析完成”和“审查完成”两个不同阶段

### 5.3 创建任务后没有把用户带到正确的下一步

#### 现象

当前上传成功后更偏向跳任务看板，而不是默认进入刚创建的任务详情。

#### 影响

- 用户操作连续性被打断
- 新建任务后无法立刻看到自己的结果承接页
- 增加理解成本

#### 建议

创建任务成功后应优先跳转：

```text
/任务详情/{caseId}
```

并默认展示：

- 文档状态
- 当前处理进度
- 初步风险摘要
- 下一步动作

### 5.4 产品主叙事不够聚焦

#### 现象

前端当前有：

- 聊天感
- 流程动画感
- 任务看板感
- 解析统计感

但缺少一个清晰主叙事。

#### 影响

- 用户不知道系统的核心价值是什么
- 演示时重点容易跑偏
- 产品形象更像“很多页面的原型集合”

#### 建议

主叙事统一成：

- 这是一个“标书风险审查工作台”
- 重点不是聊天，而是“发现风险并给出证据”

## 6. P1 核心能力完善

P1 的目标是让系统从“能跑”升级为“像一个真的标书审查产品”。

### 6.1 任务详情页现在更像解析页，不像审查页

#### 现象

当前任务详情页主要展示：

- 文档数
- 段落块数
- 表格数
- 字段数
- 字段预览

这些信息更像给研发或测试看的解析结果，而不是给业务用户看的审查结果。

#### 影响

- 用户难以迅速理解结论
- 页面价值感不足
- 无法支撑复核动作

#### 建议

任务详情页应升级为“审查结果页”，固定为以下结构：

- 任务概览
- 文档状态
- 风险总览
- 命中规则
- 关键证据
- 建议动作
- 执行日志

### 6.2 证据链表达不够强

#### 现象

当前前端仍然较多突出：

- 摘要
- 风险标签
- 统计信息
- 流程演示

但对“为什么判定有风险”的展示不够重。

#### 影响

- 不利于建立专业信任
- 用户很难直接进行人工复核
- 产品价值点不突出

#### 建议

把证据链提升为结果页主角：

- 哪条规则命中了
- 命中了哪几份文档
- 具体片段在哪里
- 为什么构成风险信号
- 是否存在免责或降权说明

### 6.3 建议动作不够产品化

#### 现象

当前“建议动作”更多还是静态文案或泛化提示。

#### 影响

- 页面看完后缺少可执行动作
- 任务结果停留在“展示”而不是“推动后续处理”

#### 建议

建议动作要更贴近业务决策，例如：

- 建议人工复核报价梯度异常
- 建议重点核查联系人与团队成员交叉复用
- 建议补充第三方证明材料
- 建议进入线下调查流程

### 6.4 看板和详情的状态表达需要统一

#### 现象

当前状态在不同页面上可能表现为：

- 任务状态
- 风险状态
- 解析状态
- 运行状态

用户不容易分清当前系统到底处于哪一步。

#### 影响

- 状态体系混乱
- 容易误解任务是否完成

#### 建议

统一成至少三层状态：

- 任务状态：待处理 / 处理中 / 已完成 / 失败
- 文档状态：待解析 / 解析中 / 已解析 / 解析失败
- 风险状态：高 / 中 / 低 / 待判定

## 7. P2 体验和表达优化

P2 的目标是增强产品化表达、演示力和可扩展性。

### 7.1 当前前端对 V1/V2 能力边界表达不够清晰

#### 现象

设计文档中已经明确：

- V1 以规则驱动的围标风险线索识别为主
- V2 再补全文语义比对

但当前前端表达容易让人误以为：

- 已经具备成熟全文语义查重能力
- 已经完成复杂洗稿识别

#### 影响

- 用户预期会被抬高
- 一旦实际能力与认知不一致，信任感会下降

#### 建议

所有对外文案都应主动收敛：

- 强调“风险筛查”
- 强调“辅助复核”
- 强调“当前重点识别围标线索”

### 7.2 过程感展示可以保留，但不应压过结果价值

#### 现象

当前工作台加入了一些过程步骤播放和动画表达。

#### 影响

- 对演示有帮助
- 但如果权重过高，会让产品像“AI 炫技页面”

#### 建议

过程可展示，但必须服务于结果理解：

- 处理到哪一步
- 当前卡在哪一步
- 哪一步产生了关键结论

而不是只展示“系统正在思考”的氛围感。

### 7.3 页面角色要更清晰

建议明确每个页面的职责：

- 工作台：发起任务、快速追问、查看最新结果摘要
- 看板：管理所有任务、筛选和定位任务
- 详情页：查看完整审查结果、证据链和建议动作

这样用户才不会在多个页面之间感到重复和混乱。

## 8. 推荐的改造优先顺序

建议按以下顺序推进：

### 第一阶段：统一主链路

- 明确只有一条标书审查主链路
- 工作台只负责发起任务
- 创建任务成功后进入任务详情

### 第二阶段：打通真实闭环

- 解析结果与审查结果串联
- 看板展示真实任务状态
- 详情页展示真实审查结果

### 第三阶段：强化结果页

- 以风险、证据、建议为核心组织详情页
- 让用户在详情页完成理解和复核

### 第四阶段：统一表达与视觉

- 收敛文案
- 明确 V1 边界
- 统一状态和视觉语言

## 9. 建议的产品主链路

推荐最终形成如下产品路径：

```text
工作台上传标书
-> 创建审查任务
-> 自动解析文档
-> 自动执行审查
-> 进入任务详情
-> 查看风险总览与证据链
-> 决定是否人工复核
```

这条链路的好处是：

- 用户理解简单
- 前端承接自然
- 看板和详情职责清晰
- 更符合监管审查产品定位

## 10. 第一批要落地的产品动作

建议优先推动以下事项：

| 优先级 | 动作 | 目标 |
|---|---|---|
| P0 | 统一标书审查主链路 | 消除入口混乱 |
| P0 | 创建任务后直达详情 | 提升链路连续性 |
| P0 | 串联解析与审查 | 保证结果可信 |
| P1 | 重构任务详情页信息架构 | 从解析页升级为审查页 |
| P1 | 强化证据链展示 | 提升专业信任感 |
| P1 | 统一状态体系 | 降低理解成本 |
| P2 | 收敛对外能力表达 | 管理用户预期 |
| P2 | 优化演示和视觉 | 提升产品感 |

## 11. 结论

当前“标书审查”功能最大的产品问题，不是页面不够多，也不是样式不够炫，而是：

- 任务主链路没有统一
- 解析和审查还没有真正串起来
- 结果页没有把证据价值充分表达出来

只要优先把这三件事做好，这个功能就会从“一个能跑的 demo”升级为“一个有产品雏形的标书审查平台”。

# 任务看板改造计划

## 一、项目背景

当前任务看板已具备基础的任务展示能力，但整体更偏“系统字段展示”，还没有达到业务用户可快速判断、快速处理、快速追踪的产品目标。

从现状看，主要存在以下问题：

1. 任务名称不可读，存在“未命名任务”、场景码直接展示等问题。
2. 卡片信息偏技术视角，用户无法快速判断任务价值和处理优先级。
3. 进度展示只有百分比，没有反映真实执行阶段。
4. 风险、异常、人工介入状态不够突出，任务之间看起来差异不明显。
5. 缺少面向操作的按钮和下一步引导，用户看到任务后不知道应该做什么。
6. 缺少筛选、排序、分组与概览统计，无法支撑多任务并行场景。

因此，需要对任务看板进行一次面向业务闭环的改造，将其从“任务列表”升级为“任务调度与处置中枢”。

---

## 二、改造目标

### 2.1 产品目标

将任务看板建设为场景一标书审查的统一任务管理入口，支持用户完成以下关键动作：

1. 快速识别当前最重要的任务。
2. 快速理解任务当前执行到哪一步。
3. 快速判断是否需要人工介入。
4. 快速进入报告、证据、复核、追问等后续动作。

### 2.2 成功标准

改造完成后，任务看板应满足：

1. 用户在 3 秒内能看懂每个任务是什么、状态如何、是否要处理。
2. 用户在 1 次点击内能进入任务详情或完整报告。
3. 高风险、失败、待人工复核任务可被明显识别并优先处理。
4. 卡片内容不再直接暴露 UUID、场景码、ISO 时间等原始技术字段。
5. 看板支持运行中、待处理、待复核、已完成等核心状态管理。

---

## 三、设计原则

### 3.1 业务优先

优先展示业务用户真正关心的信息，而不是系统内部字段。

### 3.2 状态清晰

用户必须一眼知道任务在“等待中、运行中、待复核、失败、已完成”中的哪一种。

### 3.3 风险驱动

高风险、异常中断、待人工介入任务必须更突出，并在排序上优先。

### 3.4 可操作

每张卡片不仅要“展示结果”，还要明确给出“下一步能做什么”。

### 3.5 可扩展

设计需兼容后续合同预审、合规预警等其他场景，避免只服务单一页面。

---

## 四、现状问题拆解

## 4.1 信息命名问题

当前问题：

1. 直接显示 `tender_review` 等场景码。
2. 直接显示长 UUID，阅读成本高。
3. 出现“未命名任务”，无法建立业务语义。
4. 时间展示为 ISO 格式，不符合日常阅读习惯。

改造方向：

1. 场景码转中文业务名称，如“标书审查”。
2. UUID 下沉为弱信息，默认展示简化任务编号。
3. 基于文件名、项目名、场景自动生成任务名。
4. 时间统一转为“今天 14:33 / 3分钟前 / 2026-03-22 14:33”。

## 4.2 状态表达问题

当前问题：

1. 任务卡片之间视觉差异弱。
2. `0%` 不能说明任务为什么没有进展。
3. 无法区分“排队中”和“失败中断”。

改造方向：

1. 引入统一状态模型：等待中、运行中、待复核、失败、已完成。
2. 用“阶段进度”替代纯百分比。
3. 为高风险、失败、待人工任务设置更强视觉优先级。

## 4.3 任务内容问题

当前问题：

1. 卡片没有一句话摘要。
2. 没有风险结论、文件数量、当前步骤等关键信息。
3. 用户看见任务后无法立即判断是否值得点进去。

改造方向：

每张卡片至少展示：

1. 任务名称
2. 场景/提交人/提交时间
3. 一句话任务摘要
4. 当前阶段
5. 风险等级
6. 文件数量
7. 下一步操作入口

## 4.4 看板结构问题

当前问题：

1. 所有任务平铺，没有分组。
2. 缺少总体统计，不利于任务管理。
3. 无筛选、无排序、无搜索。

改造方向：

增加以下能力：

1. 顶部统计卡片
2. 状态筛选
3. 风险筛选
4. 场景筛选
5. 按优先级/更新时间排序

---

## 五、目标方案

## 5.1 看板信息架构

建议将任务看板拆为 3 层：

### 第一层：全局概览区

展示总体任务状态，建议包含：

1. 运行中任务数
2. 待人工复核任务数
3. 高风险任务数
4. 今日完成任务数

作用：

1. 帮助用户快速判断当前工作负荷。
2. 建立“优先看哪里”的心智。

### 第二层：筛选与排序区

建议支持：

1. 按状态筛选
2. 按风险等级筛选
3. 按场景筛选
4. 按提交时间/更新时间排序
5. 关键词搜索

作用：

1. 支撑任务量上来后的查找效率。
2. 支撑不同角色按自己关注点查看任务。

### 第三层：任务卡片区

每张卡片建议包含以下内容：

1. 任务名称
2. 状态标签
3. 风险标签
4. 场景
5. 提交人
6. 提交时间
7. 一句话摘要
8. 文件数量
9. 当前阶段
10. 阶段进度条
11. 任务操作按钮

---

## 5.2 任务卡片推荐结构

推荐卡片结构如下：

### 头部信息

1. 任务名称
2. 状态标签
3. 风险标签
4. 弱化展示任务编号

### 中部信息

1. 场景
2. 提交人
3. 提交时间
4. 文件数量

### 核心摘要区

用一句话描述当前进展或结论，例如：

1. 已完成文档解析，正在进行规则扫描。
2. 识别到 3 条高风险线索，等待人工复核。
3. 未发现保留高风险命中，低风险报告已生成。

### 进度区

展示阶段型进度，例如：

1. 文件接收
2. 结构化解析
3. 规则扫描
4. 风险融合
5. 报告生成
6. 已完成

### 操作区

建议按钮：

1. 查看详情
2. 查看报告
3. 继续追问
4. 重试任务
5. 标记已复核

其中按钮按状态动态展示：

1. 运行中任务：查看详情
2. 待复核任务：查看报告、去复核
3. 失败任务：查看原因、重试任务
4. 已完成任务：查看报告、继续追问

## 六、状态模型设计

建议统一任务状态模型：

| 状态 | 含义 | 用户动作 |
| :--- | :--- | :--- |
| WAITING | 已提交，等待执行 | 查看排队信息 |
| RUNNING | 正在执行中 | 查看详情 |
| REVIEW_REQUIRED | 需人工复核 | 查看报告 / 去复核 |
| FAILED | 执行失败 | 查看原因 / 重试 |
| COMPLETED | 已完成 | 查看报告 / 继续追问 |

建议统一风险模型：

| 风险等级 | 展示文案 | 视觉建议 |
| :--- | :--- | :--- |
| HIGH | 高风险 | 红色强调 |
| MEDIUM | 中风险 | 橙色强调 |
| LOW | 低风险 | 绿色强调 |
| NONE/UNKNOWN | 信息 | 灰蓝弱化 |

## 七、数据字段改造建议

为支撑新版看板，建议后端返回以下字段：

| 字段 | 说明 |
| :--- | :--- |
| taskId | 任务唯一标识 |
| taskNo | 面向用户的短编号 |
| taskName | 任务名称 |
| sceneLabel | 场景中文名 |
| status | 任务状态 |
| statusLabel | 状态展示文案 |
| riskLevel | 风险等级 |
| riskLabel | 风险展示文案 |
| summary | 一句话摘要 |
| currentStage | 当前阶段编码 |
| currentStageLabel | 当前阶段文案 |
| stageProgress | 当前阶段完成数 |
| totalStages | 总阶段数 |
| fileCount | 文件数量 |
| submittedBy | 提交人 |
| submittedAt | 提交时间 |
| updatedAt | 最近更新时间 |
| canRetry | 是否可重试 |
| canReview | 是否可人工复核 |
| canOpenReport | 是否可查看报告 |

同时建议前端本地增加一层映射与兜底规则：

1. 没有任务名时自动生成任务名。
2. 没有摘要时自动生成一句默认摘要。
3. 没有阶段信息时按状态给出兜底展示。

## 八、分阶段实施计划

## Phase 1：可读性修复

目标：
先把“看不懂”的问题解决，让看板基本可用。

范围：

1. 场景码中文化
2. 时间格式中文化
3. UUID 弱化
4. 自动生成任务名称
5. 增加任务摘要
6. 补充风险标签与状态标签

预计工作量：
2 到 3 人天

验收标准：

1. 页面中不再出现 `未命名任务`
2. 不再直接展示原始场景码作为主要标题
3. 用户能快速读懂每条任务是什么

## Phase 2：状态与进度升级

目标：
解决“进度没有意义、状态不清晰”的问题。

范围：

1. 百分比进度改为阶段进度
2. 引入统一任务状态模型
3. 增加当前阶段显示
4. 优化高风险/失败/待复核任务的视觉优先级

预计工作量：
3 到 4 人天

验收标准：

1. 用户可明确知道任务处于哪个执行阶段
2. 高优先级任务能被明显识别
3. 运行中、待复核、失败任务不会混淆

## Phase 3：任务调度能力增强

目标：
让看板真正具备“管理任务”的能力。

范围：

1. 顶部统计卡片
2. 状态筛选
3. 风险筛选
4. 搜索与排序
5. 支持批量查看和快速定位

预计工作量：
3 到 5 人天

验收标准：

1. 用户可在多任务场景下快速定位目标任务
2. 看板可支持日常任务运营和调度

## Phase 4：动作闭环增强

目标：
让任务从“展示”走向“处置”。

范围：

1. 查看详情
2. 查看报告
3. 去复核
4. 重试任务
5. 继续追问

预计工作量：
4 到 6 人天

验收标准：

1. 用户从看板到详情、报告、复核操作链路顺畅
2. 失败任务和待复核任务都具备明确下一步入口

## 九、里程碑建议

| 里程碑 | 内容 | 目标结果 |
| :--- | :--- | :--- |
| M1 | 完成可读性修复 | 看板从“技术列表”升级为“可读任务列表” |
| M2 | 完成状态与阶段进度改造 | 用户可清楚理解任务执行进展 |
| M3 | 完成筛选排序与统计能力 | 看板具备管理多任务能力 |
| M4 | 完成操作闭环 | 看板成为任务调度入口 |

---

## 十、风险与注意事项

| 风险 | 影响 | 应对方案 |
| :--- | :--- | :--- |
| 后端字段不足 | 无法完整展示阶段与摘要 | 先前端兜底，后端补齐正式字段 |
| 多场景定义不统一 | 看板文案混乱 | 先统一状态、风险、阶段字典 |
| 自动命名不稳定 | 任务名可读性不足 | 采用“项目名/文件名 + 场景名”规则生成 |
| 任务量增长后性能下降 | 列表加载体验差 | 提前预留分页、懒加载、筛选缓存能力 |

---

## 十一、推荐下一步

建议按以下顺序推进：

1. 先完成 Phase 1 和 Phase 2，让页面“能看、能理解”。
2. 再推进 Phase 3，把看板从展示页升级为管理页。
3. 最后推进 Phase 4，形成任务处理闭环。

如果资源有限，建议优先做下面 3 件事：

1. 自动命名 + 中文字段替换
2. 状态标签 + 阶段进度
3. 查看报告 / 查看详情入口

这样改完后，任务看板的产品感会有明显提升。

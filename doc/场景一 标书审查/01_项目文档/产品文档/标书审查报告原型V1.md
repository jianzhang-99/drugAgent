# 标书审查报告原型 V1

> 文档状态：产品原型稿  
> 适用场景：标书审查、围标串标风险初筛、投标文件非独立编制风险识别  
> 目标读者：业务负责人、评标专家、招采人员、风控/合规人员、研发实现人员  
> 创建日期：2026-04-16

## 1. 原型目标

当前标书审查报告不应继续以“系统命中结果”作为主要呈现方式，而应改为“人工复核决策单”。

报告需要优先回答以下 4 个问题：

1. 这批标书到底有什么异常？
2. 为什么系统认为这些异常值得人工复核？
3. 证据在哪里，文档 A 和文档 B 分别是什么？
4. 下一步谁该做什么？

因此，本报告原型的核心原则是：

- 面向业务读者，而不是面向研发或规则引擎。
- 用自然语言解释风险，不暴露内部规则编码和原因码。
- 每条关键证据必须能看到双侧内容，不能只展示单份文档。
- 结论要具体描述问题，不只给“高/中/低风险”标签。
- 处置建议要能落到角色和动作，而不是泛泛提醒。

## 2. 总体信息架构

最终报告保留 7 个部分：

| 顺序 | 模块 | 目的 |
|---|---|---|
| 1 | 总体结论 | 让用户快速理解本次审查发现了什么，以及是否需要人工复核 |
| 2 | 本次比对文件 | 说明文档 A、文档 B 分别对应哪份文件和投标主体 |
| 3 | 风险总览 | 按业务风险方向展示真实命中的风险，不展示未命中的维度 |
| 4 | 重点风险判断 | 对核心风险逐项解释“是什么、为什么、怎么办” |
| 5 | 关键证据明细 | 展示 A/B 双侧证据、对比发现和复核建议 |
| 6 | 处置建议 | 给出可执行的人工复核任务清单和建议责任角色 |
| 7 | 报告边界说明 | 说明报告只作为辅助判断，不替代最终评审或法律定性 |

## 3. 页面顶部

页面顶部只保留最少必要信息。

### 推荐展示

```text
标书审查报告

生成时间：2026-04-16 10:30
审查说明：本报告用于辅助识别标书疑似围标、串标或非独立编制风险，不直接替代最终评审结论。
```

### 不推荐展示

| 字段 | 处理方式 | 原因 |
|---|---|---|
| 报告编号 | 不展示 | 用户无感，容易增加噪音 |
| 审查对象 | 不展示 | 文件清单已经能表达对象 |
| 审查范围 | 不展示 | 由“本次比对文件”自然说明 |
| 审查类型 | 不展示 | 标题已表达报告类型 |
| 任务编号 / traceId | 默认不展示 | 可留后台或调试区，不进入正文 |

## 4. 一、总体结论

总体结论要直接描述本次发现的问题，而不是只写“高风险”。

### 内容原型

```text
本次比对发现两份投标文件在报价结构、核心团队成员和部分关键条款表述上存在多处异常相似特征。

其中，报价明细出现规律性价差，核心团队中多名成员重复，技术方案与风险应对内容存在高度相似表述。上述线索共同指向两份文件可能存在非独立编制或协同编写风险。

建议先暂停自动通过流程，进入人工重点复核。复核重点应放在报价形成依据、人员真实归属、文件编制来源和关键条款原文比对。
```

### 总体结论指标

总体结论下只保留 3 个业务可读指标：

| 指标 | 示例值 | 说明 |
|---|---|---|
| 复核优先级 | 需优先复核 | 替代“高/中/低风险”作为主结论 |
| 关键风险项 | 3 项 | 表示需要重点关注的核心问题数量 |
| 可追溯证据 | 5 条 | 表示能支撑结论的证据数量 |

### 不推荐展示

| 内容 | 原因 |
|---|---|
| 风险分 100 | 很难解释，容易被质疑 |
| 命中规则 3 | 用户不知道规则是什么 |
| 一句话结论 | 并入总体结论，避免重复 |

## 5. 二、本次比对文件

本节替代原来的“涉及文档信息”。

### 表格原型

| 文件标识 | 投标主体 | 文件名称 | 在本次报告中的作用 |
|---|---|---|---|
| 文档 A | 晟博云创 | 投标人A_晟博云创_W-M1测试标书.md | 作为第一份投标文件参与比对 |
| 文档 B | 晟拓数科 | 投标人B_晟拓数科_W-M1测试标书.md | 作为第二份投标文件参与比对 |

### 说明文案

```text
说明：本报告中的“文档 A”和“文档 B”仅用于方便阅读，不代表评审排序或责任判断。
```

### 开发要求

- 不允许在用户报告中展示 `UPLOAD-0-1776176851202` 这类系统内部 ID。
- 所有内部文档 ID 必须映射为“文档 A / 文档 B / 文档 C”和真实文件名。
- 如果能识别投标主体，应展示投标主体；否则展示“投标方 A / 投标方 B”。

## 6. 三、风险总览

风险总览只展示真实命中的风险方向，不展示未命中的维度。

### 表格原型

| 风险方向 | 发现情况 | 复核必要性 | 简要说明 |
|---|---|---|---|
| 报价异常 | 发现明显异常 | 必须复核 | 多个报价项呈现规律性价差，需核查报价形成过程 |
| 核心团队重复 | 发现明显异常 | 必须复核 | 两份文件中出现多名核心人员重合 |
| 关键条款相似 | 发现明显异常 | 必须复核 | 技术方案、风险应对等内容存在高度相似表达 |

### 不推荐展示

```text
模板同源：低风险
其他辅助风险：低风险
```

未命中的维度不应为了凑表格而展示，否则会降低报告可信度。

## 7. 四、重点风险判断

本节替代原来的“核心风险 Top 3”。

不建议继续使用 `Top 3` 这类算法排行榜表达，建议使用“重点风险判断”。

### 风险 1：报价结构异常

```text
风险说明：
两份投标文件中多个报价项目存在规律性价差，差异呈现固定模式，不符合独立报价中常见的随机波动特征。

关键事实：
平台软件开发、配置实施、培训交付、测试支持等多个报价项均出现接近或固定差异。

为什么需要复核：
如果报价差异长期呈规律性分布，可能说明报价不是由各投标主体独立测算形成，而是存在统一编制、协同调整或陪标报价的可能。

建议动作：
复核报价明细表、报价形成依据、报价编制人员和历史报价记录。
```

### 风险 2：核心团队成员重复

```text
风险说明：
两份投标文件中发现多名核心团队成员重复，涉及项目经理、技术负责人等关键角色。

关键事实：
同一人员出现在不同投标主体的核心团队配置中。

为什么需要复核：
核心团队成员重复可能影响投标主体独立履约能力判断，也可能提示主体之间存在人员借用、资质共享或协同投标风险。

建议动作：
核查人员社保归属、劳动关系、授权文件、任职单位和项目履历。
```

### 风险 3：关键条款高度相似

```text
风险说明：
两份投标文件在风险识别、应对措施和部分实施方案描述上存在高度相似表达。

关键事实：
多处段落在内容结构、句式和业务表达上接近，部分内容相似度达到较高水平。

为什么需要复核：
如果相似内容超出行业通用表达范围，可能说明文件存在同源底稿、统一模板或协同编写情况。

建议动作：
人工对照原文，判断相似内容是否属于行业通用描述，必要时比对历史投标文件。
```

### 禁止展示的内部标识

以下内容不应进入用户报告正文：

```text
W-M1
MULTI_RULE_CO_OCCURRENCE
MULTI_HIT_ACCUMULATION
CROSS_DOCUMENT_EVIDENCE
EVIDENCE_SUFFICIENT
HIGH_PRIORITY_RULE
```

这些信息只能保留在后台调试、审计元数据或开发日志中。

## 8. 五、关键证据明细

本节是整份报告最重要的部分。

每条证据必须同时展示文档 A 和文档 B 的内容，并说明系统发现了什么。

### 报价类证据卡片原型

```text
证据 E01：报价项存在规律性差异

证据指向：
报价异常

涉及文件：
文档 A：晟博云创投标文件
文档 B：晟拓数科投标文件

文档 A 原文 / 数据：
平台软件开发与配置实施：820000 元

文档 B 原文 / 数据：
平台软件开发与配置实施：821000 元

对比发现：
两份文件在该报价项上差异为 1000 元。类似差异还出现在多个报价项目中，呈现规律性。

复核建议：
核查两家投标主体的报价测算过程、成本依据和报价审批记录。
```

### 文本类证据卡片原型

```text
证据 E02：风险应对条款高度相似

证据指向：
关键条款相似

涉及文件：
文档 A：晟博云创投标文件
文档 B：晟拓数科投标文件

文档 A 摘录：
针对患者主数据口径不一致问题，建立统一的数据治理机制……

文档 B 摘录：
针对患者主数据口径不一致问题，建立统一的数据治理机制……

对比发现：
两份文件在风险描述、应对路径和句式结构上高度一致，疑似超出普通行业通用表达。

复核建议：
结合上下文判断是否为招标文件模板要求、行业标准表述，还是投标文件之间的异常雷同。
```

### 证据卡片必须包含的字段

| 字段 | 是否必填 | 说明 |
|---|---|---|
| 证据编号 | 是 | 如 E01、E02 |
| 证据标题 | 是 | 用业务语言描述 |
| 证据指向 | 是 | 如报价异常、团队重复、条款相似 |
| 涉及文件 | 是 | 必须展示文档 A 和文档 B |
| 文档 A 内容 | 是 | 不能只展示摘要 |
| 文档 B 内容 | 是 | 不能缺失 |
| 对比发现 | 是 | 说明 A/B 之间的异常关系 |
| 复核建议 | 是 | 告诉业务下一步怎么查 |
| 定位信息 | 可选 | 章节、页码、段落位置，后续补强 |

## 9. 六、处置建议

处置建议应从“建议动作列表”升级为“复核任务清单”。

### 表格原型

| 优先级 | 建议动作 | 责任角色 | 目标 |
|---|---|---|---|
| 高 | 复核报价明细和报价形成依据 | 评标专家 / 招采人员 | 判断报价异常是否成立 |
| 高 | 核查核心人员归属和授权关系 | 风控 / 合规人员 | 判断团队重复是否合理 |
| 中 | 对关键相似段落做人工原文比对 | 评标专家 | 判断是否超出通用模板范围 |
| 中 | 查询历史投标记录和历史模板 | 招采管理员 | 判断是否存在长期协同或同源文件 |
| 低 | 归档系统报告、人工复核意见和佐证材料 | 项目负责人 | 形成可追溯审查闭环 |

## 10. 七、报告边界说明

报告边界说明要保留，但需要简短、明确。

### 推荐文案

```text
本报告为系统辅助审查结果，仅用于提示疑似风险和辅助人工复核。

报告结论基于当前已上传文件生成。如存在未上传附件、补充说明、历史投标文件或外部主体关系资料，可能影响最终判断。

文本相似、报价规律和团队重复均属于风险信号，不直接等同于违法违规认定。最终处理意见应结合人工复核、评审规则和项目实际情况确定。
```

## 11. 删除内容清单

以下内容不进入 V1 报告正文：

| 删除内容 | 删除原因 |
|---|---|
| 报告编号 | 用户无感，正文不需要 |
| 审查对象 | 与文件清单重复 |
| 审查范围 | 由“本次比对文件”表达 |
| 审查类型 | 标题已表达 |
| 一句话结论 | 并入总体结论 |
| 规则编码 / 原因码 | 内部实现，不面向用户 |
| 空泛附录 | 暂无明确业务价值 |
| 未命中风险维度 | 容易显得凑内容 |

## 12. 开发落地约束

后续实现时应遵守以下约束：

1. 前端正式报告不得直接渲染后端内部编码字段。
2. 后端可保留规则编码和原因码，但必须在响应适配层转为用户可读描述。
3. 证据明细必须优先使用双侧对比结构，不能只展示单侧内容。
4. 如果某条证据缺少文档 B 内容，该证据不得作为“关键证据明细”展示，应降级为“待补充线索”。
5. 风险总览只展示真实命中的风险方向。
6. 总体结论必须是完整自然语言段落，不得只输出“高风险”“中风险”“低风险”。
7. `traceId`、`UPLOAD-*`、规则原因码等调试信息不得出现在报告正文。

## 13. 验收标准

一版报告是否合格，可以按以下问题验收：

| 验收问题 | 合格标准 |
|---|---|
| 用户能否 30 秒内看懂本次主要异常？ | 总体结论能直接说明异常类型和建议动作 |
| 用户是否知道比对了哪些文件？ | 文档 A/B 能映射真实文件和投标主体 |
| 用户是否能理解为什么有风险？ | 重点风险判断中有“为什么需要复核” |
| 用户是否能看到证据双方内容？ | 每条关键证据都有文档 A 和文档 B |
| 用户是否知道下一步怎么做？ | 处置建议能落到动作、角色和目标 |
| 报告是否避免暴露内部实现？ | 正文无 `UPLOAD-*`、规则编码、原因码 |

# 标书审查测试用例与AI执行指引

## 1. 文档目的

本文档用于在当前版本进入集中测试阶段时，统一标书审查场景的测试目标、样本集、通过标准与 AI 执行方式。

适用范围：

- 标书审查主链路
- `POST /api/agent/chat`
- `POST /api/agent/submit`
- `POST /api/agent/chat/stream`

当前默认测试地址：

- 后端地址：`http://localhost:8124`
- 接口前缀：`/api`

---

## 2. 测试目标

本轮测试不只验证“能不能返回回答”，而是重点验证以下 5 件事：

1. 是否正确路由到 `TENDER_REVIEW` 场景。
2. 是否在文件不足、参数异常时稳定返回结构化澄清或错误。
3. 是否能对高危围标样本给出合理风险判断、证据链和报告字段。
4. 是否能控制误报，对合规样本不过度判高风险。
5. 是否能在灰度与对抗样本下保持可解释、不过度幻觉。

---

## 3. 执行前准备

### 3.1 环境准备

执行测试前应满足：

- 后端已启动。
- MySQL 已初始化 `schema.sql` 与 `taskboard-schema.sql`。
- 已配置 `DASHSCOPE_API_KEY`。
- 如需验证语义分析增强能力，确保外部 LLM 服务可用。

### 3.2 样本目录

本轮建议优先使用以下现成样本：

- 基准模板：`doc/场景一 标书审查/03_整理后样本数据/0_标准基准样本/标准标书模板_医院智慧平台项目.md`
- 高危样本组：`doc/场景一 标书审查/03_整理后样本数据/2_高危样本对比组`
- 合法合规样本组：`doc/场景一 标书审查/03_整理后样本数据/3_合法合规样本组`
- 灰度与对抗组：`doc/场景一 标书审查/03_整理后样本数据/4_灰度与对抗演练测试组`

### 3.3 执行约束

每个测试用例建议：

- 使用新的 `sessionId`，避免历史上下文串扰。
- 优先使用 `/api/agent/submit` 上传文件，不要手工先传 OSS 再拼 `fileIds`。
- 记录完整响应 JSON，不只摘录 `answer`。
- 对每条用例分别记录“是否通过”和“失败原因”。

## 4. 统一通过标准

### 4.1 P0 必过项

以下任一项失败，都应判定为阻塞问题：

1. 上传 2 份标书后未路由到 `TENDER_REVIEW`。
2. 返回体缺失 `scene`、`routeReason`、`routeSource`、`answer` 关键字段。
3. 高危样本返回 `LOW` 且无任何有效证据。
4. 合规样本被直接判为 `HIGH`，且没有充分证据支持。
5. 文件不足时没有给出明确澄清或错误提示。

### 4.2 P1 重要项

以下项建议作为重点评分指标：

1. `riskLevel`、`score`、`report`、`evidenceList`、`evidenceGroups`、`steps` 是否完整。
2. `answer` 是否能复述核心风险，而不是泛泛而谈。
3. `evidenceList` 是否指向明确风险点，而非空洞描述。
4. `thinkingSteps` 是否与执行链路基本一致。
5. 对弱命中或灰度样本，是否提示“建议人工复核”。

### 4.3 P2 观察项

以下项用于后续优化，不作为本轮一票否决：

1. `sessionTitle` 是否生成准确。
2. `managementSummary` 与 `suggestedActions` 是否可读。
3. `structuredData` 是否便于前端复用。
4. SSE 流式场景是否优雅降级。

## 5. 响应断言模板

对于成功进入标书审查的响应，至少应断言：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "sessionId": "非空",
    "traceId": "非空",
    "scene": "TENDER_REVIEW",
    "routeReason": "非空",
    "routeSource": "非空",
    "confidence": "非空",
    "answer": "非空",
    "riskLevel": "非空",
    "score": "存在即可",
    "steps": "非空数组",
    "thinkingSteps": "非空数组"
  }
}
```

如命中标书工作流，建议进一步断言：

- `data.report` 不为空
- `data.evidenceList` 长度大于 0
- `data.documentIds` 长度等于上传文件数
- `data.documentNames` 长度等于上传文件数

## 6. 接口与异常测试用例

### 6.1 冒烟与协议测试

| 用例ID | 类型 | 输入 | 预期结果 |
| --- | --- | --- | --- |
| API-01 | 普通对话 | `POST /api/agent/chat`，仅传 `query=你好，介绍一下你能做什么` | `scene=DEFAULT`；接口 200；不应误入 `TENDER_REVIEW` |
| API-02 | 文件强路由 | `POST /api/agent/submit`，上传任意 2 份标书文件，`query=帮我看看这两份标书是否有围标风险` | `scene=TENDER_REVIEW`；`routeSource` 应体现文件或强规则来源；返回结构化审查结果 |
| API-03 | 文件不足 | 只上传 1 份文件 | 接口 200 或明确错误；必须提示“至少需要两份标书文件”或同义信息 |
| API-04 | 缺少 query | `/api/agent/submit` 传空 `query` | 返回 `code=500` 且 `message` 提示 `query 不能为空` |
| API-05 | 显式场景 | `/api/agent/chat` 传 `sceneHint=TENDER_REVIEW`，同时附 `fileIds` 或文件 | 应直接进入 `TENDER_REVIEW` |
| API-06 | 流式降级 | `/api/agent/chat` 传 `stream=true` 且带文件 | 不应崩溃；允许降级为同步结果，但需返回可消费响应 |

### 6.2 推荐请求示例

#### 同步聊天

```bash
curl -X POST "http://localhost:8124/api/agent/chat" \
  -H "Content-Type: application/json" \
  -d '{
    "sessionId": "tc-api-01",
    "query": "你好，介绍一下你能做什么"
  }'
```

#### 文件上传审查

```bash
curl -X POST "http://localhost:8124/api/agent/submit" \
  -F 'req={"sessionId":"tc-wm1","query":"帮我看看这两份标书是否有围标风险"}' \
  -F "files=@doc/场景一 标书审查/03_整理后样本数据/2_高危样本对比组/W-M1_报价梯度异常测试组/投标人A_晟博云创_W-M1测试标书.md" \
```

## 8. 推荐判定口径

### 8.1 高危样本判通过

满足以下 4 项中的至少 3 项，可判高危样本基本通过：

1. `scene=TENDER_REVIEW`
2. `riskLevel` 为 `HIGH` 或 `MEDIUM`
3. `evidenceList` 或 `report.riskItems` 中出现与该组标签一致的风险线索
4. `answer` 明确提到对应异常特征，而非泛化描述

对于 `W-M1 / W-M2 / W-M4 / W-M5 / W-M6 / W-P5 / W-P6`，建议提高标准：

- 最好直接判 `HIGH`
- 最好有明确证据标题或命中说明
- 不应只返回“建议人工核查”这种弱结论

### 8.2 合规样本判通过

满足以下条件可判通过：

1. 不得直接判 `HIGH`
2. `answer` 中不应无依据指控串标
3. 若识别出局部相似，应解释为模板、法规、公开材料或行业常规表达等可能原因
4. 若无法完全确认，应提示人工复核，而不是武断定性

### 8.3 灰度样本判通过

灰度样本更关注系统行为是否健康：

1. 可以不完全命中，但不能明显幻觉。
2. 可以给出不确定结论，但必须说明原因。
3. 如果证据不足，优先输出“建议人工复核”，而不是捏造证据。

## 9. AI 执行测试提示词

以下提示词可以直接交给另一个 AI 使用：

```text
你现在是 drug-agent 项目的测试执行助手。请严格按照以下要求执行标书审查测试：

1. 测试目标：
- 验证 /api/agent/chat、/api/agent/submit、/api/agent/chat/stream 在标书审查场景下的正确性、稳定性、证据链完整性和误报控制能力。

2. 执行规则：
- 每个用例使用新的 sessionId。
- 优先使用 /api/agent/submit 上传本地样本文件。
- 保存完整响应 JSON。
- 不要只看 answer，要同时检查 scene、routeReason、routeSource、riskLevel、score、report、evidenceList、evidenceGroups、steps、thinkingSteps。
- 对每个用例输出：用例ID、请求、关键响应、是否通过、失败原因、改进建议。

3. 判定标准：
- 文件上传双标书后必须进入 TENDER_REVIEW。
- 高危样本不应大量落成 LOW 且无证据。
- 合规样本不得被武断判成 HIGH。
- 灰度样本若证据不足，应明确表达不确定性并建议人工复核。

4. 输出格式：
- 先输出总览表。
- 再输出失败用例详情。
- 最后输出问题归类：路由问题、误报问题、漏报问题、证据链问题、稳定性问题。

5. 样本来源：
- 使用文档《标书审查测试用例与AI执行指引.md》中的样本路径与用例表执行。
```

## 11. 本轮建议执行顺序

建议按照以下顺序跑，效率最高：

1. 先跑 `API-01 ~ API-06`，确认接口和协议稳定。
2. 再跑高危样本中的强规则组：`TR-H01、TR-H02、TR-H04、TR-H05、TR-H06、TR-H13、TR-H14`。
3. 再跑历史弱项：`TR-H07 ~ TR-H12`。
4. 最后跑误报与灰度组：`TR-N01、TR-N02、TR-G01、TR-G02、TR-G03`。

如果时间有限，最低保留集建议为：

- `API-02`
- `API-03`
- `TR-H01`
- `TR-H02`

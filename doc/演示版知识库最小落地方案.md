# 演示版知识库最小落地方案

## Project: Drug-Agent 演示版知识库功能

**Goal**: 基于当前项目已经实现的 RAG 基础能力，快速落地一个“可演示、可上传知识、可提问命中知识片段、前后端都能看得见”的最小知识库版本。  
**Timeline**: 3-5 天  
**Team**: 默认 1 人完成  
**Constraints**:

- 当前项目已有 RAG 后端雏形，但业务接入和前端承接较弱
- 当前知识库前端页面大多还是静态占位
- 本次目标是演示版，不追求生产级治理和云端部署
- 必须尽量复用现有接口与代码结构，避免大改

---

## 1. 方案定位

本方案不是做“正式知识库平台”，而是做一个**最小可演示知识库闭环**。

演示目标是让你可以清晰展示这件事：

```text
我上传一段知识
-> 系统把它存进知识库
-> 我提一个问题
-> AI 或 RAG 服务能命中这段知识
-> 前端能看到回答和引用来源
```

也就是说，这一版只追求 4 个最小结果：

1. 能录入知识  
2. 能查询知识  
3. 能返回引用片段  
4. 前端能看见整个过程

## 2. 基于当前项目已有能力的判断

你当前项目已经具备以下可以直接复用的基础：

### 后端已具备

- `KnowledgeController`：已有知识入库和问答接口
- `KnowledgeIngestService`：支持文本切片、embedding、入库
- `KnowledgeRagService`：支持候选过滤、关键词检索、向量检索、融合排序、门控决策
- `VectorStoreConfig`：已有 `SimpleVectorStore`
- `KnowledgeChunkIndex`：已有本地关键词索引能力

### 前端已具备

- `KnowledgeBaseView.vue`：已有知识库页面入口，但目前还是静态展示
- 工作台已有对话区，可作为后续“引用知识”演示入口
- 已有本地状态工具，可暂时承接简单知识条目列表

### 当前不足

- 没有一个真正可用的知识录入页面
- 没有知识列表页
- 没有调用 `/agent/knowledge/ask` 的前端页面
- 没有把 citations 清晰展示出来
- 没有最小的演示工作流

所以这次不是重做一套 RAG，而是**把已有能力包装成一个能演示的产品功能**。

## 4. 演示版的产品形态

建议把“知识库”页面设计成一个最小工作台，而不是静态说明页。

推荐页面结构：

```text
左侧：
  知识录入区
  已录入知识列表

右侧：
  知识问答区
  回答结果
  引用来源
```

这样你演示时非常自然：

1. 左边录入一段知识
2. 点击保存
3. 右边输入一个问题
4. 立即看到回答和引用

这比做成复杂管理后台更适合当前阶段。

## Phase 1: 打通最小后端闭环 (Day 1)

### 目标

确保知识入库和 RAG 问答接口可稳定用于前端演示。

### 任务

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 校验 `/agent/knowledge/ingest/text` 接口 | 2h | 你 | - | 可正确入库文本 |
| 校验 `/agent/knowledge/ask` 接口 | 2h | 你 | 入库可用 | 可返回 answer + citations |
| 补充最小异常提示 | 2h | 你 | 上两项 | 空内容、空 orgId 等错误可读 |
| 增加启动时知识缓存说明 | 1h | 你 | - | 知道演示数据是否会保留 |

### 怎么实现

当前接口已经有：

- `POST /agent/knowledge/ingest/text`
- `POST /agent/knowledge/ask`

所以第一阶段的工作不是新建接口，而是先确认这两个接口在本地能跑通。

建议你用固定演示数据验证：

#### 入库请求

```json
{
  "title": "高血压用药规范",
  "content": "高血压患者服用降压药时应遵医嘱，不可自行停药。常见降压药包括钙通道阻滞剂、ACEI、ARB 等。",
  "scene": "general",
  "subScene": "drug_guideline",
  "docType": "policy",
  "orgId": "demo-org",
  "topicTags": ["高血压", "降压药", "用药规范"],
  "sourceId": "demo-guideline-001",
  "version": "v1"
}
```

#### 问答请求

```json
{
  "question": "高血压患者能不能自行停降压药？",
  "scene": "general",
  "subScene": "drug_guideline",
  "docType": "policy",
  "orgId": "demo-org",
  "topicTags": ["高血压"],
  "topK": 3,
  "sessionId": "demo-session"
}
```

### 关键注意点

- 这一版统一使用固定 `orgId=demo-org`
- 这样前后端最容易对齐
- 演示时不要引入复杂多租户逻辑

## Phase 3: 建立最小演示话术和工作流 (Day 3-4)

### 目标

把知识库能力从“有页面”变成“能讲得清楚”。

### 任务

| Task | Effort | Owner | Depends On | Done Criteria |
|------|--------|-------|------------|---------------|
| 准备 2-3 条演示知识文本 | 2h | 你 | Phase 2 | 有稳定命中样本 |
| 准备 3-5 个演示问题 | 2h | 你 | 上一项 | 可以命中引用 |
| 调整问答页文案 | 2h | 你 | 页面完成 | 用户知道怎么操作 |

### 推荐演示素材

建议准备 3 类知识：

1. 政策规范类
- 如药品使用规范、处方审核要求

2. 案例经验类
- 如历史审查案例、违规处理经验

3. 内部准则类
- 如“某类问题建议人工复核”的内部规则说明

### 推荐演示动作

#### 演示 1：录入一条知识

输入：

- 标题：高血压用药规范
- 内容：高血压患者不可自行停用降压药……

展示：

- 提示“已成功入库”
- 左侧列表出现该知识

#### 演示 2：立即提问

提问：

- “高血压患者能不能自己停药？”

展示：

- 回答明确引用知识内容
- citations 显示来源标题和片段

#### 演示 3：再录入一条案例

再问：

- “如果患者擅自停药，系统通常建议什么？”

展示：

- 新回答命中新知识或多条知识

## 5. 技术实现细节建议

## 后端部分

### 保持当前技术方案不变

演示版建议继续使用：

- `SimpleVectorStore`
- `KnowledgeChunkIndex`
- 当前 `KnowledgeIngestService`
- 当前 `KnowledgeRagService`

原因：

- 改动最小
- 不需要新装数据库
- 最快出效果

### 后端只做最小增强

建议增强的点：

#### 5.1 入库返回更多可用信息

当前入库接口只返回 `chunkCount`。

建议演示版可增加返回：

- `sourceId`
- `title`
- `scene`
- `chunkCount`

这样前端更容易展示成功结果。

#### 5.2 问答响应保留 citations

这一点当前已经有了，建议不要删减。

#### 5.3 增加简单日志

建议在知识入库和问答时打印：

- `sourceId`
- `orgId`
- `chunkCount`
- `question`
- `selected citations count`

方便演示和排错。

## 前端部分

### 推荐页面布局

建议将知识库页改成双栏：

#### 左栏

- 知识录入表单
- 已录入知识列表

#### 右栏

- 问题输入框
- 问答结果
- 引用来源列表

### 交互建议

- 入库成功后清空表单
- 自动把新知识加到左栏列表
- 提问成功后滚动到结果区
- 引用来源支持折叠/展开

### 文案建议

不要说：

- 长期记忆大脑
- 多模态知识治理平台

演示版建议说：

- 本地知识库演示
- 文本知识录入
- 检索增强问答
- 引用片段展示

这样更符合当前能力边界。

## 7. 风险与规避

| 风险 | Impact | Probability | Mitigation |
|---|---|---|---|
| 本地知识重启丢失 | 中 | 中 | 演示前固定重新导入样本，或确认 `vector_store.json` 是否持久化 |
| 前端没有知识列表接口 | 低 | 高 | 演示版先用前端本地状态承接 |
| citations 不明显，用户感知不到 RAG | 高 | 中 | 在结果区突出“引用来源” |
| 问题问得太发散导致检索不稳 | 中 | 高 | 预先准备稳定演示问题 |
| 想一次做成正式知识库 | 高 | 高 | 明确本方案是演示版，不做治理系统 |

## 9. 验收标准

当以下条件满足时，可认为演示版知识库落地完成：

- 可以在前端录入一段知识文本
- 后端成功切片并入库
- 前端能针对问题调用 RAG 问答接口
- 页面能展示回答、决策、风险等级
- 页面能展示至少一条 citation
- 可以完整演示“录入 -> 提问 -> 命中”

## 10. 最终建议

这一版最重要的，不是把知识库做复杂，而是：

- 把已有后端能力真正变成前端可见功能
- 把 citations 展示出来
- 让外部一眼看懂“上传知识后，系统真的会用这段知识回答”

如果这个最小闭环成立，你后面再升级到：

- 文件上传入库
- PostgreSQL + pgvector
- workflow 内部接入 RAG
- 知识治理后台

都会顺很多。

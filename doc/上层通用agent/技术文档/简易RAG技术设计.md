# 简易RAG技术设计

## 1. 文档目标

本文档用于为当前项目定义一版简单、清晰、可快速落地的 RAG 技术方案。

这版方案的目标不是一步到位做复杂检索平台，而是先收敛出一条稳定主链路，让系统具备下面这些基础能力：

- 支持上传业务文档进入知识库
- 支持按问题检索相关知识片段
- 支持基于证据生成回答
- 支持返回引用信息
- 支持后续平滑扩展到更复杂的检索与重排能力

本文档强调“先收敛主链路，再逐步增强”，避免在当前阶段同时并行多套 RAG 方案，导致职责混乱。

---

## 2. 设计目标

当前项目是医药监管方向的上层通用 Agent，不是一个纯通用问答机器人。

因此，RAG 的目标不应只是“查到一点相关文本”，而应该服务于业务 Agent 的整体链路，重点支持：

1. 知识补充  
   当用户提问涉及制度、规范、案例、合同条款、审查要求时，系统可以通过检索补足模型知识盲区。

2. 可解释回答  
   回答不能只给自然语言结论，还要尽量带上引用来源和证据片段。

3. 业务场景过滤  
   检索不能直接在全库裸搜，而应具备基础场景过滤能力，例如：
   - `scene`
   - `subScene`
   - `docType`
   - `orgId`

4. 可持续演进  
   当前先做简易版，后续再逐步补：
   - 混合检索
   - 重排
   - 多路召回
   - 更细颗粒度证据组织

---

## 3. 总体方案

本项目的简易 RAG 采用最小闭环设计：

```text
上传文档
-> 文本提取
-> chunk 切分
-> embedding
-> 向量库存储

用户提问
-> query embedding
-> 检索 top-k chunk
-> 拼装上下文
-> 交给模型回答
-> 返回答案 + 引用
```

如果结合业务系统实际使用场景，推荐再补上一层业务过滤，形成下面这条更完整的主链路：

```text
上传文档
-> 文本提取
-> 结构化切块
-> embedding
-> 连同 metadata 写入向量库

用户提问
-> 按 orgId / scene / subScene / docType 做范围过滤
-> query embedding
-> 向量检索 top-k
-> 拼装证据上下文
-> LLM 基于证据回答
-> 返回 answer + citations + decision
```

这就是当前项目推荐收敛的简易 RAG 主链路。

## 4. 核心设计原则

### 4.1 只保留一条知识检索主链路

RAG 在当前阶段应收敛为“知识检索增强回答”这一类能力。

不要把下面两类逻辑混在一起：

- 基于知识块召回的检索型 RAG
- 基于 query/focus 关键词打分的策略型判断

前者是知识检索，后者更像业务规则辅助判断。

如果两者长期并列存在，容易导致：

- 主入口不清楚
- 输出证据来源不清楚
- 维护成本增加
- 后续场景接入方式不一致

因此本设计中，RAG 默认指“知识检索型 RAG”。

### 4.2 检索层只负责找证据，不直接承担完整业务决策

简易 RAG 的主要职责是：

- 找到相关知识片段
- 形成可消费的证据上下文
- 为模型回答提供依据

它不应该直接替代：

- 场景路由
- Workflow 执行
- 业务规则命中
- 风险融合

也就是说，RAG 是增强层，不是总业务引擎。

### 4.3 证据链要天然可返回

只返回一段回答是不够的。

RAG 输出至少应该具备：

- `answer`
- `citations`
- `decision`
- `reason`

这样后续前端、工作台和审查报告层都更容易消费。

### 4.4 优先使用 metadata 做范围收敛

在医药监管类场景中，直接对全库做裸向量检索风险较高。

因此建议最少支持以下 metadata：

- `orgId`
- `scene`
- `subScene`
- `docType`
- `sourceId`
- `sourceTitle`
- `chunkId`
- `chunkIndex`

其中：

- `orgId` 建议作为硬过滤条件
- `scene / subScene / docType` 建议作为业务范围过滤条件

## 5. 入库链路设计

### 5.1 主流程

文档入库链路如下：

```text
上传文档
-> 文本提取
-> 结构化清洗
-> chunk 切分
-> 生成 chunk metadata
-> embedding
-> 写入向量库
```

### 5.2 文本提取

文档上传后，先做统一文本提取。

根据当前项目情况，可以优先支持：

- `docx`
- `doc`
- `md`
- 纯文本

文本提取阶段的职责仅包括：

- 提取可用文本
- 做基础清洗
- 保留源文档标识

不要在这个阶段做复杂业务判断。

### 5.3 chunk 切分

简易版建议采用“结构优先，长度兜底”的切分方式。

推荐规则：

1. 优先按标题、章节、段落切
2. 若单个段落过长，再按固定长度切分
3. 相邻 chunk 允许少量 overlap

不建议一开始只用纯字符硬切，因为这会导致：

- 引用片段语义不完整
- 回答可解释性差
- 章节边界丢失

建议的简化参数：

- `chunkSize`: 600 ~ 1000 字符
- `overlap`: 80 ~ 150 字符

### 5.4 metadata 设计

每个 chunk 入库时建议写入以下 metadata：

```json
{
  "orgId": "xxx",
  "scene": "tender_review",
  "subScene": "general",
  "docType": "regulation",
  "sourceId": "DOC-001",
  "sourceTitle": "招标审查管理办法",
  "chunkId": "DOC-001-0",
  "chunkIndex": 0
}
```

如果后续文档结构更稳定，还可以继续补：

- `sectionTitle`
- `pageNo`
- `paragraphNo`
- `version`
- `createdAt`

### 5.5 向量库存储

当前简易版设计建议以向量库作为检索主存储。

也就是说：

- 入库后，检索主入口应以向量库查询为准
- 本地附加索引如果存在，应视为辅助能力，而不是另一个真相源

设计原则是：

不要形成“向量库存了一份，本地索引又存了一份，查询时再绕开向量库”的双轨结构。

## 6. 查询链路设计

### 6.1 主流程

用户提问后的查询链路如下：

```text
接收问题
-> 构建查询请求
-> metadata 过滤
-> query embedding
-> 向量检索 top-k
-> 证据片段整理
-> 拼装 Prompt
-> 调用 LLM 生成回答
-> 返回 answer + citations + decision
```

### 6.2 查询请求结构

建议统一定义一个查询请求对象，至少包含：

- `question`
- `orgId`
- `scene`
- `subScene`
- `docType`
- `topK`

示例：

```json
{
  "question": "这份条款是否存在明显合规风险？",
  "orgId": "org-001",
  "scene": "contract_precheck",
  "subScene": "general",
  "docType": "contract",
  "topK": 5
}
```

### 6.3 过滤策略

简易版建议：

- `orgId`：硬过滤
- `scene`：优先过滤
- `subScene`：有值时再过滤
- `docType`：有值时再过滤

这里要特别注意：

`orgId` 缺失时，不建议静默降级到默认租户，而应该：

- 直接报错
或
- 返回需要补充上下文

因为医药监管类业务对数据隔离要求较高。

### 6.4 top-k 检索

简易版可以直接使用向量相似度检索 `top-k`。

建议默认值：

- `topK = 5`

不建议一开始取太大，否则会导致：

- Prompt 太长
- 噪音变多
- 模型回答不聚焦

### 6.5 上下文拼装

检索完成后，不建议把片段直接裸拼给模型。

建议统一组装成下面这种结构：

```text
问题：
{question}

检索证据：
[1] 来源：{sourceTitle}
内容：{snippet1}

[2] 来源：{sourceTitle}
内容：{snippet2}

要求：
1. 只能基于以上证据回答
2. 如果证据不足，要明确说明
3. 输出时尽量引用对应来源
```

这种写法的价值是：

- 让模型知道哪些是证据
- 限制自由发挥
- 更容易在回答中保留引用意识

### 6.6 回答策略

简易版推荐采用“证据约束式回答”。

即模型被要求：

- 优先基于检索证据回答
- 证据不足时明确说明
- 尽量不要脱离证据做过强推断

这比单纯把 chunk 拼进去再让模型自由发挥，更适合当前项目。

---

## 7. 输出结构设计

简易版 RAG 建议返回统一结构：

```json
{
  "decision": "ANSWERED",
  "reason": "HIT",
  "answer": "基于检索证据，当前条款存在……",
  "citations": [
    {
      "chunkId": "DOC-001-0",
      "sourceId": "DOC-001",
      "sourceTitle": "招标审查管理办法",
      "snippet": "......",
      "score": 0.87
    }
  ]
}
```

其中：

- `decision`
  - `ANSWERED`
  - `NO_HIT`
  - `NEED_HUMAN_REVIEW`

- `reason`
  - `HIT`
  - `NO_CANDIDATE`
  - `LOW_CONFIDENCE`
  - `MISSING_CONTEXT`

这样的好处是：

- 前端可以直接展示回答与引用
- Workflow 可以判断后续是否继续执行
- 会话层可以记录结构化检索结果

## 8. 分层职责设计

结合本项目整体架构，简易 RAG 建议按下面分层理解。

### 8.1 IngestService

职责：

- 文本切块
- metadata 构造
- embedding
- 写入向量库

不负责：

- 前端会话处理
- 最终回答生成

### 8.2 RagService

职责：

- 接收查询请求
- 做 metadata 过滤
- 做向量检索
- 拼装证据
- 调用模型生成回答
- 返回统一检索结果

不负责：

- 场景路由
- Workflow 执行
- 业务规则决策

### 8.3 Adapter / Facade

如果某些 Workflow 需要接入 RAG，可以通过适配层对接。

适配层职责：

- 把业务上下文转换成 RAG 查询请求
- 把 RAG 返回结果转换成 Workflow 可消费结构

它不应该在中间夹杂新的检索逻辑。

---

## 9. 与当前项目的关系

当前项目里已经存在一部分 RAG 相关代码，但整体上还有收敛空间。

本设计建议后续按以下方向统一：

1. 明确“知识检索型 RAG”作为主链路
2. 统一入库与查询的数据真相源
3. 将 query/focus 关键词打分逻辑从 RAG 主链路中解耦
4. 优先保留简易向量检索版本，后续再补混合检索

换句话说：

先把主链路跑直，再考虑增强，不要在当前阶段同时维护多套概念相近但职责不同的 RAG 方案。

---

## 10. MVP 落地建议

如果按最小可用版本推进，建议分三步落地。

### 第一步：收敛入库主链路

完成：

- 文档文本提取
- chunk 切分
- embedding
- metadata 写入
- 向量库存储

### 第二步：收敛查询主链路

完成：

- query embedding
- 按 metadata 过滤
- top-k 检索
- 证据上下文拼装
- LLM 生成回答
- 返回 answer + citations + decision

### 第三步：接入业务场景

完成：

- 提供统一 `RagService` 入口
- 在需要的 Workflow 或场景服务中通过 Adapter 接入
- 逐步让前端支持显示引用与检索状态

---

## 11. 后续演进方向

在简易版稳定后，可以按优先级逐步增强：

1. 增加关键词召回，形成混合检索
2. 增加 rerank 层，提高 top-k 质量
3. 支持更细粒度结构化切块
4. 支持按章节、页码、段落返回引用
5. 支持多知识源联合检索
6. 支持检索 trace 和命中解释输出

这些能力都可以在不推翻当前简易方案的前提下逐步加上。

---

## 12. 结论

本项目当前最适合的 RAG 方案，不是复杂多路并行的检索架构，而是一条清晰、稳定、可解释的简易主链路：

```text
文档入库
-> 文本提取
-> chunk 切分
-> embedding
-> 向量库存储

用户提问
-> metadata 过滤
-> query embedding
-> 向量检索 top-k
-> 拼装证据上下文
-> LLM 基于证据回答
-> 返回答案与引用
```

这条链路的最大价值，不是“看起来高级”，而是：

- 主流程清楚
- 职责边界清楚
- 可快速实现
- 可逐步增强

对于当前项目阶段，这是一条更适合工程化落地的路线。

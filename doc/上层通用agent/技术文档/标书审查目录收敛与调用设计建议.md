# 标书审查目录收敛与调用设计建议

## 1. 文档目标

本文用于收敛 `com.liang.drugagent.scene.tender_review` 目录的职责边界，并明确：

- 标书审查场景代码应如何分层
- 通用层应依赖哪个场景暴露入口
- `Workflow` 应由谁调用，不应由谁调用
- Day 2 到后续迭代阶段的推荐演进路径

目标不是一次性做过度抽象，而是先把标书审查场景整理成：

- 边界清晰
- 对通用层暴露入口稳定
- 场景内演进成本低
- 后续扩展合同、风险预警时可复用同一接入模式

---

## 2. 当前主要问题

结合现有代码，标书审查目录已经聚集了大部分场景能力，这是正确方向；但当前还存在几个典型问题：

### 2.1 通用层与场景层之间缺少稳定入口

当前通用层主入口是：

- `AgentController`
- `AgentChatService`
- `AgentSceneService`

但标书场景虽然已经有：

- `TenderReviewToolOrchestrator`
- `ReviewTenderTool`
- `TenderReviewWorkflow`

通用层仍然没有一个明确、稳定、唯一的“场景服务入口”可以调用。

结果就是：

- 通用层容易直接碰 `Workflow`
- 通用层容易自己拼装 `TenderReviewData`
- 场景接入逻辑分散，不利于后续收敛

### 2.2 场景目录内部存在职责接近的类

当前场景目录中同时存在：

- `tool/ReviewTenderTool`
- `service/ReviewTenderToolService`

这两个类从命名上看都像“标书工具执行入口”，容易造成职责重叠。

类似问题如果继续累积，会让目录虽然都放在 `scene/tender_review` 下，但内部边界还是模糊的。

### 2.3 Workflow 调用边界还不够稳定

当前理想架构是：

`AgentChatService -> AgentRouteService -> 场景入口 -> Orchestrator -> Tool -> Workflow`

但如果没有明确限制，后面很容易演变成：

- 有的地方调 `Orchestrator`
- 有的地方调 `Tool`
- 有的地方直接调 `Workflow`

这样会导致：

- 标书场景入口不唯一
- 数据准备逻辑四处分散
- 返回结构难以统一

---

## 3. 总体设计原则

标书审查场景建议坚持以下原则：

### 3.1 场景专属能力尽量留在场景目录

凡是“只对标书审查成立”的类，原则上都放在：

`com.liang.drugagent.scene.tender_review`

包括但不限于：

- 标书数据准备
- 标书文件解析
- 标书规则执行
- 豁免判断
- 风险融合
- 报告生成
- 证据组装
- Tool 编排

### 3.2 通用层只依赖场景暴露入口，不依赖场景内部细节

通用层应该知道：

- 什么时候进入 `TENDER_REVIEW`
- 调哪个场景服务入口
- 拿到统一的 `AgentExecutionResult`

通用层不应该知道：

- `TenderReviewData` 如何构建
- `ReviewTenderToolReq` 如何拼装
- `Workflow` 具体执行了哪些规则

### 3.3 Workflow 作为场景内部确定性引擎，不直接暴露给通用层

`TenderReviewWorkflow` 的职责应保持为：

- 确定性执行主链路
- 规则命中
- 豁免处理
- 风险融合
- 证据组装
- 报告生成

不建议让通用层直接调用 `Workflow`。

原因很简单：

- 一旦通用层直接依赖 `Workflow`，后续就会把场景数据准备和结果包装也搬到通用层
- `Workflow` 就会被迫承担越来越多不属于它的职责

---

## 4. 推荐目录收敛方案

建议保留 `scene/tender_review` 作为标书审查场景主目录，并在语义上收敛为以下几层。

### 4.1 推荐目录结构

```text
scene/tender_review
├── facade/                 # 对通用层暴露的唯一场景入口
├── orchestrator/           # 场景编排
├── preparation/            # 场景数据准备
├── tool/                   # Tool 调用入口
├── workflow/               # 确定性业务引擎
├── service/                # 场景内部领域服务
├── support/                # 规则引擎/解析器/执行器/装配器/存储支撑
├── model/                  # 场景模型
└── ...
```

### 4.2 各层职责建议

#### `facade/`

建议新增一个对通用层暴露的入口类，例如：

- `TenderReviewSceneService`

职责：

- 接收通用层请求
- 调用 `PreparationService` 补齐场景数据
- 调用 `TenderReviewToolOrchestrator`
- 返回统一 `AgentExecutionResult`

这是通用层唯一应依赖的标书场景服务。

#### `preparation/`

建议新增：

- `TenderReviewPreparationService`

职责：

- 从 `AgentChatReq`、`AgentChatContext`、上传文件、metadata 中准备 `TenderReviewData`
- 补齐文档、caseId、compareScopes 等场景所需数据
- 对缺文件、文件不足、metadata 不完整等情况给出明确失败结果或空值判断

这部分不应放在 `AgentSceneService`。

#### `orchestrator/`

保留：

- `TenderReviewToolOrchestrator`

职责：

- 组织 Tool 调用
- 组织结果润色
- 统一产出 `AgentExecutionResult`

这里仍然是标书场景的编排核心。

#### `tool/`

保留：

- `ReviewTenderTool`
- `ReviewTenderToolRequest`
- `ReviewTenderToolResult`

职责：

- 参数校验
- 请求转换
- 调用 `Workflow`
- 返回结构化工具结果

#### `workflow/`

保留：

- `TenderReviewWorkflow`

职责：

- 执行标书审查确定性主链路

它是场景内部引擎，不直接面向通用层。

#### `service/`

这里保留真正的场景内服务，例如：

- `RiskFusionService`
- `EvidenceAssemblerService`
- `ReportGenerationService`
- `TenderDocumentParseService`
- `TenderCaseService`

这些类仍然应放在场景目录内。

### 4.3 建议收敛或调整的类

#### `ReviewTenderToolService`

建议评估是否删除或并入 `ReviewTenderTool` / `TenderReviewSceneService`。

如果它的职责是：

- 接请求
- 构建上下文
- 调 workflow

那么它与 `ReviewTenderTool` 很可能已经重复。

推荐原则：

- 对外作为 Tool 入口的，只保留一个 `ReviewTenderTool`
- 对通用层暴露的，只保留一个 `TenderReviewSceneService`

不要同时保留多个“看起来都是入口”的类。

#### `TaskCardService`

如果它服务的是标书审查任务看板，且强绑定标书场景，放在场景目录可以接受。

如果未来会被合同预审、风险预警共用，则应迁移到更通用的模块。

## 5. 通用层应依赖哪个 service

建议在标书场景目录中明确暴露一个 service 给通用层调用：

- `TenderReviewSceneService`

推荐放置位置：

- `com.liang.drugagent.scene.tender_review.facade.TenderReviewSceneService`

推荐接口形态：

```java
public interface TenderReviewSceneService {

    AgentExecutionResult execute(AgentChatContext context, AgentChatReq req);
}
```

或直接类实现：

```java
@Service
public class TenderReviewSceneService {

    public AgentExecutionResult execute(AgentChatContext context, AgentChatReq req) {
        ...
    }
}
```

### 5.1 为什么暴露这个 service，而不是直接暴露 Workflow

因为通用层需要的不是“规则引擎调用能力”，而是“一个完整的标书场景执行入口”。

这个入口至少要覆盖：

1. 场景数据准备
2. 场景参数校验
3. 编排执行
4. 错误兜底
5. 返回统一结果

`Workflow` 本身不适合作为这个入口。

### 5.2 为什么不直接让通用层调用 Orchestrator

从工程上讲，通用层直接调 `Orchestrator` 也能跑。

但长期建议仍然增加一层 `TenderReviewSceneService`，原因是它可以吸收通用层与场景层之间的适配逻辑，例如：

- 从请求里补场景数据
- 做场景级参数兜底
- 处理“有场景意图但无附件”的特殊提示
- 后续接入埋点、审计、任务记录

这样 `TenderReviewToolOrchestrator` 就能专注于“工具编排”，不用再承接入口适配杂务。

---

## 6. 推荐调用链路

建议将调用链路固定为：

```text
AgentController
-> AgentChatService
-> AgentRouteService
-> AgentSceneService
-> TenderReviewSceneService
-> TenderReviewPreparationService
-> TenderReviewToolOrchestrator
-> ReviewTenderTool
-> TenderReviewWorkflow
```

其中：

- `AgentRouteService` 负责“是不是 TENDER_REVIEW”
- `AgentSceneService` 负责“该把请求分发给哪个场景入口”
- `TenderReviewSceneService` 负责“标书场景怎么接住这次请求”
- `TenderReviewToolOrchestrator` 负责“场景内部怎么编排 Tool”
- `ReviewTenderTool` 负责“Tool 如何调用 Workflow”
- `TenderReviewWorkflow` 负责“规则链路如何执行”

---

## 7. Workflow 调用逻辑怎么设计更好

这是本次收敛里最关键的问题。

我的建议是：

### 7.1 Workflow 不直接给通用层调用

通用层禁止直接调用：

- `TenderReviewWorkflow`

否则后面很容易出现：

- 通用层自己构建 `TenderReviewData`
- 通用层自己决定是否生成报告
- 通用层自己拼 `WorkflowResult -> AgentExecutionResult`

这会让场景边界重新散掉。

### 7.2 Workflow 由 Tool 调用，而不是由 AgentSceneService 调用

推荐固定关系：

```text
TenderReviewToolOrchestrator -> ReviewTenderTool -> TenderReviewWorkflow
```

原因：

- Tool 更适合做参数校验和请求整理
- Workflow 更适合做确定性执行业务
- Orchestrator 更适合做 LLM 编排和最终回复组织

这是你们当前目录最顺的一条链。

### 7.3 场景 facade 不直接碰 Workflow 细节

`TenderReviewSceneService` 的角色应该是：

- 组装场景请求
- 调 Orchestrator
- 统一接收返回结果

而不是：

- 自己判断该不该调哪个 executor
- 自己调 workflow 的内部方法
- 自己拼报告

### 7.4 推荐的伪代码

```java
@Service
@RequiredArgsConstructor
public class TenderReviewSceneService {

    private final TenderReviewPreparationService preparationService;
    private final TenderReviewToolOrchestrator orchestrator;

    public AgentExecutionResult execute(AgentChatContext context, AgentChatReq req) {
        TenderReviewData data = preparationService.prepare(context, req);
        if (data == null || data.getDocuments() == null || data.getDocuments().size() < 2) {
            return AgentExecutionResult.failure(SceneEnum.TENDER_REVIEW, "至少需要两份标书文件才能进行围标审查");
        }
        return orchestrator.orchestrate(data, req.getQuery(), context);
    }
}
```

然后通用层：

```java
switch (decision.getScene()) {
    case TENDER_REVIEW:
        return tenderReviewSceneService.execute(context, req);
    default:
        return generalChat(...);
}
```

这个设计的优点是：

- 通用层不感知标书内部结构
- 场景入口稳定
- Workflow 不越层暴露
- 后续合同预审、风险预警可照样复制同一模式

## 8. Day 2 阶段的最小落地建议

如果当前目标是优先满足 Day 2 验收，而不是做大重构，建议按下面顺序最小收敛：

### 8.1 新增 `TenderReviewSceneService`

作为通用层唯一调用入口。

### 8.2 新增 `TenderReviewPreparationService`

把下面逻辑从通用层隔离出去：

- 从 metadata 读取 `documents` / `tenderDocuments`
- 必要时补 `caseId`
- 组装 `TenderReviewData`

### 8.3 `AgentSceneService` 只保留“判断 + 分发”

只做：

- 根据 `AgentRouteService` 判断是否 `TENDER_REVIEW`
- 路由到 `TenderReviewSceneService`

不要在这里拼 `TenderReviewData`。

### 8.4 收敛重复入口

优先评估并清理：

- `ReviewTenderToolService`

尽量保证标书场景入口只有三层：

1. `TenderReviewSceneService`
2. `TenderReviewToolOrchestrator`
3. `ReviewTenderTool`

不要出现第四个、第五个“也像入口”的类。

## 9. 推荐的最终边界

### 9.1 通用层负责

- 会话管理
- 消息存储
- 路由决策
- 场景分发
- 统一响应包装

### 9.2 标书场景负责

- 场景数据准备
- 工具编排
- 工作流执行
- 风险识别
- 证据与报告生成

### 9.3 明确禁止

- `Controller` 直接调 `TenderReviewWorkflow`
- `AgentChatService` 直接调 `TenderReviewWorkflow`
- `AgentSceneService` 直接拼标书规则细节
- 通用层直接依赖 `ReviewTenderToolReq`

---

## 10. 结论

标书审查场景当前的正确收敛方向不是把场景 service 拆回通用层，而是：

1. 继续把标书专属能力留在 `scene/tender_review`
2. 在场景目录中新增一个对通用层暴露的唯一入口 `TenderReviewSceneService`
3. 由该入口负责调用 `TenderReviewPreparationService`
4. 再进入 `TenderReviewToolOrchestrator -> ReviewTenderTool -> TenderReviewWorkflow`

推荐的一句话原则是：

**通用层只知道“调用标书场景”，但不应该知道“标书场景内部如何工作”。**

这能最大程度保证：

- 目录收敛
- 调用链稳定
- Workflow 不越层
- 后续多场景扩展时保持一致架构

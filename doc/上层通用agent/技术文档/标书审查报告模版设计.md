# 标书审查报告模版设计

> 文档版本：V1.0
> 更新时间：2026-04-10
> 适用场景：标书审查（围标、串标、雷同、异常协同等风险识别）

---

## 1. 背景与目标

当前标书审查结果已经具备一定的结构化字段和 Markdown 报告能力，但最终报告仍存在几个典型问题：

1. 结构化结果与展示文案混在一起，导致报告逻辑层次不稳定。
2. 报告章节较多，但主结论不够靠前，业务方第一眼抓不住重点。
3. 风险项、证据项、豁免项虽然都有输出，但彼此之间缺少“结论 -> 依据 -> 处置”的闭环。
4. 过多“待补充”“系统说明”等占位语会降低正式报告质感。
5. 报告既像系统日志，又像业务结论，缺少正式审查文书应有的表达方式。

本模版的目标不是把报告写得更长，而是把报告写得更稳、更像正式审查结论，做到：

- 先给结论，再给依据
- 先讲重点，再讲明细
- 证据可回溯，判断可解释
- 豁免单列披露，避免误伤
- 输出既能给业务看，也能给后续导出和前端结构化展示复用

## 2. 模版设计原则

### 2.1 报告必须回答的 4 个问题

一份优秀的标书审查报告，必须在前 30 秒内让阅读者看明白：

1. 这批标书整体风险高不高？
2. 最高风险到底是什么？
3. 为什么这样判断？证据在哪？
4. 下一步建议怎么处理？

### 2.2 推荐的报告层次

建议固定为 8 个章节：

1. 报告基本信息
2. 审查结论摘要
3. 审查范围与方法
4. 重点风险清单
5. 重点风险详述
6. 证据链与交叉印证
7. 豁免与不确定性说明
8. 后续处置建议

这个顺序的好处是：

- 业务负责人先看结论和建议
- 复核人员直接下钻风险项和证据
- 监管或审计人员能看到豁免逻辑和边界说明

### 2.3 语言风格约束

报告语言建议统一遵循以下规则：

- 用“审查结论”“风险线索”“证据显示”“建议复核”这类正式表述。
- 不用“我认为”“可能有点像”“感觉存在问题”这类口语。
- 不直接把内部实现词汇暴露给用户，例如“命中数”“权重调整”等，除非有业务解释。
- 不出现没有意义的占位词，例如“待补充”“暂无可展示证据组”。
- 如信息缺失，明确写“当前材料未提供”“现有证据不足以判断”，不要伪造内容。

### 2.4 一份好报告的结构闭环

每个重点风险都应当完整回答：

- 风险是什么
- 异常表现是什么
- 判断依据是什么
- 涉及哪些文档或主体
- 可能带来什么影响
- 建议下一步怎么核查

## 4. 推荐的章节写法

### 4.1 审查结论摘要要短

这一部分建议控制在 4 到 6 行，不能把所有细节都塞进去。

好的写法：

> 本次对 3 份投标文件进行比对审查，综合判定为高风险。主要异常集中在技术方案大段雷同、商务条款表达高度一致以及核心团队履历交叉复用，已形成可回溯证据链，建议进入人工重点复核流程。

不好的写法：

> 本次共命中 12 条规则，其中 4 条经过豁免后降权，3 条高风险，2 条中风险，系统综合打分 87 分……

原因是第一种先告诉阅读者“结论是什么”，第二种更像系统日志。

### 4.2 风险清单要像“问题目录”

风险清单不是明细堆砌，而是一个目录页。每一行只需要回答：

- 风险主题
- 风险等级
- 涉及对象
- 一句话结论
- 最关键的证据编号

不要在表格里塞过长原文。

### 4.3 风险详述要像“结论卡片”

每个风险点建议稳定输出 6 个字段：

1. 涉及对象
2. 异常表现
3. 审查判断
4. 判定依据
5. 影响评估
6. 建议处置

其中“审查判断”建议使用明确句式：

- “现有证据显示，两份标书在技术实施方案上存在超出行业通用表述范围的高度同源特征。”
- “现有证据显示，不同投标主体在商务响应条款中存在异常一致性，具有协同编制嫌疑。”
- “目前证据仅能支持中等强度风险提示，尚不足以单独认定围标行为。”

### 4.4 证据部分要强调“可回溯”

证据展示的重点不是数量多，而是能回到原文。

推荐每个证据组至少包含：

- 证据类型
- 关联风险
- 涉及文档
- 两个关键片段
- 一句交叉印证说明

如果当前系统没有页码或段落号，也不要写“定位信息待补充”，建议改成：

> 当前版本可定位到文档级与片段级，页码级定位待后续增强。

### 4.5 豁免要单列，不要埋在正文里

优秀报告不是只会报风险，也要清楚说明哪些相似内容属于合理重复，例如：

- 法规条文引用
- 招标文件标准格式响应
- 行业通用模板语
- 规范性附件结构一致

这样能显著提升报告可信度，避免“误判一切相似”为风险。

### 4.6 不确定性必须明示

如果存在以下情况，建议在报告中单列说明：

- 上传文件不完整
- 某些分析器降级或未执行
- 证据只支持“疑点提示”，不支持“强结论”
- 外部关联主体信息暂未接入

这是正式报告和“漂亮长文”的关键区别。

## 5. 与当前结构化字段的映射建议

为了方便直接落地到现有代码，推荐优先沿用当前 `ReviewReport`，并按下表映射正文章节。

| 报告章节 | 优先来源字段 | 说明 |
|------|------|------|
| 报告基本信息 | `caseId` `scene` `generatedAt` | 项目名、文档名建议从 `TenderReviewData` 补齐 |
| 审查结论摘要 | `overview.riskLevel` `overview.score` `overview.summary` | 这是首页核心信息 |
| 审查概览 | `overview.documentCount` `rawHitCount` `effectiveHitCount` `exemptionCount` `evidenceGroupCount` | 建议不要只显示内部术语，可转成业务表达 |
| 重点风险清单 | `riskItems` | 每项只保留一条结论和一组证据引用 |
| 重点风险详述 | `riskItems` + `explanations` | `explanations` 更适合做补充说明，不适合直接顶替风险详述 |
| 证据链与交叉印证 | `evidenceGroups` / 证据组装结果 | 最好用组，不建议直接平铺 `evidenceList` |
| 豁免说明 | `exemptionHits` | 建议后续显式进入 `ReviewReport`，避免只在 Markdown 临时渲染 |
| 后续建议 | `recommendedActions` | 建议固定输出 3 到 4 条 |

## 6. 建议补充的字段

如果后续要让报告更稳定，建议在 `ReviewReport` 中逐步补齐以下字段：

```java
private String projectName;
private List<String> documentNames;
private String scopeDescription;
private String overallConclusion;
private String overallAction;
private String coverageText;
private List<ExemptionReportItem> exemptions;
private CoverageInfo coverageInfo;
private UncertaintyInfo uncertaintyInfo;
```

这样做的好处是：

- Markdown 模版只负责渲染，不负责临时拼业务语义
- 前端卡片展示可以直接消费结构化字段
- 后续导出 PDF / Word 时无需再从长文本反向拆数据

## 7. 生成规则建议

为了让最终报告“稳”，建议在生成层加上以下约束：

1. 首页最多展示 3 个重点风险，不要一上来铺满所有命中项。
2. 没有足够证据时，不输出强结论，只输出“疑点提示”。
3. 风险项标题必须业务化，不要直接裸露规则编码作为标题。
4. 所有结论都要能对应到至少 1 组证据或 1 条明确依据。
5. 豁免项必须单列披露，不能只在内部做降权。
6. 不输出“待补充”“未知文档”“暂无证据内容”这类弱质感占位文本。
7. `answer` 建议作为会话摘要版，`report.markdownContent` 作为正式报告版，两者不要完全等同。

---

## 8. 推荐落地顺序

如果后续要把这份模版真正接进现有链路，建议按下面顺序推进：

1. 先按本模版重构 `ReportGenerationService` 的章节顺序和文案风格。
2. 再把“豁免”“覆盖度”“不确定性”从临时字符串拼接升级为结构化字段。
3. 最后再考虑把 Markdown 拼接改成模板引擎，降低维护成本。

---

## 9. 一句话结论

优秀的标书审查报告，不是“把系统跑出来的所有信息都写进去”，而是用稳定、正式、可解释的结构，把最关键的风险结论、证据链和处置建议讲清楚。

# 对话文件保存改造方案

## 1. 背景

当前项目已经接入腾讯云 COS，具备文件上传、下载、删除与元信息落库能力，并已有 `oss_file` 表用于保存文件基础信息。

现阶段需要补上的能力不是“新增一套独立文件系统”，而是：

1. 在原有对话链路中接住用户上传文件
2. 将文件上传到 COS 并保存 `oss_file` 记录
3. 将文件与当前 `sessionId` 关联
4. 让后续对话、记忆、RAG、场景执行都能使用这些文件信息

本次改造目标是“最小闭环、边界清晰、先服务当前对话场景”，不引入过度复杂的数据模型。

---

## 2. 改造目标

本次只解决以下问题：

1. 用户通过 `/agent/submit` 上传文件时，文件不再只是临时存在于请求中
2. 文件必须先保存到 COS，并写入 `oss_file`
3. 文件必须挂到当前对话 `sessionId`
4. `AgentChatService` 后续可基于这些文件记录构建对话上下文
5. 为后续本地知识库 RAG 复用同一张表保留扩展位

不在本次范围内的内容：

1. 文件解析结果持久化
2. 文件分片与向量化
3. 证据链文件归档
4. 文件版本控制
5. 复杂的多业务对象关联表拆分

---

## 3. 当前问题

当前 `/agent/submit` 虽然已经能接收 `MultipartFile[] files`，但在对话主链路中仍存在明显缺口：

1. `AgentController.submit()` 只是把 `files` 塞回 `AgentChatReq`
2. `AgentChatService.chat()` 没有统一处理上传文件保存
3. 文件没有在对话主流程中稳定落库并绑定 `sessionId`
4. 场景层只能直接消费本轮 `MultipartFile[]`，不能稳定复用已上传文件
5. 会话记忆层无法知道“本会话有哪些附件”

这会带来几个问题：

1. 文件只存在于本次请求生命周期，无法回溯
2. 后续多轮对话无法直接引用上一轮已上传文件
3. RAG 或工作流重试时缺少稳定文件入口
4. 文件能力散落在 Controller 和场景准备逻辑中，不利于后续收敛

---

## 4. 设计原则

本次改造遵守仓库 `AGENTS.md` 中的分层约束：

### 4.1 Controller 只接请求，不做上传编排

`AgentController` 只负责：

1. 接收 `reqJson`
2. 接收 `MultipartFile[] files`
3. 组装 `AgentChatReq`
4. 调用 `AgentChatService`

不在 Controller 中直接写：

1. COS 上传细节
2. `oss_file` 落库逻辑
3. 文件与会话绑定逻辑

### 4.2 AgentChatService 负责统一编排，不承载底层存储细节

`AgentChatService` 可以负责：

1. 获取或创建会话
2. 调用文件准备服务保存上传文件
3. 将文件记录补入上下文
4. 再继续场景路由和执行

但不应该直接自己写：

1. 文件转临时文件
2. objectKey 生成细节
3. COS SDK 调用
4. `OssFileMapper.insert(...)` 细节

### 4.3 文件保存动作下沉为通用 Preparation Service

建议新增通用文件准备服务，例如：

- `AgentConversationFileService`
- 或 `ConversationFilePreparationService`

它的职责是：

1. 接收本轮上传文件和 `sessionId`
2. 上传到 COS
3. 写入 `oss_file`
4. 返回本轮上传后的文件上下文

这是“对所有场景都成立”的通用能力，应该作为通用层服务存在，而不是放在某个单一场景里。

---

## 5. 目标表结构约定

当前你已经将表收敛为单表方案，本次方案默认 `oss_file` 结构为：

```sql
CREATE TABLE oss_file (
    id            VARCHAR(36)  NOT NULL COMMENT '文件ID' PRIMARY KEY,
    session_id    VARCHAR(36)  NULL COMMENT '会话ID，RAG文件可为空',
    file_name     VARCHAR(255) NOT NULL COMMENT '原始文件名',
    file_suffix   VARCHAR(50)  NULL COMMENT '文件后缀',
    file_size     BIGINT       NULL COMMENT '文件大小（字节）',
    oss_key       VARCHAR(500) NOT NULL COMMENT 'OSS对象路径',
    file_type     TINYINT      NOT NULL DEFAULT 1 COMMENT '1-对话附件 2-RAG知识库',
    upload_status TINYINT      NOT NULL DEFAULT 1 COMMENT '0-待上传 1-成功 2-失败 3-已删除',
    created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间'
) COMMENT='OSS文件信息表';
```

说明：

1. 本次对话链路只使用 `file_type = 1`
2. RAG 文件上传能力仍可继续复用同一张表，使用 `file_type = 2`
3. 如果代码中仍使用 `ossUrl` 字段命名，需要同步做实体命名收敛，建议统一为 `ossKey`

## 6. 推荐改造后的主链路

### 6.1 对话上传主链路

```text
AgentController.submit
-> AgentChatService.chat
-> AgentSessionService.getOrCreateSession
-> ConversationFilePreparationService.saveUploadedFiles
   -> 校验文件
   -> 生成 objectKey
   -> 上传 COS
   -> 写入 oss_file(session_id=file session id, file_type=1)
   -> 返回 uploadedFiles
-> AgentChatService 构建 AgentChatContext
-> AgentSceneService.decideAndExecute
-> 保存用户消息
-> 保存助手消息
-> 更新 Session 聚合状态
-> 返回 AgentChatResp
```

### 6.2 无文件对话链路

```text
AgentController.chat
-> AgentChatService.chat
-> AgentSessionService.getOrCreateSession
-> 跳过 saveUploadedFiles
-> 构建上下文
-> AgentSceneService.decideAndExecute
-> 回写消息和会话
```

关键点：

1. 文件保存发生在路由前
2. 文件保存完成后，本轮上下文才算完整
3. 路由服务本身不负责上传文件
4. 场景服务消费的是“已保存的文件上下文”，而不是直接管理上传过程

## 7. 类职责改造建议

## 7.1 AgentController

保持轻量，仅保留以下动作：

1. 解析 `reqJson`
2. 将 `MultipartFile[]` 放入 `AgentChatReq`
3. 调用 `agentChatService.chat(req)`

本次原则上不需要把上传逻辑继续堆进 [`AgentController.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/controller/AgentController.java)。

## 7.2 AgentChatService

建议在 [`AgentChatService.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/chat/AgentChatService.java) 中新增一个稳定步骤：

```text
1. 获取或创建 Session
2. 保存本轮上传文件
3. 读取最近消息
4. 构建上下文
5. 场景决策与执行
6. 回写消息
7. 更新会话聚合字段
8. 返回统一响应
```

即把当前 10 步主流程调整为：

```text
1. 获取或创建会话
2. 保存本轮上传文件并获得 fileIds
3. 读取最近消息和摘要，构建上下文
4. 调用 AgentSceneService 执行场景判断与分发
5. 保存用户消息
6. 保存助手消息
7. 更新会话聚合状态
8. 如需要更新标题
9. 如需要更新摘要
10. 返回统一响应
```

建议新增私有方法：

- `prepareConversationFiles(req, sessionId)`
- `mergeFileIds(req, uploadedFiles)`

## 7.3 ConversationFilePreparationService

建议新增通用服务：

`com.liang.drugagent.agent.chat.ConversationFilePreparationService`

建议职责：

1. 接收 `sessionId` 和 `MultipartFile[]`
2. 逐个校验文件名、大小、空文件
3. 生成 `objectKey`
4. 调用 `CosStorageService.uploadFile(...)`
5. 写入 `oss_file`
6. 返回结构化结果

建议返回对象：

- `ConversationFileSaveResult`
- 或直接返回 `List<OssFile>`

建议接口形态：

```java
List<OssFile> saveUploadedFiles(String sessionId, MultipartFile[] files);
```

为了保持最小改造，也可以先不单独抽 `Resp`，直接返回 `List<OssFile>`。

## 7.4 OssFile / OssFileMapper

已有 [`OssFile.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/common/entity/OssFile.java) 和 [`OssFileMapper.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/agent/common/mapper/OssFileMapper.java) 可以直接复用。

本次建议做的调整：

1. 字段命名与数据库结构统一
2. 如果表字段已改为 `oss_key`，实体字段也建议改为 `ossKey`
3. `uploadStatus` 继续表达上传状态，不承载更多业务含义

## 7.5 AgentChatContext

建议增加文件上下文字段，至少满足以下两种消费方式之一：

1. 保存 `fileIds`
2. 保存 `uploadedFiles`

推荐优先级：

1. `fileIds` 作为轻量通用引用
2. `uploadedFiles` 作为本轮运行时增强信息

例如：

```java
private List<String> fileIds;
private List<OssFile> uploadedFiles;
```

这样既能让通用层知道有哪些附件，也方便场景服务按需使用。

## 8. 请求与上下文模型建议

## 8.1 AgentChatReq

当前 [`AgentChatReq.java`](/Users/liangjiajian/Desktop/医药监管AI项目/drug-agent/src/main/java/com/liang/drugagent/controller/domain/request/agent/AgentChatReq.java) 已包含：

1. `List<String> fileIds`
2. `MultipartFile[] files`

这正好适合本次改造：

1. `files` 表示本轮新上传文件
2. `fileIds` 表示前端已选择、已存在的文件引用

因此本次不建议再新增新的请求结构。

## 8.2 推荐语义

建议明确统一以下语义：

1. `files`
   - 本轮 multipart 新上传文件

2. `fileIds`
   - 已经保存过的文件 ID
   - 可来自同一 session 既有附件
   - 可用于多轮对话继续引用历史文件

3. `sessionId`
   - 文件归属的唯一会话主键

## 8.3 本轮处理规则

当 `chat(req)` 收到请求时：

1. 若 `req.files` 为空，则不做文件保存
2. 若 `req.files` 不为空，则先保存文件，得到本轮新增 `uploadedFileIds`
3. 将 `uploadedFileIds` 合并到 `req.fileIds`
4. 后续路由、场景准备、对话上下文统一读取合并后的 `fileIds`

## 9. 对话保存文件的落地流程

### 9.1 文件保存步骤

建议流程：

1. `AgentChatService` 获取真实 `sessionId`
2. 调用 `ConversationFilePreparationService.saveUploadedFiles(sessionId, req.getFiles())`
3. 服务内部逐个处理文件：
   - 校验文件非空
   - 提取后缀
   - 生成 `objectKey`
   - 落临时文件
   - 上传 COS
   - 写 `oss_file`
4. 返回本轮成功保存的文件记录列表
5. 将文件 ID 合并进 `req.fileIds`
6. 再进入对话路由和执行

### 9.2 objectKey 建议

建议统一按会话维度组织对象路径，便于后续回溯和清理：

```text
attachment/{yyyy-MM-dd}/{sessionId}/{uuid}.{suffix}
```

相比当前 `attachment/{date}/{uuid}.{suffix}`，增加 `sessionId` 目录更适合“按会话追踪上传材料”的场景。

### 9.3 写库时机

建议采用“上传成功后再插入成功记录”的方式：

1. COS 上传成功
2. 插入 `oss_file`，`upload_status = 1`

失败场景下：

1. 直接抛异常，由 `AgentChatService` 统一降级
2. 第一阶段不强制保存失败记录

原因：

1. 当前目标是先跑通闭环
2. 失败记录审计不是本次重点
3. 先避免引入过多状态分支

## 10. 对记忆层的影响

本次改造完成后，对话记忆会从“只保存文本消息”扩展为“文本消息 + 文件引用”。

但要注意：

1. 文件元信息不等于文件内容记忆
2. `session.summary` 仍然只维护文本摘要
3. `ChatMessage` 仍以文本消息为主，不建议本次强行扩展成复杂附件消息模型

本次建议的最小落地方式：

1. 文件元信息单独保存在 `oss_file`
2. `ChatMessage.metadata` 中可选记录本轮上传文件 ID 列表
3. `AgentChatContext` 在运行时携带 `fileIds/uploadedFiles`

这样能保证：

1. 记忆层不被一次性改太重
2. 会话维度仍然能查到关联文件
3. 后续如要做“消息级附件”再逐步增强

## 14. 风险与注意事项

### 14.1 不要把文件上传细节塞回 Controller

这是最需要避免的点。

一旦在 `AgentController` 中直接完成：

1. 文件上传
2. `oss_file` 插入
3. 结果拼装

后续 `AgentChatService` 就失去统一编排能力，文件逻辑也无法复用到其他入口。

### 14.2 不要让场景层各自重复上传文件

例如标书审查场景如果直接继续在 `TenderReviewPreparationService` 中单独维护文件上传，会造成：

1. 通用对话与场景对话两套入口
2. 文件记录规则不一致
3. 后续历史文件复用困难

正确做法是：

1. 通用层先完成文件保存
2. 场景层只消费已保存文件引用

### 14.3 不要把 `oss_file` 当成复杂业务主表

本次这张表只做：

1. 存储对象路径
2. 会话关联
3. 文件类型区分
4. 上传状态

不要在这一阶段继续往里塞：

1. 解析结果
2. 向量化状态
3. 业务规则结论
4. 证据链归档信息

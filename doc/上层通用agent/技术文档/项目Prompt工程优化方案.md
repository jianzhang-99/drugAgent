# 项目 Prompt 工程优化方案

> 文档版本：V1.0
> 更新时间：2026-04-02
> 状态：建议落地方案

---

## 1. 文档目标

本文不是讨论“如何写一段更厉害的提示词”，而是面向当前医药监管 Agent 项目，给出一套可落地的 Prompt 工程优化方案。

本方案重点解决以下问题：

1. 当前 Prompt 虽然集中在一个文件夹中，但职责边界不够清晰
2. 不同层级 Prompt 混放后，容易出现“大而全 Prompt”持续膨胀
3. Prompt 缺少统一分类、版本、评测和回滚机制
4. 回答质量优化往往凭感觉推进，缺少稳定的工程闭环

本文目标是让 Prompt 设计和项目分层保持一致，使 Prompt 成为“受控的行为约束层”，而不是“补架构漏洞的临时补丁”。

---

## 2. 当前问题判断

结合当前仓库情况，项目已经存在：

1. 通用 Prompt
2. 场景 Prompt
3. 校验 Prompt
4. RAG Prompt
5. 局部场景内联 Prompt

这说明 Prompt 已经开始承担实际业务能力，但当前还存在几个典型问题。

### 2.1 Prompt 集中存放，不等于职责清晰

把所有 Prompt 放在同一个文件夹，本身没有错。

问题不在“放一起”，而在于：

1. 是否能一眼看出每个 Prompt 属于哪一层
2. 是否能明确这个 Prompt 解决什么问题
3. 是否能判断它的输入输出边界
4. 是否能知道修改它会影响哪条链路

如果这些问题不清晰，后续 Prompt 数量一多，就很容易失控。

### 2.2 通用 System Prompt 容易承载过多职责

当前常见风险是把以下内容全部塞进一个 System Prompt：

1. 角色设定
2. 场景识别
3. 工具调用规则
4. 风险判断标准
5. 输出格式要求
6. 回答风格
7. 降级策略

结果通常是：

1. Prompt 很长，但行为反而不稳定
2. 模型容易职责漂移
3. 中间层结果不适合复用
4. 一次小改动会影响整条链路

### 2.3 Prompt 与代码分层还没有完全对齐

根据项目架构，系统已经明确分层为：

1. AgentChatService / AgentSceneService
2. SceneService
3. Orchestrator
4. Tool
5. Workflow

Prompt 也应该遵循同样的边界。

不能出现：

1. 通用层 Prompt 承担场景内业务规则
2. 最终回复 Prompt 重新推翻 Workflow 结论
3. 语义判断 Prompt 直接生成面向前端的长答案
4. Tool Calling Prompt 兼做路由和最终报告

### 2.4 回答质量优化缺少评测闭环

当前很多项目在优化 Prompt 时，常见做法是：

1. 看一两条回答不满意
2. 直接改 Prompt
3. 主观感觉“好像更好了”

这类做法很容易引入新的副作用，例如：

1. 长回答变得更像报告，但证据约束更弱
2. 场景识别更激进，误路由增加
3. 结构化输出字段更丰富，但解析失败率上升
4. 模型更爱解释，但执行动作变慢

## 3. 优化总原则

本项目 Prompt 工程建议遵循以下原则。

### 3.1 Prompt 必须服从架构，而不是替代架构

Prompt 的职责是：

1. 约束模型行为
2. 补充当前轮任务说明
3. 限定输出格式
4. 指导失败恢复

Prompt 不应该承担：

1. 用自然语言硬编码整个业务流程
2. 替代代码层应有的规则判断
3. 兜底所有上下文缺失问题
4. 让模型自由决定跨层职责

### 3.2 一类 Prompt 只解决一类问题

每个 Prompt 最好只回答一个问题，例如：

1. 这是什么场景
2. 缺哪些参数
3. 这条规则是否命中
4. 结果是否合规
5. 如何向用户组织结果

不要让同一个 Prompt 同时回答五个问题。

### 3.3 中间层尽量结构化，最终层才做自然语言组织

建议约束：

1. 路由层输出 JSON
2. 参数抽取层输出 JSON
3. 规则判断层输出 JSON
4. 结果校验层输出 JSON
5. 最终面向用户的回答层输出 Markdown 或自然语言

这样可以最大化降低链路漂移。

### 3.4 先证据，后结论

这是本项目最核心的 Prompt 原则。

任何涉及风险判断、围标嫌疑、合同风险、预警结论的 Prompt，都应明确：

1. 只能基于已提供证据判断
2. 证据不足时必须降级为“无法判定”或“建议复核”
3. 禁止补造事实
4. 禁止直接给出处罚性结论

### 3.5 Prompt 优化必须可观测、可回滚

每一次 Prompt 变更，都应至少满足：

1. 可定位变更范围
2. 可标记版本
3. 可比较新旧效果
4. 可快速回滚

## 4. 项目级 Prompt 分层方案

建议将全项目 Prompt 按职责拆成 6 层。

### 4.1 L0：基础边界 Prompt

定位：定义通用角色、回答语言、合规边界、禁止事项。

适用范围：

1. 通用对话
2. 各类下游 Prompt 的共享基础约束

典型内容：

1. 永远使用中文回答
2. 如信息不足，明确说明无法判断
3. 不输出越权结论
4. 不编造法规或证据

注意：

这一层只放“全局稳定约束”，不要放场景专属业务规则。

### 4.2 L1：路由与意图识别 Prompt

定位：只负责场景识别，不负责回答用户问题。

适用范围：

1. AgentSceneService 中的 LLM 路由兜底
2. sceneHint 与规则判断不足时的场景补判

输出建议：

```json
{
  "scene": "TENDER_REVIEW | CONTRACT_PRECHECK | RISK_ALERT | DEFAULT | UNKNOWN",
  "confidence": 0.0,
  "reason": "string",
  "requiresClarification": false,
  "clarificationQuestion": ""
}
```

禁止事项：

1. 禁止输出长回答
2. 禁止直接做业务审查
3. 禁止推测不存在的文件内容

### 4.3 L2：参数抽取与澄清 Prompt

定位：只负责识别当前场景缺什么输入，不负责做结论。

适用范围：

1. 标书审查缺文件、缺比较范围、缺关注重点
2. 合同预审缺合同类型、缺审查关注点
3. 风险预警缺时间范围、缺维度、缺对象

输出建议：

```json
{
  "passed": true,
  "missingFields": [],
  "extractedParams": {},
  "requiresClarification": false,
  "clarificationQuestion": ""
}
```

这一层的价值是减少“用户一问，模型直接开始回答”的漂移。

### 4.4 L3：场景执行 Prompt

定位：为 Orchestrator 或场景内 LLM 子任务服务，只做当前任务，不负责最终对用户展示。

典型类型：

1. 标书语义判定 Prompt
2. 合同条款风险识别 Prompt
3. 风险预警异常说明 Prompt
4. Tool Calling 决策 Prompt

输出建议：

1. 优先结构化 JSON
2. 枚举字段固定
3. 支持 `unknown`、`insufficient_evidence`、`review_required`

禁止事项：

1. 禁止输出最终业务结论
2. 禁止越过 Tool / Workflow 自己编业务流程
3. 禁止输出与当前 ruleCode 无关的扩展判断

### 4.5 L4：结果校验 Prompt

定位：校验 Workflow 或场景执行结果是否完整、合规、可展示。

职责：

1. 检查必要字段是否缺失
2. 检查文本与结构化结果是否冲突
3. 检查是否存在越权表述
4. 生成最终展示所需的 summary / warnings

不负责：

1. 重新判案
2. 推翻 Workflow 的结构化结论
3. 编造缺失证据

### 4.6 L5：最终回复组织 Prompt

定位：把已确定的结构化结果组织成用户可读回复。

职责：

1. 面向用户生成简洁、可解释、可复核的回答
2. 按场景组织 summary、answer、复核建议
3. 明确输出中性措辞

这一层最容易被误用。

必须强调：

1. 只做“表达整理”
2. 不做“二次业务推理”

## 5. 建议目录方案

你现在把所有 Prompt 放在一个文件夹里，可以先继续保留“统一入口”，但目录内部必须完成分类。

建议从“一个平铺文件夹”演进为“一个根目录 + 分层子目录”。

### 5.1 推荐结构

```text
src/main/resources/prompts
├── shared/
│   ├── base/
│   │   ├── global-boundary.st
│   │   ├── output-style.st
│   │   └── failure-recovery.st
│   ├── route/
│   │   └── scene-route.st
│   ├── extract/
│   │   └── clarification.st
│   └── validate/
│       └── common-result-validate.st
├── tender_review/
│   ├── route/
│   ├── extract/
│   ├── orchestrator/
│   ├── tool/
│   ├── judge/
│   │   ├── semantic-rule-W-P1.st
│   │   ├── semantic-rule-W-P2.st
│   │   └── ...
│   ├── validate/
│   │   └── tender-review-result-validate.st
│   └── answer/
│       └── tender-review-answer.st
├── contract_precheck/
│   ├── route/
│   ├── extract/
│   ├── judge/
│   ├── validate/
│   └── answer/
└── risk_alert/
    ├── route/
    ├── extract/
    ├── judge/
    ├── validate/
    └── answer/
```

### 5.2 为什么推荐从 Java 常量迁移到资源文件

建议中长期把大段 Prompt 从 Java 常量迁移到 `resources/prompts`，原因如下：

1. 结构更清晰
2. 文本更容易维护
3. 更适合版本化
4. 更方便做 A/B 测试
5. 更容易做 PromptTemplate 渲染

短期内可以允许：

1. 关键 Prompt 仍保留在 Java 中
2. 新增 Prompt 优先放资源文件
3. 逐步将超长 Prompt 迁移出去

## 6. 命名规范

Prompt 文件名和类名都应表达三个信息：

1. 场景
2. 职责
3. 版本或子类型

### 6.1 文件命名建议

推荐格式：

```text
{scene}-{layer}-{purpose}.st
```

例如：

1. `shared-route-scene.st`
2. `tender-review-extract-params.st`
3. `tender-review-judge-semantic-W-P1.st`
4. `tender-review-validate-result.st`
5. `contract-precheck-answer-user.st`

### 6.2 Java 常量命名建议

如果仍保留部分 Java Prompt 常量，建议统一为：

1. `SHARED_ROUTE_SCENE`
2. `TENDER_REVIEW_VALIDATE_RESULT`
3. `TENDER_REVIEW_ANSWER_USER`

避免继续出现：

1. `SystemPrompt` 里混放所有场景
2. `GeneralPrompt` 里同时放聊天和分类
3. 命名看不出层次和用途

## 7. 各场景 Prompt 设计建议

### 7.1 标书审查

标书审查是当前项目最复杂、最适合做 Prompt 分层治理的场景。

建议拆成以下几类：

1. 场景路由 Prompt
2. 参数补齐 Prompt
3. Tool Calling 决策 Prompt
4. 单规则语义判断 Prompt
5. 结果校验 Prompt
6. 最终答复 Prompt

关键约束：

1. 语义判断 Prompt 只判断当前规则是否命中
2. 最终答复 Prompt 不重新做围标结论推理
3. 校验 Prompt 只负责一致性检查和合规措辞修正
4. 正常模板相似、法规引用相似、行业固定表达相似必须明确排除

### 7.2 合同预审

合同预审的 Prompt 重点不在“分析得多复杂”，而在“风险识别维度稳定”。

建议 Prompt 内显式约束：

1. 风险类型枚举固定
2. 每条风险必须带条款片段
3. 每条建议必须对应风险点
4. 没有条款证据不能给出断言

### 7.3 风险预警

风险预警更适合“数据分析 + 异常解释”风格的 Prompt。

建议 Prompt 明确：

1. 区分事实描述与风险解释
2. 区分统计异常与合规结论
3. 指出时间范围、波动幅度、对比基线
4. 数据不足时不输出趋势性结论

## 8. Prompt 模板结构建议

建议所有 Prompt 尽量遵循统一骨架。

### 8.1 通用模板骨架

```text
你是【角色】。

你的唯一任务是：【本轮唯一职责】。

输入信息：
- 场景：
- 用户问题：
- 上下文：
- 结构化数据：
- 已知证据：

判断原则：
1. 只能基于输入信息判断
2. 信息不足时明确说明无法判断
3. 不得补造事实
4. 不得输出超出本层职责的内容

禁止事项：
- ...
- ...

输出要求：
- 只输出 JSON
- 不要输出解释性前后缀

输出 Schema：
{
  ...
}
```

### 8.2 场景内 Prompt 最重要的三段

对于本项目，最重要的三段不是“华丽角色设定”，而是：

1. 职责边界
2. 判断原则
3. 禁止事项

角色设定只要够用即可，不必过度堆砌。

## 9. 当前项目的重点优化动作

结合当前项目现状，建议按以下顺序推进。

### 9.1 第一步：先做 Prompt 分类收口

目标：

1. 梳理现有 Prompt 清单
2. 标记每个 Prompt 属于哪一层
3. 标记调用入口、上下游、输出格式

建议输出一张清单表：

| Prompt 名称 | 所属场景 | 所属层级 | 当前载体 | 调用位置 | 输出类型 |
|------|------|------|------|------|------|

没有这张表，不建议直接大规模重写 Prompt。

### 9.2 第二步：拆掉“大一统 Prompt”

优先识别以下高风险 Prompt：

1. 同时承担路由 + 判断 + 输出组织的 Prompt
2. 同时承担校验 + 再推理的 Prompt
3. 过长且频繁变更的场景主 Prompt

拆分方式：

1. 先保留原有语义内容
2. 再按职责拆为多个小 Prompt
3. 先做到边界清晰，再追求文本优雅

### 9.3 第三步：收紧结构化输出

所有中间层 Prompt 应尽量统一：

1. 只输出 JSON
2. 字段固定
3. 枚举固定
4. 空值处理固定

推荐加入以下字段类型：

1. `status`
2. `confidence`
3. `reason`
4. `requiresClarification`
5. `warnings`
6. `missingFields`

### 9.4 第四步：补误判样例

Prompt 的 few-shot 样例应围绕“高频误判点”来写，而不是围绕“理想回答”来写。

优先补这些样例：

1. 正常模板复用，不应误判
2. 法规引用相似，不应误判
3. 证据不足，只能建议复核
4. 用户问题含糊，应先澄清
5. 文件不够，不应直接生成审查结论

### 9.5 第五步：建立 Prompt 评测集

建议至少建立三类评测样本。

#### A. 路由评测集

覆盖：

1. 明确标书审查请求
2. 明确合同预审请求
3. 明确风险预警请求
4. 多场景混合请求
5. 含糊请求

指标：

1. 场景识别准确率
2. 澄清触发准确率
3. 误路由率

#### B. 中间执行评测集

覆盖：

1. 规则命中
2. 规则不命中
3. 证据不足
4. 正常相似排除

指标：

1. JSON 合法率
2. 枚举合法率
3. 误报率
4. 漏报率

#### C. 最终回答评测集

覆盖：

1. 强证据高风险
2. 中等风险建议复核
3. 证据不足无法判定
4. 缺参数需澄清

指标：

1. 是否引用结构化结果
2. 是否越权下结论
3. 是否包含可复核建议
4. 用户可读性

## 10. Prompt 版本管理方案

建议对 Prompt 建立最小版本治理。

### 10.1 版本字段

建议每个重要 Prompt 至少记录：

1. `promptKey`
2. `promptVersion`
3. `scene`
4. `layer`
5. `owner`
6. `lastUpdatedAt`
7. `changeSummary`

### 10.2 版本策略

建议：

1. 小改动使用文档内版本递增
2. 影响结构化输出字段的改动视为重要版本变更
3. 重要 Prompt 改动前后必须跑评测集

### 10.3 回滚策略

如果出现以下情况，应能快速回滚：

1. JSON 解析失败率明显上升
2. 场景识别误判率上升
3. 回答越权率上升
4. Tool 调用稳定性下降

---

## 11. 与现有架构的对齐建议

Prompt 工程必须和当前项目架构保持一致。

### 11.1 AgentChatService / AgentSceneService

适合承接：

1. 通用边界 Prompt
2. 路由 Prompt
3. 参数澄清 Prompt

不适合承接：

1. 场景内单规则判断 Prompt
2. Workflow 结论生成 Prompt

### 11.2 SceneService

适合承接：

1. 场景参数补齐 Prompt
2. 场景结果整理 Prompt

不适合承接：

1. 通用层路由 Prompt
2. 跨场景共享大 Prompt

### 11.3 Orchestrator

适合承接：

1. Tool Calling Prompt
2. 场景内子任务编排 Prompt
3. 最终结果组织 Prompt

这是 Prompt 工程最关键的主战场。

### 11.4 Tool / Workflow

原则上：

1. Tool 应尽量减少 Prompt
2. Workflow 优先走确定性逻辑
3. 只有确实需要语义判断时，才引入局部 Prompt

## 12. 落地路线图

建议按三阶段推进。

### 12.1 第一阶段：治理现状

目标：

1. 盘点现有 Prompt
2. 分类分层
3. 补文档
4. 统一命名

产出：

1. Prompt 清单
2. Prompt 分层目录
3. 关键 Prompt 责任说明

### 12.2 第二阶段：重构重点链路

优先处理：

1. 标书审查
2. 通用路由
3. 结果校验

原因：

1. 标书场景最复杂
2. 最容易暴露 Prompt 边界问题
3. 最容易体现回答质量提升

### 12.3 第三阶段：建立评测与版本化

目标：

1. Prompt 变更可测
2. Prompt 版本可追踪
3. Prompt 效果可比较

这一步完成后，Prompt 优化才真正进入工程化阶段。

---

## 13. 对当前“所有 Prompt 放一个文件夹”的结论

结论不是“必须立刻拆成很多地方”，而是：

1. 可以保留统一管理入口
2. 但必须在统一入口内完成分层分类
3. 必须明确每个 Prompt 的职责边界
4. 必须建立版本和评测机制

换句话说，问题不是“放一个文件夹”，问题是“是否无分层地堆在一起”。

如果只是一个目录，但内部有清晰层次、命名规范、模板规范、评测机制，这仍然是可维护的。

---

## 14. 最终建议

对本项目而言，Prompt 工程优化的核心不是追求“更像专家”，而是追求：

1. 路由更稳
2. 判断更受控
3. 输出更结构化
4. 回答更可解释
5. 整体更可评测

建议立即执行的动作只有三件：

1. 先补全 Prompt 清单和分层映射
2. 先拆标书审查链路中的大 Prompt
3. 先建立最小评测集和版本记录

这三步做完之后，再去逐条优化文本细节，收益才会稳定。

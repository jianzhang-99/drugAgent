> 文档版本：V1.1

> 适用范围：上层通用 Agent、RAG、标书审查、后续语音与多模态扩展

> 2. 本仓库当前已经接了哪些能力、还缺哪些关键能力

## 0. 已完成的优化（2026-04-08）

### ✅ RAG 链路优化：移除双 LLM 调用
- **改动**：`AgentSceneService.dispatchToGeneralChat()` 改用 `knowledgeRetrievalTool.search()` 替代 `retrieve()`
- **效果**：命中知识库时，去掉一轮额外 LLM 调用，总耗时减少一整轮模型请求时间

### ✅ 标题生成异步化
- **改动**：`AgentSceneService.generalChatWithTitle()` 使用 query 截断作为默认标题，不再等待 LLM 生成标题
- **效果**：减少主请求输出负担，降低解析复杂度

### ✅ 标书审查语义分析器并行化
- **改动**：`TenderReviewWorkflow.executeSemanticAnalyzers()` 真正使用 `semanticAnalyzerExecutor` 并行执行 6 个分析器
- **效果**：从串行执行变为并行收敛，每个分析器独立超时 30 秒

### ✅ L4 校验可配置开关
- **改动**：`TenderReviewWorkflow` 增加 `agent.tender-review.l4-validation-enabled` 配置项
- **效果**：可根据场景决定是否启用 L4 校验，默认启用

### ✅ 通用对话阶段耗时埋点
- **改动**：`AgentSceneService.decideAndExecute()` 和 `dispatchToGeneralChat()` 增加耗时日志
- **埋点指标**：`routeCostMs`、`ragRetrieveCostMs`、`finalAnswerCostMs`、`totalCostMs`

## 1. 当前仓库与百炼的实际接入现状

当前代码里，百炼已经不是“待接入”，而是“部分已接入”状态。

### 1.1 已接入能力

- 文本/多模态对话调用
  - 入口：`src/main/java/com/liang/drugagent/shared/llm/DashScopeLlmClient.java`
  - 当前通过 DashScope 官方 Java SDK 的 `MultiModalConversation` 调用模型
  - 默认聊天模型：`qwen3.5-plus`

- 流式输出能力
  - 入口：`DashScopeLlmClient.streamChat(...)`
  - 主链路已完成流式改造

- Function Calling 工具调用
  - 入口：`src/main/java/com/liang/drugagent/shared/llm/FunctionCallOrchestrator.java`
  - 通过 Generation API 实现，支持工具注册、调用、结果注入循环

- JSON Schema 严格结构化输出
  - 入口：`src/main/java/com/liang/drugagent/shared/llm/JsonSchemaUtils.java`
  - 支持 json_object 和 json_schema 格式

- 百炼官方 Rerank 模型
  - 入口：`src/main/java/com/liang/drugagent/shared/rerank/DashScopeRerankService.java`
  - 支持文本重排序优化

- OCR / 文档解析模型
  - 入口：`src/main/java/com/liang/drugagent/shared/ocr/DashScopeOcrService.java`
  - 使用 Qwen-VL 模型进行文档解析

- Responses API 客户端
  - 入口：`src/main/java/com/liang/drugagent/shared/llm/DashScopeResponsesService.java`
  - 支持对话托管和会话管理

- MCP Model Context Protocol
  - 入口：`src/main/java/com/liang/drugagent/shared/mcp/DashScopeMcpService.java`
  - 支持 MCP Server 注册和工具调用

- Context Cache 上下文缓存
  - 入口：`src/main/java/com/liang/drugagent/shared/contextcache/DashScopeContextCacheService.java`
  - 支持显式/隐式缓存，减少 token 消耗

- Web Extractor 网页抓取
  - 入口：`src/main/java/com/liang/drugagent/shared/webextract/DashScopeWebExtractorService.java`
  - 支持网页内容提取

- 语音识别 / 语音合成
  - 入口：`src/main/java/com/liang/drugagent/shared/speech/DashScopeSpeechService.java`
  - 支持音频转文本和文本转音频

- 全模态交互（视觉理解）
  - 入口：`LlmRequest.ChatMessage.multiModalContent`
  - 支持图片、视频等多模态内容输入

- Batch 批量推理
  - 入口：`src/main/java/com/liang/drugagent/shared/batch/DashScopeBatchService.java`
  - 支持离线批量处理，成本降至实时推理的 50%

- 思考模式控制
  - 通过 `LlmRequest.thinkingEnabled` 控制
  - 简单问答可禁用思考以降低延迟和成本

- 向量化能力
  - 入口：`src/main/java/com/liang/drugagent/shared/rag/config/DirectDashScopeEmbeddingModel.java`
  - 当前 embedding 模型：`text-embedding-v3`

- 百炼联调测试
  - 入口：`src/test/java/com/liang/drugagent/shared/llm/DashScopeLlmClientIntegrationTest.java`
  - 已覆盖同步对话与流式对话联调

### 1.2 待接入能力

- Conversations API 会话托管（高级功能）

结论：

当前仓库已经接上了“基础聊天 + 流式 SDK + embedding”，但还没有把百炼更适合 Agent 系统的能力真正接满。

## 2. 百炼平台可接入能力清单

下面这份清单不只是“平台有什么”，而是结合本项目实际可落地的接入项来整理。

### 2.1 文本生成与多轮对话

可接：

- Chat Completions
- Responses API
- 流式输出
- 多轮消息上下文
- 深度思考开关

适合本项目的用途：

- 通用问答
- 标书审查中的 LLM 判断
- 合同预审与风险预警的总结生成
- 报告生成与解释生成

建议：

- 主问答链路优先使用流式输出
- 对简单问答显式关闭思考模式，避免不必要延迟
- 对复杂审查与长报告生成再按需开启思考模式

### 2.2 Function Calling 工具调用

可接：

- 模型按工具 schema 选择工具
- 工具参数结构化下发
- 流式返回工具名与参数
- 并行工具调用

适合本项目的用途：

- 标书审查 Tool 化主入口
- 合同预审工具链
- 风险预警多工具组合
- 知识检索、文档解析、规则执行等工具化编排

和当前架构的关系：

- 这项能力非常契合本仓库在 `AGENTS.md` 里强调的 `Orchestrator -> Tool -> Workflow` 方向
- 标书审查目标主入口本来就应该继续向 `TenderReviewToolOrchestrator` 收敛

### 2.3 严格结构化输出

可接：

- `json_object`
- `json_schema`

适合本项目的用途：

- 审查结果结构化回写
- 风险项列表生成
- 证据链提取
- 报告摘要、标题、分值、置信度输出

建议：

- 规则命中后的 LLM 归纳结果，不要再依赖“正文里约定特殊标记再手工解析”
- 标题、summary、riskLevel、score、evidenceList 等优先切到 `json_schema`

### 2.4 MCP

可接：

- 通过 Responses API 配置 MCP Server
- 让模型直接使用外部工具与服务

适合本项目的用途：

- 查询法规库
- 查询企业信息
- 查询招采公告
- 查询外部知识服务

注意：

- 百炼官方文档说明 MCP 当前通过 Responses API 接入
- 当前仓库使用的是 DashScope SDK `MultiModalConversation`
- 这意味着如果后续要接 MCP，通常需要补一层 Responses API 客户端，而不是只沿用当前 SDK 调法

### 2.5 Conversations API

可接：

- 会话创建
- 历史消息托管
- 配合 Responses API 自动注入历史上下文

适合本项目的用途：

- 长对话
- 跨端会话续接
- 降低手工拼接 messages 的复杂度

注意：

- 当前仓库已经有自己的 `ChatSession` / `ChatMessage` 体系
- 是否接入百炼会话托管，需要评估“平台托管会话”和“本地业务会话”之间的边界

### 2.6 Embedding 向量化

可接：

适合本项目的用途：

## 4. 当前 LLM 对话为什么慢

这一部分不是泛泛而谈，而是结合当前代码链路看。

## 4.1 通用对话命中 RAG 时，当前链路很可能串行调用了两次 LLM

当前代码：

- `AgentSceneService.dispatchToGeneralChat(...)` 先调用 `knowledgeRetrievalTool.retrieve(query, orgId, null)`
- `KnowledgeRetrievalTool.retrieve(...)` 默认 `needGenerateAnswer = true`
- `RagService.query(...)` 在检索命中后会自己拼 prompt 再调用一次 `llmService.chat(...)` 生成答案
- 回到 `AgentSceneService` 后，又会再调用一次 `generalChatWithTitle(...)` 生成最终回答

问题：

- 第一轮 LLM 调用是在 RAG 内部生成答案
- 第二轮 LLM 调用才是实际返回给前端的回答
- 但当前通用对话实际上只用到了 RAG 的证据，不直接使用 RAG 生成的 answer

结果：

- 命中知识库时，链路会额外多一次完整的大模型请求
- 用户体感就是“同样一句问题，命中知识库时明显更慢”

这是当前最值得优先处理的慢因。

## 4.2 主对话入口 `/agent/chat` 是同步返回，不是完整流式返回

当前现状：

- `DashScopeLlmClient` 底层支持 `streamChat`
- `AgentController` 也有 `/agent/chat/stream`
- 但主业务链路 `AgentChatService.chat(...) -> AgentSceneService.decideAndExecute(...)` 走的是同步结果返回

影响：

- 即使模型总耗时没有特别夸张，用户也会在首字节前长时间等待
- 这会把“后端总耗时”直接变成“前端空白等待时间”

## 4.3 标题与回答耦合在同一次大模型输出里

当前通用对话要求模型同时输出：

- 最终回答
- 会话标题（通过 `【会话标题】xxx` 约定格式回传）

问题：

- 模型要额外生成标题
- 输出长度更长
- 还要再做字符串截取和兜底解析

这不是最大的慢因，但属于持续增加耗时的低效设计。

## 4.4 标书审查链路还有额外的 LLM 后处理

在 `TenderReviewWorkflow` 中：

- 规则执行后会进入 LLM 语义分析
- 报告生成完成后还会执行一次 `validateAndNormalizeResult(...)`
- 这个 L4 校验本质上又是一轮额外 LLM 调用

因此：

- 标书审查不只是“一个工作流”
- 而是“规则 + 多轮 LLM 判断 + L4 校验”的复合链路
- 如果用户把“审查等待时间”理解成“对话慢”，这也是核心原因之一

## 4.5 标书审查里的语义分析器实现与注释不一致，容易导致总耗时偏长

`TenderReviewWorkflow.executeSemanticAnalyzers(...)` 的注释写的是：

- 6 个分析器并行执行
- 每个分析器独立超时 30 秒

但当前实际代码：

- 定义了 6 个任务和 `semanticAnalyzerExecutor`
- 却没有真正使用并行执行逻辑
- 最终只串行执行了 `W-P2 / W-P3 / W-M3`
- `W-P1 / W-P4 / W-M8` 仅定义未执行
- `analyzerStatus` 也没有真正写入执行状态

这说明当前实现存在两个问题：

- 不是预期中的“并行 + 超时收口”
- 代码行为与设计说明不一致，后续排查性能会很困难

## 4.6 缺少通用对话主链路的阶段耗时打点

目前仓库里有标书审查相关的 metrics 代码，但通用聊天主链路没有形成清晰的阶段耗时日志，例如：

- 路由耗时
- 知识检索耗时
- RAG 生成耗时
- 最终回答耗时
- 标题生成耗时

没有这些打点时，大家会感觉“LLM 很慢”，但实际上可能是：

- 检索慢
- 额外 LLM 调用慢
- 标题耦合拖慢
- 大模型本身慢

## 4.7 平台侧潜在慢因：思考模式与大模型规格

百炼官方文档说明：

- 深度思考会提升质量
- 但也会增加响应延迟和成本

当前 `DashScopeLlmClient` 没有显式控制 `enable_thinking`。

这意味着：

- 如果某些模型或后续切换的接口默认带思考过程
- 简单问答也可能被不必要地拉长耗时

因此建议：

- 对通用闲聊、标题生成、校验、路由类任务，显式关闭思考模式
- 只对复杂推理、长报告生成按需开启

## 5. 一个可执行的优化方案

下面给出的是“先解决 80% 体感问题”的方案，不是一步到位的大重构。

## 5.1 P0 方案：先把最明显的浪费砍掉

### 方案一：RAG 只负责取证，不负责先生成答案

改造目标：

- `AgentSceneService.dispatchToGeneralChat(...)` 不再调用 `knowledgeRetrievalTool.retrieve(query, orgId, null)`
- 改为调用“仅检索不生成答案”的方法，例如 `search(...)`

效果：

- 命中知识库时，去掉一轮额外 LLM
- 总耗时通常会直接少一整轮模型请求时间

这是当前收益最高、改动最小的优化项。

### 方案二：把完整主链路切到真正的流式输出

改造目标：

- 不是只保留一个”旁路 SSE 接口”
- 而是让 `AgentChatService -> AgentSceneService -> RAG/LLM` 主链路支持流式返回

效果：

- 后端总耗时不一定立刻大幅下降
- 但首字节时间会明显改善
- 用户体感会从”长时间空白”变成”很快开始出字”

**详细方案见**：[流式输出主链路改造方案](./流式输出主链路改造方案.md)

### 方案三：标题生成从主回答链路剥离

建议做法：

- 首轮先用 query 截断作为默认标题
- 或者异步生成标题
- 或者在会话首轮结束后后台补写标题

效果：

- 减少主请求的输出负担
- 降低解析复杂度

## 5.2 P1 方案：把慢点变成可观测

建议增加统一埋点：

- `routeCostMs`
- `ragRetrieveCostMs`
- `ragGenerateCostMs`
- `finalAnswerCostMs`
- `titleCostMs`
- `totalCostMs`
- `model`
- `provider`
- `inputTokens`
- `outputTokens`

收益：

- 后面再说“慢”的时候，可以直接定位是哪一段慢
- 也方便比较不同模型、不同 prompt、不同场景的耗时差异

## 5.3 P1 方案：辅助型任务切到低时延模型或显式关闭思考

建议拆分模型职责：

- 最终回答：保留当前高质量模型
- 标题生成：低时延模型或规则生成
- 路由分类：低时延模型或规则
- L4 校验：低时延模型，必要时再开

同时：

- 对简单任务显式关闭思考模式

收益：

- 把“不是必须用大模型高配能力”的步骤降本增速

## 5.4 P2 方案：修正标书审查语义分析链路

建议做法：

- 真正使用 `semanticAnalyzerExecutor`
- 用 `CompletableFuture` 并行跑分析器
- 每个分析器设置独立超时
- 把 `analyzerStatus` 真正写全
- 明确哪些分析器是 P0 必跑，哪些是可降级跳过

收益：

- 标书审查场景从“串行等多个模型”变成“并行收敛”
- 也更符合当前代码注释与设计意图

## 5.5 P2 方案：让 L4 校验变成可配置能力

建议做法：

- 对低风险或短结果，默认不开 L4 校验
- 对高风险结论、正式报告导出场景，再开启 L4 校验
- 或者改成异步校验

收益：

- 避免所有请求都多一轮 LLM

## 6. 推荐落地顺序

如果只允许做一轮优化，我建议按这个顺序推进：

1. 通用对话 RAG 改成“只检索不先生成答案”
2. 主链路改为流式输出
3. 标题生成异步化
4. 增加通用对话阶段耗时埋点
5. 标书审查语义分析器并行化
6. L4 校验开关化

## 7. 对本项目的直接建议

### 7.1 近期最值得做的百炼接入项

- Function Calling
- JSON Schema 结构化输出
- OCR / 文档解析
- Context Cache
- 官方 Rerank

### 7.2 近期最值得做的性能优化项

- 去掉 RAG 命中场景下的双 LLM 调用
- 将主链路切到流式输出
- 路由/标题/校验与最终回答分模型治理
- 给关键阶段补齐耗时指标

### 7.3 一个很重要的架构判断

百炼不是只应该被当成“一个 LLM 厂商 API”。

对于本项目，更合适的理解是：

- 百炼 = 模型层 + 工具调用层 + 结构化输出层 + OCR/语音/多模态层 + 平台级提效能力

如果只把它当成 `chat(model, prompt)` 使用，会浪费掉它对 Agent 系统最有价值的部分。

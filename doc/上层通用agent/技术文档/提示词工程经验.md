# 提示词工程经验

## 1. 文档目的

本文总结上层通用 Agent 在提示词设计与调优过程中的真实经验，重点不是讨论“如何写出更华丽的 Prompt”，而是回答一个更工程化的问题：

- 如何让 Agent 的行为更可控
- 如何让提示词更容易验证和迭代
- 如何减少“看起来变聪明，实际上更不稳定”的伪优化

本文适用于以下场景：

- Code Agent 或业务 Agent 的 System Prompt 设计
- Tool Calling Agent 的行为约束设计
- Agent 线上问题的排查与提示词调优

---

## 2. 早期最常见的三类错误

### 2.1 照抄“神级提示词”

最早做 Prompt 时，很容易沉迷于收集各种“顶级提示词”。

例如 GitHub 上那些高星项目里的“专家模式”“终极工程师模式”“突破限制模式”，常见写法通常是：

- 让模型扮演拥有多年经验的资深专家
- 强调模型必须严谨、自信、专业、优雅
- 希望模型表现得更像一个“高级工程师”

这类提示词在普通对话场景中可能偶尔有效，但在 Agent 场景中往往副作用很大。

典型问题是：

- 模型会更“敢说”
- 模型会更依赖自身推断
- 模型在缺乏证据时更容易编造看似合理的内容

例如，当仓库中根本没有某个函数、某个类、某段实现时，模型不会老老实实承认“没找到”，而是根据常识补出一套“听起来很像真的”的答案。

这类错误的根因是：

提示词强化了“专家姿态”，却没有强化“证据约束”。

在 Agent 系统里，这种导向通常是危险的。对 Agent 来说，最重要的不是“像专家”，而是：

- 基于真实上下文
- 基于真实工具结果
- 基于真实代码和数据做结论

一句话总结：

不要追求让模型“更像专家”，而要优先让模型“更依赖证据”。

### 2.2 凭感觉调优

另一个高频错误是凭主观感受改提示词。

典型模式通常是：

- Agent 表现不好，就立刻改 Prompt
- 加一条“不要猜测”，感觉似乎稳了一些
- 再加一条“必须基于证据”，感觉似乎又聪明了一些
- 但没有任何对照实验，也没有明确指标

这种调优方式的问题在于：

- 不知道究竟是哪条规则起了作用
- 不知道优化是否只对当前样例有效
- 不知道副作用会不会在别的任务里放大

例如，曾经为了让模型处理复杂任务时更有条理，在提示词里加了一段很长的规则，要求它“先分解再执行”。结果模型开始机械地在每轮都输出一段分解步骤，真正有价值的动作反而被淹没，执行效率和响应质量都下降了。

这类现象说明：

提示词不是越多越好，也不是越完整越好。没有验证的调优，最终往往只是把系统推向另一种不稳定。

### 2.3 先改提示词，再补观测

这是最容易导致“治标不治本”的坏习惯。

Agent 出错后，第一反应如果是直接改 Prompt，而不是先看执行轨迹，往往会把真正的问题掩盖掉。

例如，某段时间 Agent 经常在不合适的时候调用写入类工具。直觉上很容易在提示词里补一堆规则，例如：

- 只有确认用户要修改时才允许写入
- 必须先读取再写入
- 无法确认时优先使用 Read

这些规则看起来很合理，但实际效果可能是：

- 模型过度保守
- 每轮先读大量文件
- Token 消耗明显上升
- 正确率却没有同步提高

回过头看 Trace 才发现，根因并不是模型“不守规则”，而是上下文里缺少“当前任务类型”这类关键信息。模型无法判断当前请求是浏览、分析还是修改，提示词中的“应该如何做”自然也无法真正生效。

这类问题说明：

提示词可以约束行为，但不能补齐本来就不存在的上下文信息。

如果观测层缺失、工具描述不清、上下文不完整，那么继续堆 Prompt 往往只会让系统更重、更慢、更难调。

## 3. 后来逐步稳定下来的做法

### 3.1 先记录，再优化

现在更可靠的做法是：

Agent 出问题时，先不要急着改提示词，而是先看完整 Trace。

重点排查以下问题：

- 模型从哪一步开始偏离预期
- 当时上下文里有哪些信息，缺了哪些信息
- 工具返回的 Observation 是否足够清晰
- 模型有没有正确理解工具结果
- 问题究竟出在 Prompt、工具描述、上下文注入，还是流程设计

很多时候真正的问题并不在提示词本身。

常见情况包括：

- 工具描述过于模糊，导致模型选错工具
- 上下文过长，导致注意力分散
- 返回结构不稳定，导致模型误读 Observation
- 工作流边界不清，导致模型承担了本不该承担的决策

这类问题如果只靠改 Prompt，很难真正解决。

### 3.2 用 Trace 做对比实验

当确认确实需要调整提示词时，应该尽量按实验方式推进，而不是凭直觉堆规则。

建议做法：

1. 保持任务、上下文、工具集合、测试样例不变
2. 只修改提示词中的一个点
3. 重新跑同一组测试
4. 对比行为变化，而不是只看主观感受

重点关注的指标包括：

- 成功率是否变化
- 平均步数是否变化
- Token 消耗是否变化
- 是否引入新的误判或漏判
- 行为变化是否符合预期

例如，曾经为了让模型搜索得更精准，删掉了一部分关于搜索策略的描述，只保留“使用精确关键词”这条规则。结果 Trace 显示：

- 无关文件确实搜少了
- 但漏搜率也明显上升
- 模型变得过于保守

这类反馈说明：

调优不是追求某个单点最优，而是在“全、准、稳、成本”之间找平衡。

### 3.3 坚持单变量改动

提示词调优最怕一次改很多条。

如果一次性新增、删减、重写多条规则，会立刻失去归因能力：

- 变好了，不知道是哪条起作用
- 变差了，不知道是哪条造成副作用
- 即便短期有效，也很难复制到下一轮调优中

因此，更可控的方式是：

- 一次只改一个关键点
- 每次调优都能说清楚预期行为变化
- 每次验证都能明确判断“是否达到目标”

这套方法虽然慢一点，但更适合工程化 Agent 系统。

## 4. 一个更稳定的提示词结构

经过多次踩坑后，比较稳的一种写法是把提示词拆成三层：边界层、决策层、恢复层。

### 4.1 边界层：明确不能做什么

边界层只写红线和底线，不写长解释。

适合放入这类规则：

- 未找到证据时，必须明确说明“未找到”，禁止猜测
- 只能基于当前上下文和工具结果做判断
- 信息不足时必须承认不足，必要时请求补充
- 禁止访问约束范围之外的资源
- 禁止把推测包装成事实

这一层的作用不是指导模型“怎么聪明地做”，而是先约束它“绝对不能怎么做”。

对于 Agent 系统来说，边界层通常比角色设定更重要。

### 4.2 决策层：明确应该如何思考和行动

决策层要尽量写成可执行的过程，而不是抽象要求。

例如，优先使用这类描述：

- 先搜索证据，再读取上下文，再形成结论
- 能通过工具确认的，不要仅靠推理
- 每个 Action 之后都要基于 Observation 再决定下一步
- 给出修改建议时，必须能指出对应代码或数据依据

尽量避免这类模糊表达：

- 聪明地分析
- 合理地推断
- 尽可能全面
- 认真思考后给出最佳方案

原因很简单：

模型无法稳定理解“聪明”“合理”“最佳”这些抽象词，但它能执行明确的流程约束。

### 4.3 恢复层：明确失败时如何降级

失败不是异常情况，而是 Agent 系统的常态之一。

所以提示词中应明确写出常见失败场景下的处理策略，例如：

- 工具返回空结果时，先检查参数，再考虑更换关键词重试
- 编辑类工具遇到冲突时，必须重新读取最新内容后再修改
- 连续多次尝试仍失败时，停止盲目重试并向用户报告
- 上下文不足且无法补齐时，明确说明阻塞点

这一层的价值非常大，因为它直接决定了 Agent 出错时是“继续失控”，还是“可控降级”。

## 5. 一些真正有用的工程细节

### 5.1 让 System Prompt 保持稳定

建议把变化最少的内容放在 System Prompt 中，例如：

- 基础行为边界
- 工具使用原则
- 不可突破的安全约束
- 核心决策规则

而将动态内容放在 User Message、上下文注入或运行时状态中，例如：

- 当前任务目标
- 当前场景
- 用户的特殊要求
- 本轮 Todo
- 当前可用资源或文件

这样做的好处是：

- 降低变量数量
- 便于定位问题
- 减少每次调 Prompt 对整体行为的扰动

### 5.2 不要把规则清单写得过长

如果 System Prompt 长到几千 token，且堆满了几十条“注意事项”，通常意味着系统已经开始把流程问题、工具问题、上下文问题一股脑推给 Prompt 解决。

这往往不是好现象。

更好的原则是：

- 只保留真正稳定、真正关键的规则
- 其他问题优先从工具设计、返回格式、流程拆分、上下文组织上解决

换句话说：

Prompt 应该解决“行为约束问题”，而不是承担“系统设计补丁”的角色。

### 5.3 具体例子往往优于抽象要求

抽象要求经常会失效，具体示例通常更容易被模型正确执行。

例如，不要只写：

“工具返回错误时要正确处理。”

更有效的写法通常是：

如果 Edit 返回 `CONFLICT`，你应该：

1. 重新读取该文件
2. 对比当前文件内容与预期修改点
3. 调整修改参数以匹配最新内容
4. 再次尝试编辑

这种写法的价值在于：

- 行为更具体
- 预期更明确
- 更容易验证
- 更容易和 Trace 对照

### 5.4 优先解决“信息缺口”，不要只加规则

当模型频繁犯错时，一个值得优先排查的问题是：

它究竟是“知道该怎么做但没照做”，还是“根本没有足够信息做对”？

如果是后者，那么继续加 Prompt 往往收益很低。

更应该优先补的是：

- 任务类型标记
- 当前场景标记
- 工具返回结构
- 上下文摘要
- 文件/对象的唯一标识

很多提示词问题，本质上是信息工程问题。

## 6. 面向上层通用 Agent 的补充建议

结合本项目“场景路由 + Orchestrator + Tool + Workflow”的架构，提示词设计还应额外注意以下几点。

### 6.1 不要让 Prompt 代替架构分层

如果某段 Prompt 试图告诉模型：

- 什么时候该走哪个场景
- 什么时候该自己推断业务规则
- 什么时候该决定完整工作流

那通常说明架构分层还不够清晰。

应该优先由系统层解决的问题包括：

- 场景识别由 Route 层负责
- Tool 暴露由 Orchestrator 负责
- 业务主链路由 Workflow 负责
- Prompt 负责的是“在已知边界内如何行动”

不要把本该由代码确定的流程，全部交给提示词临时约束。

### 6.2 对 Tool Calling 的提示词要强调“受控调用”

在 Tool Calling 场景中，提示词不应鼓励模型“自由发挥”，而应强调：

- 只在工具职责范围内调用
- 先理解工具用途，再决定是否调用
- 无法从工具结果得到结论时，要承认不确定性
- 工具返回结构化结果后，应基于结果回答，而不是绕开结果另起一套推理

尤其在医药监管这类强调证据链和可解释性的场景下，提示词要帮助模型形成：

“以工具结果为主，以语言组织为辅”

而不是：

“以语言推断为主，工具只是参考”

### 6.3 Prompt 的目标是“稳定产出”，不是“更像人”

在业务 Agent 中，一个好的 Prompt 最终要服务于：

- 场景识别更稳定
- 工具调用更克制
- 输出结构更一致
- 失败降级更可预测
- 结果更容易审计和解释

因此，评价 Prompt 的标准不应只是“回复自然不自然”，还要看：

- 是否减少误调用
- 是否减少无依据回答
- 是否更容易调试
- 是否更利于复盘

---

## 7. 结论

好的提示词工程，不是写出一段“特别厉害的话”，而是建立一套可验证、可迭代、可复盘的行为约束机制。

更准确地说：

- 提示词不是魔法咒语
- 提示词不是架构补丁
- 提示词也不是让模型突破能力上限的捷径

提示词真正的价值在于：

- 把模型行为限制在可控范围内
- 帮助系统在失败时可降级、可解释
- 让调优过程从“凭感觉”变成“基于证据的工程迭代”

如果要用一句话概括本文的核心经验，那就是：

提示词的目标，不是让模型显得更聪明，而是让整个 Agent 系统更稳定、更可调试、更可信。

# RAG优化计划

## 1. 文档目标

本文档用于为当前项目制定一份面向 Agent 系统的 RAG 优化计划。

本文档不讨论排期、人力和时间安排，只回答 3 个问题：

1. 当前 RAG 应按什么顺序优化
2. 每个阶段要收敛哪些能力
3. 每个阶段完成后如何验证是否有效

本文档的定位不是“做一个通用检索平台”，而是让 RAG 更稳定地服务于上层通用 Agent，尤其是标书审查、合同预审、风险预警这类需要证据链和可解释性的业务场景。

---

## 2. 当前问题概述

结合当前实现，RAG 主链路已经具备最小闭环：

```text
文档入库
-> 文本提取
-> chunk 切分
-> embedding
-> 向量库存储

用户提问
-> metadata 过滤
-> 向量检索 top-k
-> 拼装检索证据
-> LLM 生成回答
```

但这条链路仍然停留在“简易 RAG”阶段，主要问题包括：

1. chunk 切分仍不够贴近业务结构，章节标题、条款编号、段落语义没有被充分保留
2. metadata 设计不完整，部分字段虽然在查询侧预留，但没有稳定入库
3. 检索主链路目前主要依赖单路向量召回，缺少混合检索和重排
4. prompt 侧虽然限制“基于证据回答”，但回答与证据块之间的绑定仍不够强
5. 缺少面向业务问题的检索评测和答案评测闭环
6. RAG 在 Agent 体系中的边界还需要进一步收敛，避免后续把业务规则和场景逻辑重新塞回通用 RAG 层

一句话总结：

当前 RAG 已经“能跑”，但距离“可控、可评估、可扩展”的业务 Agent 基础设施还有明显差距。

---

## 3. 优化总原则

### 3.1 先收敛主链路，再增加复杂能力

优先保证下面这条链路稳定：

```text
高质量切分
-> 完整 metadata
-> 稳定召回
-> 可验证引用
-> 可评测结果
```

不要一开始同时并行多套召回方案、多套提示词方案和多套业务适配方式。

### 3.2 RAG 只负责“找证据”和“组织证据输入”

RAG 的职责应收敛为：

1. 让知识可入库
2. 让问题可检索
3. 让证据可消费
4. 让引用可回传

RAG 不应负责：

1. 场景路由
2. 业务规则命中
3. Workflow 主执行
4. 风险融合和最终业务判定

### 3.3 优化目标应服务 Agent，而不是孤立优化检索指标

本项目是上层通用 Agent，不是纯知识问答系统。

因此 RAG 优化的目标不是单纯提升“文本相似度命中率”，而是提升：

1. Agent 在业务场景里的证据补充能力
2. 最终回答的可解释性
3. Tool / Workflow / Report 的证据消费稳定性

### 3.4 先解决高频错误，再做高级架构

优先级建议如下：

1. 先解决切分和 metadata 问题
2. 再解决检索和重排问题
3. 再解决生成和引用问题
4. 最后再做复杂编排，例如动态检索、查询改写、多轮检索、自纠错 RAG

---

## 4. Agent 体系中的边界约束

为了避免后续优化过程中再次出现职责混乱，RAG 在 Agent 架构中的边界建议固定如下。

### 4.1 Controller 层

只负责：

1. 接收知识问答或知识检索请求
2. 接收知识入库请求
3. 返回统一响应

不要在 Controller 中写检索策略判断或证据拼装逻辑。

### 4.2 AgentChatService 层

只负责：

1. 在对话主链路中决定当前是否需要知识增强
2. 构建统一上下文
3. 调用场景 Orchestrator 或知识检索 Tool
4. 做统一降级和回写

不要在 `AgentChatService` 中直接写：

1. chunk 处理逻辑
2. 检索策略选择逻辑
3. 查询改写细节
4. 重排逻辑

### 4.3 Route 层

只负责：

1. 识别当前问题属于哪个业务场景
2. 判断是否适合进入知识增强链路

不要让路由层直接负责知识检索结果生成。

### 4.4 Orchestrator 层

当某业务场景需要知识增强时，应优先让场景 Orchestrator 决定：

1. 当前是否调用知识检索 Tool
2. 调哪个知识域
3. 检索结果是给 LLM 回答，还是给 Workflow / Tool 做证据补充

这意味着：

RAG 更适合作为场景 Orchestrator 可调用的一种能力，而不是所有场景都直接从 `AgentChatService` 裸连 `RagService`。

### 4.5 Tool 层

建议收敛出稳定的知识检索 Tool，例如：

`KnowledgeRetrievalTool`

它负责：

1. 参数整理
2. 调用 RAG 服务
3. 返回统一的 `RagOutcome`

这样做的好处是：

1. 上层 Agent 编排接口统一
2. 后续可以平滑替换底层检索策略
3. 不会把底层 RAG 细节暴露给过多上层服务

### 4.6 Workflow 层

Workflow 可以消费知识证据，但不应承担通用检索实现。

换句话说：

1. Workflow 可以“使用检索结果”
2. Workflow 不应“自己变成检索系统”

## 5. 分阶段优化计划

## 阶段一：收敛数据基础层

### 目标

先把知识入库质量做扎实，解决“检索对象本身不够好”的问题。

### 重点内容

1. 重构 chunk 切分策略，从“长度优先”收敛为“结构优先、长度兜底”
2. 让标题、章节名、条款号、段落边界尽量进入 chunk 内容或 metadata
3. 完整写入 metadata，至少稳定覆盖：
   - `orgId`
   - `scene`
   - `subScene`
   - `docType`
   - `sourceId`
   - `sourceTitle`
   - `chunkId`
   - `chunkIndex`
   - `sectionTitle`
   - `pageNo`（若可提取）
   - `topicTags`（若可确定）
4. 明确不同文档类型的切分策略差异
   - 制度/规范类文档偏章节与条款切分
   - 合同类文档偏条款切分
   - 标书类文档偏章节与小节切分
5. 修正超长 section 的切分逻辑，确保不会丢失正文中间语义

### 产出物

1. 新版 chunk 切分规则
2. 入库 metadata 字段规范
3. 文档类型与切分策略映射说明

### 验证方式

1. 抽样检查 20 个 chunk，确认每个 chunk 都能独立表达一个相对完整的证据单元
2. 抽样检查 20 个 chunk 的 metadata，确认关键字段完整率达到预期
3. 对 10 份代表性文档做人工 spot check，确认标题、条款和章节语义没有明显丢失
4. 检查同一文档重新入库后，chunk 结构和 metadata 是否稳定，不出现大幅波动

---

## 阶段二：收敛检索主链路

### 目标

先让“找证据”这件事更稳定，而不是直接追求复杂生成效果。

### 重点内容

1. 继续保留向量检索作为主干能力
2. 将混合检索正式接入主链路
   - 向量召回负责语义相关
   - 关键词召回负责条款名、编号、术语等精确匹配
3. 将重排接入主链路，减少重复 chunk 和低价值 chunk 混入前列
4. 明确 top-k、相似度阈值、重排数量的配置边界
5. 对不同场景设置默认过滤条件
   - 知识问答
   - 合同预审知识增强
   - 标书审查知识增强
   - 风险预警知识增强
6. 为查询请求预留查询改写能力，但暂不在第一版做复杂多轮查询规划

### 产出物

1. 标准检索主链路
2. 检索策略配置项说明
3. 场景默认过滤策略说明

### 验证方式

1. 建立一组标准检索问题集，每题标注应命中的 `sourceId` 或 `chunkId`
2. 对比优化前后 top-k 命中率是否提升
3. 观察重复来源占比是否下降
4. 观察问题中包含明确关键词、章节名、条款号时，召回是否更稳定
5. 对 20 个真实业务问题进行人工比对，确认“检索到的证据是否更像人会选的资料”

---

## 阶段三：收敛证据组织与生成约束

### 目标

让模型不是“看了一堆资料自由发挥”，而是“基于证据块做可验证回答”。

### 重点内容

1. 重构 RAG prompt 结构
   - 明确问题区
   - 明确证据区
   - 明确输出区
2. 强化回答与 chunk 的绑定关系
   - 回答中引用 chunk 编号
   - 引用与 `citations` 一一对应
3. 区分回答任务类型
   - 直接问答
   - 归纳总结
   - 多来源对比
   - 证据不足说明
4. 减少重复证据对模型上下文的污染
5. 对“证据冲突”和“证据不足”设计明确输出规范
6. 让生成结果更适合上层 Agent 消费，而不是只适合直接展示给用户

### 产出物

1. 新版 RAG prompt 模板
2. 标准化引用格式
3. `RagQueryResponse` 消费约定

### 验证方式

1. 抽样检查回答中的每个核心结论，确认都能回溯到具体 chunk
2. 对“证据不足”问题集进行测试，确认系统会拒答或降级，而不是胡乱补充
3. 对“多来源冲突”问题集进行测试，确认系统会指出冲突而不是强行统一
4. 对比优化前后 hallucination 样本数量是否下降

---

## 阶段四：收敛 Agent 接入方式

### 目标

让 RAG 作为 Agent 体系中的标准增强能力被接入，而不是各场景各自绕路调用。

### 重点内容

1. 明确 `KnowledgeRetrievalTool` 作为统一知识检索入口
2. 明确场景 Orchestrator 如何决定是否调用知识检索
3. 区分两类使用方式
   - 给 LLM 回答直接补知识
   - 给 Tool / Workflow 提供证据输入
4. 避免在 `AgentChatService` 中直接编排复杂检索参数和策略判断
5. 给不同场景定义知识增强接入模式
   - 标书审查场景：知识增强主要作为规则解释、法规依据补充，不替代 Workflow
   - 合同预审场景：知识增强可以参与条款解释、范式对比、风险依据补充
   - 风险预警场景：知识增强可以参与制度引用、案例支撑和监管规则补充

### 产出物

1. Agent 侧知识增强接入规范
2. Orchestrator 调用模式说明
3. Tool 输入输出约定

### 验证方式

1. 抽查各场景接入点，确认没有绕过统一 Tool 直接拼装 RAG 调用
2. 抽查 `AgentChatService`，确认未重新混入场景专属检索逻辑
3. 对 3 个核心场景分别跑通一条知识增强主链路，确认调用路径一致、职责清晰

---

## 阶段五：建立评测与监控闭环

### 目标

让 RAG 优化不再依赖“感觉变好了”，而是能持续观察和回归验证。

### 重点内容

1. 建立 RAG 评测集
   - 检索问题集
   - 生成问题集
   - 证据不足问题集
   - 冲突证据问题集
2. 定义核心评测维度
   - top-k 命中率
   - 首条命中率
   - 重复来源占比
   - 引用准确性
   - 证据支撑率
   - 人工复核触发率
3. 记录关键运行日志
   - query
   - filterExpression
   - topK
   - hit chunks
   - citations
   - answer decision
4. 建立回归验证流程
   - chunk 规则变更后回归
   - metadata 变更后回归
   - prompt 变更后回归
   - 检索策略变更后回归

### 产出物

1. RAG 评测样本集
2. 核心指标说明
3. 回归验证流程说明

### 验证方式

1. 每次关键调整后，都能在同一套样本上重跑并对比结果
2. 检索层问题和生成层问题可以被分层识别，不再混为一谈
3. 至少能回答这 3 个问题：
   - 没答对，是没检索到，还是答错了
   - 没检索到，是切分问题，还是召回问题
   - 答错了，是 prompt 约束问题，还是模型组织问题

---

## 6. 各阶段的完成标准

为了避免“做了一部分但无法判断是否完成”，每个阶段建议采用下面的完成标准。

### 阶段一完成标准

1. chunk 结构从“纯长度块”收敛为“可独立引用的证据块”
2. metadata 字段规范明确且入库稳定
3. 抽样检查结果可以支撑后续检索优化

### 阶段二完成标准

1. 混合检索和重排接入主链路
2. 有一套稳定的检索参数配置
3. 检索命中质量相比当前实现有可观察提升

### 阶段三完成标准

1. 回答与证据块绑定关系更强
2. 引用可回溯
3. 证据不足与证据冲突场景输出可控

### 阶段四完成标准

1. RAG 作为 Agent 能力的接入方式统一
2. `AgentChatService`、Orchestrator、Tool、Workflow 的边界清晰
3. 不同场景对 RAG 的调用方式一致可维护

### 阶段五完成标准

1. 有可重复执行的评测集
2. 有可持续对比的核心指标
3. 有能力分层定位 RAG 问题来源

---

## 7. 非目标说明

当前优化计划不建议在第一阶段就做下面这些内容：

1. 知识图谱检索
2. 多跳推理检索
3. 多智能体检索编排
4. 自动构建复杂检索树
5. 面向所有场景的一次性通用知识平台

这些能力并非永远不做，而是不应抢在基础链路稳定之前优先推进。

---

## 8. 一句话执行建议

对当前项目来说，RAG 优化最合理的推进顺序是：

```text
先修 chunk 和 metadata
-> 再修召回和重排
-> 再修生成和引用
-> 再统一 Agent 接入
-> 最后建立评测闭环
```

如果这条顺序被打乱，就很容易出现“模型换了很多次、prompt 改了很多版、但效果始终不稳定”的情况。

因此，本项目应优先把 RAG 视为：

“Agent 的证据供给层”

而不是：

“另一个什么都想做的通用大 Service”

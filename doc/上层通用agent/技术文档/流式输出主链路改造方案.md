> 创建时间：2026-04-08
> 负责人：后端工程师

## 1. 当前架构问题分析

### 1.1 现状梳理

| 组件 | 当前实现 | 返回类型 |
|------|---------|---------|
| `AgentController.chat()` | 同步调用 `AgentChatService.chat()` | `Result<AgentChatResp>` |
| `AgentController.streamChat()` | 旁路调用 `LLMChatService.streamChatWithScene()` | `Flux<ServerSentEvent<String>>` |
| `AgentChatService.chat()` | 同步执行场景路由、LLM调用、结果回写 | `AgentChatResp` |
| `LLMChatService.streamChatWithScene()` | 仅调用底层LLM，不走完整Agent链路 | `Flux<String>` |

### 1.2 核心问题

**问题一：主链路不是流式的**

当前 `AgentController.streamChat()` 绕过了完整的Agent流程，仅作为简单LLM调用使用。这意味着：

- 标书审查场景不走流式
- RAG增强场景不走流式
- 会话管理（保存消息、更新标题等）不执行

**问题二：同步等待时间长**

`AgentChatService.chat()` 的执行流程：
```
1. 路由决策（毫秒级）
2. 场景分发
3. 知识检索（RAG）
4. LLM调用（秒级，等待完整回答）
5. 结果回写
6. 返回响应
```

用户看到的是：长时间空白 → 完整回答

**问题三：流式和非流式是两套独立路径**

```
/agent/chat  → AgentChatService.chat() → 同步完整响应
/agent/chat/stream → LLMChatService.streamChatWithScene() → 仅LLM调用
```

两套路径复用度低，维护成本高。

### 1.3 期望的用户体验

用户期望：
- 点击发送后，很快看到"正在思考..."
- 然后逐字/逐句看到回答输出
- 标书审查等复杂场景也能看到进度

## 2. 改造方案

### 2.1 方案一：渐进式流式改造（推荐）

#### 阶段划分

**Phase 1: 流式响应框架搭建**

目标：让主链路能返回流式响应，但后端仍是同步执行

改动点：
1. 新增 `AgentChatService.streamChat()` 方法，返回 `Flux<AgentChatResp>`
2. 将 `AgentChatResp` 拆分为"起始帧"、"增量帧"、"结束帧"
3. 复用现有同步逻辑，通过 `Flux.create()` 或 `Flux.generate()` 将同步结果转为流式

```java
public Flux<AgentChatResp> streamChat(AgentChatReq req) {
    return Flux.create(sink -> {
        // 同步执行完整链路
        AgentChatResp resp = chat(req); // 现有同步方法
        // 转换为流式
        sink.next(resp);  // 发送完整响应
        sink.complete();
    }, FluxSink.OverflowStrategy.BUFFER);
}
```

问题：用户仍需等待完整回答后才能看到任何输出。

---

**Phase 2: LLM层真流式**

目标：让LLM输出就开始推送，不等待完整回答

关键改动：
1. 在 `AgentSceneService` 的 `generalChatWithTitle()` 中使用 `LlmService.streamChat()`
2. 将流式响应通过 `SseEmitter` 或 `ServerSentEvent` 推送
3. 前端收到增量数据后立即渲染

```java
private Flux<String> streamChatWithTitle(String query, String sessionId, String model, String systemPrompt) {
    LlmRequest request = LlmRequest.builder()...
    return llmService.streamChat(request)
            .map(LlmResponse::getContent)
            .filter(content -> content != null && !content.isEmpty());
}
```

---

**Phase 3: 全链路流式编排**

目标：实现"边生成边推送"的用户体验

需要解决的问题：
1. RAG检索和LLM生成如何并行？
2. 会话消息如何保存（流式过程中的中间结果）？
3. 标题生成、摘要更新等后处理如何与流式协调？

可能的方案：

**方案A: 异步消息保存**
```
1. LLM开始生成 → 推送"开始"帧
2. LLM输出增量 → 实时推送 + 异步保存到数据库
3. LLM结束 → 推送"结束"帧 + 触发标题/摘要更新
```

**方案B: 双缓冲**
```
1. 后端维护一个响应缓冲区
2. LLM输出时同时：写入缓冲区 + 推送给前端
3. 结束后一次性保存到数据库
```

### 2.2 方案二：简单流式开关（快速实现）

目标：用最小改动实现流式效果

**实现方式**：

1. 在 `AgentChatReq` 中增加 `stream: boolean` 字段
2. 在 `AgentChatService.chat()` 中根据 `stream` 标志决定返回类型
3. 流式模式下，将回答分词推送

```java
public Object chat(AgentChatReq req) {
    if (Boolean.TRUE.equals(req.getStream())) {
        return streamChat(req);
    }
    return syncChat(req);
}

public Flux<ServerSentEvent<String>> streamChat(AgentChatReq req) {
    AgentChatResp resp = syncChat(req);  // 先完整执行
    String answer = resp.getAnswer();

    // 将回答分批推送，模拟流式效果
    return Flux.fromIterable(splitAnswer(answer))
            .map(chunk -> ServerSentEvent.<String>builder()
                    .event("message")
                    .data(chunk)
                    .build())
            .concatWithValues(ServerSentEvent.<String>builder()
                    .event("done")
                    .data("[DONE]")
                    .build());
}
```

**优点**：改动小，能快速上线
**缺点**：不是真正的流式，用户仍需等待完整回答

### 2.3 方案三：WebSocket替代SSE

如果需要双向通信或更高实时性，可以考虑 WebSocket：

```java
@MessageMapping("/chat")
public Flux<String> handleMessage(String message) {
```

## 3. 改造风险评估

### 3.1 技术风险

| 风险 | 级别 | 缓解措施 |
|------|------|---------|
| 流式过程中异常处理困难 | 中 | 设置超时、使用 `retry()` 策略 |
| 前端流式渲染兼容性 | 低 | 提供多种前端SDK |
| 会话消息保存时序问题 | 高 | 使用事务或最终一致性 |
| 连接断开后的状态恢复 | 中 | 消息ID + 断点续传 |

### 3.2 业务风险

| 风险 | 级别 | 缓解措施 |
|------|------|---------|
| 流式响应影响现有功能 | 中 | 灰度发布、开关控制 |
| 用户体验期望差异 | 低 | 产品明确说明流式效果 |
| 复杂场景（标书审查）流式收益低 | 中 | 复杂场景保持同步，仅简单问答走流式 |

### 3.3 性能考虑

- 流式响应会增加服务器连接时长
- 需要评估百炼API的流式支持能力
- 考虑连接数限制和超时配置

## 4. 分阶段实施计划

### 4.1 建议优先级

```
P0（立即可做）:
- Phase 1: 流式响应框架搭建（方案二快速实现版）

P1（下个迭代）:
- Phase 2: LLM层真流式（通用对话场景）
- Phase 3.1: 异步消息保存

P2（后续迭代）:
- Phase 3.2: 全链路流式编排
- 复杂场景（标书审查）的流式支持
```

### 4.2 验收标准

**Phase 1 验收**：
- [ ] `/agent/chat?stream=true` 返回 SSE 流
- [ ] 前端能收到增量数据并渲染
- [ ] 现有同步接口 `/agent/chat` 不受影响

**Phase 2 验收**：
- [ ] LLM 开始输出后 100ms 内前端收到首字节
- [ ] 流式过程中断后，下次请求能恢复上下文

**Phase 3 验收**：
- [ ] 完整Agent链路（路由+RAG+LLM）支持流式
- [ ] 会话消息完整保存
- [ ] 标书审查场景支持流式进度展示

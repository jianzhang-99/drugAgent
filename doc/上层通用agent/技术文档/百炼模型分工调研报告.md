# 百炼模型分工调研报告

> 文档版本：V1.0
> 更新时间：2026-04-08
> 适用范围：Drug-Agent 上层通用 Agent、标书审查、合同预审、风险预警、RAG
> 调研方式：结合当前仓库实现与阿里云百炼官方文档整理

---

## 1. 调研目标

回答三个问题：

1. 百炼当前有哪些适合本项目的模型能力
2. 这些模型在本项目中分别适合承担什么角色
3. 当前项目从“单模型默认使用”升级为“按任务分工使用”的最优落地方式是什么

---

## 2. 当前项目现状

结合当前仓库代码，模型接入现状如下：

- 当前已接阿里云百炼 `DashScope`
- 默认聊天模型为 `qwen3.5-plus`
- 当前切换粒度主要还是 `provider` 级，而不是 `task` 级
- 当前主要链路仍是：
  - 场景路由
  - 通用问答
  - 标书审查编排
  - RAG 检索增强
  - 报告生成

对应代码位置：

- `src/main/resources/application.yml`
- `src/main/java/com/liang/drugagent/shared/llm/LlmService.java`
- `src/main/java/com/liang/drugagent/shared/llm/DashScopeLlmClient.java`
- `src/main/java/com/liang/drugagent/agent/chat/AgentSceneService.java`

当前问题不是“能不能接更多模型”，而是“已经到了必须按任务拆模型职责的时候”。

## 3. 百炼官方模型能力摘要

根据阿里云官方文档，截至 2026-04-08，与本项目最相关的能力可归纳为以下几类。

### 3.1 通用文本与多模态主模型

- `qwen3-max`
  - 适合复杂任务，能力最强
- `qwen3.6-plus`
  - 效果、速度、成本均衡
- `qwen3.5-plus`
  - 通用能力强，适合智能体任务
- `qwen3.5-flash`
  - 简单任务速度快、成本低

官方信息显示：

- `Qwen3.6-Plus` 与 `Qwen3.5-Plus` 支持文本、图像和视频输入
- `Qwen3.5-Flash` 适合简单任务，速度快、成本低
- `qwen3.5-plus`、`qwen3.5-flash` 均支持内置工具调用

### 3.2 向量与检索增强

- `text-embedding-v4`
  - 相比 `text-embedding-v3` 在多语言、中英检索、代码检索等任务上有明显提升
- `qwen3-rerank`
  - 适合 Query + Document 重排
- `qwen3-vl-rerank`
  - 适合图文混排或文档图像相关性重排

### 3.3 OCR / 文档解析

- `qwen-vl-ocr`
  - 面向扫描文档、表格、票据、结构化信息抽取

### 3.4 代码相关

- `qwen3-coder-next`
  - 适合代码理解与生成

### 3.5 MCP / 外部工具生态

- 百炼 MCP 当前通过 `Responses API` 接入
- 这意味着后续若要让模型直连外部法规库、企业信息库、招采公告等 MCP 服务，需要新增 Responses API 客户端能力，而不能只停留在当前 `MultiModalConversation` SDK 用法

## 4. 结合本项目的模型分工建议

本项目不是单一聊天产品，而是“路由 + 工具编排 + Workflow + 结构化结果 + 证据链”的业务 Agent。

因此模型分工应该围绕任务类型，而不是围绕“一个默认模型走全链路”。

建议最少拆成以下 8 类任务。

### 4.1 场景路由

适用位置：

- `AgentSceneService.decideRoute()`
- 后续如果引入 LLM 兜底路由

推荐模型：

- 首选：`qwen3.5-flash`
- 备选：`qwen3.5-plus`

原因：

- 路由任务文本短、结构简单、对成本和延迟敏感
- 不值得用最强模型
- 应优先保证低成本、高速度、稳定 JSON 分类结果

建议：

- 规则强匹配继续保留
- 仅在规则无法判断且确实像业务请求时，使用 `qwen3.5-flash` 做兜底意图分类
- 路由输出固定为 JSON Schema，不要自由文本解析

### 4.2 通用对话

适用位置：

- `AgentSceneService.dispatchToGeneralChat()`

推荐模型：

- 首选：`qwen3.6-plus`
- 成本优先：`qwen3.5-plus`
- 低成本降级：`qwen3.5-flash`

原因：

- 通用问答需要较强的中文表达与事实组织能力
- 但大多数请求并不值得用 `qwen3-max`
- 如果结合 RAG，主模型主要负责“基于证据组织答案”，`plus` 级通常足够

建议：

- 无 RAG 命中时可走 `qwen3.5-plus`
- 有 RAG 命中且证据较多时可升级为 `qwen3.6-plus`
- 简单寒暄、短问短答可下沉到 `qwen3.5-flash`

### 4.3 Tool Orchestrator 主模型

适用位置：

- `TenderReviewToolOrchestrator`
- 后续合同预审 Orchestrator
- 后续风险预警 Orchestrator

推荐模型：

- 首选：`qwen3.5-plus`
- 更强版本：`qwen3.6-plus`

原因：

- 编排器任务不是最终业务引擎，而是“理解用户意图 -> 判断是否调用 Tool -> 组织工具参数 -> 汇总结构化结果”
- 这类任务需要一定工具调用能力和稳定性，但不一定每次都需要最强模型

建议：

- 标书审查主入口优先用 `qwen3.5-plus`
- 合同预审、风险预警如果工具链更复杂，可评估 `qwen3.6-plus`
- 不建议让 `qwen3-max` 常驻编排层，性价比不高

### 4.4 严格结构化输出

适用位置：

- 标题生成
- 审查摘要生成
- `riskLevel / score / confidence / evidenceList / steps` 输出
- 路由分类结果输出

推荐模型：

- 首选：`qwen-plus` 系列的非思考结构化输出链路
- 当前项目可先验证：`qwen3.5-plus` 或 `qwen3.6-plus` + `json_schema`

原因：

- 你的项目前端响应本身就是结构化的
- 如果继续靠自然语言拼接再手工解析，稳定性会越来越差
- 结构化输出任务不是“越会写文章越好”，而是“越遵守 schema 越好”

建议：

- 建立单独的 structured-output 调用模板
- 所有可枚举字段都走 `json_schema`
- 不要把“报告正文生成”和“结构化字段生成”混在同一次调用里

### 4.5 长报告与复杂归纳

适用位置：

- 标书审查报告润色
- 合同预审长报告
- 风险预警总结与解释

推荐模型：

- 首选：`qwen3.6-plus`
- 高质量版本：`qwen3-max`

原因：

- 这类任务关注长文本组织、复杂归纳、解释完整性
- 适合用更强模型承担最终“面向用户的表达层”
- 但前提是底层事实和证据已经由 Workflow / Tool 准备好

建议：

- 报告正文生成与结构化字段拆成两步
- 复杂案件、高价值客户、演示场景再上 `qwen3-max`
- 普通生产默认先用 `qwen3.6-plus`

### 4.6 RAG 向量检索

适用位置：

- 知识库检索
- 合规条文召回
- 标书片段召回
- 合同条款召回

推荐模型：

- 首选：`text-embedding-v4`
- 当前兼容保底：`text-embedding-v3`

原因：

- 官方文档显示 `text-embedding-v4` 在检索、聚类、分类上较 `v3` 有明显提升
- 你当前项目是业务知识问答和审查依据召回场景，优先优化检索质量比继续压榨生成模型更有效

建议：

- 新索引、新知识库直接上 `text-embedding-v4`
- 老索引可分阶段迁移
- 维度优先使用 1024，若后续考虑存储成本再评估 512

### 4.7 RAG 重排

适用位置：

- 召回后候选文档排序
- 标书片段相关性二次排序
- 合同条款命中精排

推荐模型：

- 首选：`qwen3-rerank`
- 图文混合场景：`qwen3-vl-rerank`

原因：

- 当前通用问答已经有 RAG
- 但“召回到的内容是否排在前面”会直接影响回答质量
- 重排模型比让主聊天模型自己消化大量噪音片段更划算

建议：

- 在 `KnowledgeRetrievalTool` 后增加官方 rerank 层
- 保留本地 `RerankService` 作为兜底或离线策略

### 4.8 OCR / 扫描件解析

适用位置：

- 扫描版标书
- 合同图片/扫描 PDF
- 表格识别
- 票据、附件、截图抽取

推荐模型：

- 首选：`qwen-vl-ocr`

原因：

- OCR 不应该由通用聊天模型承担
- 官方模型就是为文字提取、表格解析、结构化信息抽取设计的
- 对标书、合同这类文档型业务，OCR 是底层入口能力，不是可有可无

建议：

- 将 OCR 下沉为独立 Tool 或 PreparationService
- Preparation 阶段先完成 OCR / 文档解析，再把结构化结果送入 Workflow

## 5. 三大业务场景的具体分工

### 5.1 标书审查

建议分工：

- 文档解析 / 扫描识别：`qwen-vl-ocr`
- 招标文档片段召回：`text-embedding-v4`
- 召回精排：`qwen3-rerank`
- Tool 编排主模型：`qwen3.5-plus`
- 最终长报告生成：`qwen3.6-plus`
- 高价值复杂案件报告：`qwen3-max`

设计原则：

- 风险判定主逻辑仍留在 `TenderReviewWorkflow`
- 模型负责“理解、编排、总结”，不要替代确定性规则引擎
- 模型不应直接决定最终风险分，而应基于 Workflow 结果做解释和归纳

### 5.2 合同预审

建议分工：

- 条款召回：`text-embedding-v4`
- 条款重排：`qwen3-rerank`
- 预审编排：`qwen3.5-plus`
- 风险总结和修改建议：`qwen3.6-plus`
- 重点合同终稿意见：`qwen3-max`

设计原则：

- 合同预审比标书更适合“RAG + 结构化建议 + 风险解释”组合
- 合同条款对结构化输出要求高，应尽早切 `json_schema`

### 5.3 风险预警

建议分工：

- 外部资料接入：后续 MCP / 外部检索
- 规则触发与聚合：本地规则 + Workflow
- 事件归纳：`qwen3.5-flash` 或 `qwen3.5-plus`
- 预警解释与摘要：`qwen3.6-plus`

设计原则：

- 风险预警通常频次高、单次价值较低
- 不应默认使用最昂贵模型
- 更适合“先规则聚合，再低成本归纳，必要时升级”

## 6. 推荐的首版模型策略表

| 任务类型 | 推荐模型 | 备用模型 | 备注 |
|------|------|------|------|
| 路由分类 | `qwen3.5-flash` | `qwen3.5-plus` | 短文本、低成本、快 |
| 普通问答 | `qwen3.5-plus` | `qwen3.6-plus` | RAG 命中多时可升级 |
| Tool 编排 | `qwen3.5-plus` | `qwen3.6-plus` | 面向 Orchestrator |
| 严格结构化输出 | `qwen3.5-plus` / `qwen3.6-plus` | `qwen-plus` 系列 | 走 `json_schema` |
| 长报告生成 | `qwen3.6-plus` | `qwen3-max` | 高价值案件可升级 |
| OCR / 扫描件 | `qwen-vl-ocr` | 无 | 独立文档解析入口 |
| 向量召回 | `text-embedding-v4` | `text-embedding-v3` | 建议逐步迁移 |
| 文本重排 | `qwen3-rerank` | 本地 RerankService | 用于 RAG 精排 |

## 7. 对当前项目的改造建议

### 7.1 先做“任务级选型”，不要直接做“全局模型切换”

当前仓库已经有：

- `default-provider`
- `routing-provider`
- `chat-provider`
- `report-provider`

但这还不够。

建议新增：

- `taskType`
  - `ROUTING`
  - `GENERAL_CHAT`
  - `TOOL_ORCHESTRATION`
  - `STRUCTURED_OUTPUT`
  - `REPORT_GENERATION`
  - `RAG_EMBEDDING`
  - `RAG_RERANK`
  - `OCR_PARSE`

然后让模型选择逻辑由“provider 维度”升级为“taskType -> provider + model + params”。

### 7.2 不要把模型策略塞回 AgentChatService

符合本仓库分层原则的做法是：

- 新增 `ModelSelectionService` 或 `LlmModelStrategyService`
- 上层只传：
  - scene
  - taskType
  - 是否流式
  - 是否需要严格 JSON
  - 是否长文本
- 由策略层返回：
  - provider
  - model
  - temperature
  - maxTokens
  - responseFormat

### 7.3 标书审查优先落这三步

1. 将 `Tool Orchestrator` 固定到 `qwen3.5-plus`
2. 将最终报告生成升级为 `qwen3.6-plus`
3. 将扫描文档解析拆到 `qwen-vl-ocr`

这是当前收益最高、改造成本最可控的一组动作。

### 7.4 通用问答优先落这两步

1. 将通用问答默认模型与路由模型拆开
2. 将 RAG 向量模型升级为 `text-embedding-v4`，并接入 `qwen3-rerank`

---

## 8. 不建议的做法

以下做法不建议继续：

- 所有任务默认都走 `qwen3.5-plus`
- 把路由、编排、结构化输出、长报告全部混在一个模型里
- 用自然语言正文承载结构化字段，再靠正则或字符串截取解析
- 把模型直接下沉到 Workflow 内部替代确定性规则
- 在 `AgentChatService` 里写大量场景专属模型选择逻辑

---

## 9. 结论

对当前 Drug-Agent 项目，百炼模型最合理的分工不是“选一个最强模型全项目通吃”，而是：

- `qwen3.5-flash` 负责快而便宜的轻任务
- `qwen3.5-plus` 负责日常问答与 Tool 编排
- `qwen3.6-plus` 负责高质量总结与报告生成
- `qwen3-max` 只用于复杂高价值案件
- `text-embedding-v4` 负责召回
- `qwen3-rerank` 负责精排
- `qwen-vl-ocr` 负责扫描文档解析

对本项目来说，最优路径不是“换掉 qwen3.5-plus”，而是“把 qwen3.5-plus 从唯一主模型，降为其中一个职责明确的主力模型”。

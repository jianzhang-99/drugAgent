# 投资人演示 MVP 代办事项汇总

> 文档版本：v1.0
> 更新时间：2026-04-02
> 使用目标：作为当前阶段统一开发清单，严格围绕“可给投资人演示的 MVP”推进

---

## 1. 当前统一判断

当前项目已经具备较强的后端能力骨架，尤其是标书审查主链路已经初步成型：

- 已有统一 Agent 对话入口
- 已有场景路由能力
- 已有标书审查数据准备链路
- 已有 Workflow、规则命中、免责处理、风险融合、证据组装、报告生成能力

但距离“投资人可感知为一个完整产品”仍然差几个关键闭环：

1. 前端仍存在 mock 演示成分
2. 真实上传到结果展示的产品闭环尚未完全打透
3. 任务详情、证据链、报告页等演示核心页面还不够完整
4. 环境与测试稳定性不足，现场演示存在翻车风险
5. 三场景叙事已建立，但当前真正适合重点展示的是“标书审查单场景 MVP”

因此本阶段的总策略应统一为：

**先把“标书审查”做成一个稳定、可信、可解释、可演示的单场景 MVP，再把合同预审与风险预警作为后续扩展能力进行展示。**

---

## 2. 产品收敛原则

开发时统一遵守以下原则：

1. 不追求同时做实三个场景
2. 不优先追求炫技式 Agent 交互
3. 不把大量时间花在非演示关键路径上
4. 所有工作优先服务“上传文件 -> 自动审查 -> 查看结果 -> 理解证据 -> 形成可信演示”

本阶段最重要的不是“功能数量多”，而是：

- 演示稳定
- 风险结果清楚
- 证据链可信
- 页面观感完整
- 讲故事时前后自洽

---

## 3. P0 必须完成

P0 的定义是：不完成就不建议拿去做正式投资人演示。

### 3.1 标书审查主链路真实跑通

目标：

让用户上传两份真实标书后，系统能稳定返回结构化审查结果。

代办事项：

- 打通前端到后端真实上传链路
- 确认 `/agent/submit` 联调稳定
- 确认 `MultipartFile[] -> DocumentTool -> TenderReviewData -> Workflow` 全链可用
- 确认结果中稳定返回 `summary`、`answer`、`riskLevel`、`score`、`report`、`evidenceList`、`evidenceGroups`、`steps`

完成标准：

- 使用固定样本文件进行审查时，可稳定输出完整结果
- 至少可演示 1 组高风险样本和 1 组低风险样本

### 3.2 前端关闭 mock，进入真实联调态

目标：

让演示页面基于真实后端返回，而不是 mock 数据。

代办事项：

- 关闭前端默认 mock 开关
- 清理关键页面中的 mock 文案和 mock 返回依赖
- 确认工作台、上传入口、结果卡片都来自真实接口
- 对无法立即真实落地的模块明确标识为“规划中”或“即将上线”，避免混淆

完成标准：

- 主演示路径不依赖 mock API
- 演示时可明确说明哪些是真能力，哪些是后续扩展

### 3.3 补齐标书审查结果承接页

目标：

让投资人一眼看懂系统做了什么、为什么这样判断、价值在哪里。

代办事项：

- 增加任务详情页或结果详情页
- 展示风险等级、风险分、摘要结论
- 展示命中规则摘要
- 展示证据链分组与关键片段
- 展示最终报告或报告摘要
- 展示处理步骤与状态

完成标准：

- 演示时不用翻日志或 Swagger，看页面就能理解审查结果

### 3.4 补齐失败路径与提示

目标：

让系统即使失败，也要失败得像个成熟产品。

代办事项：

- 文件少于 2 份时给出明确提示
- 文件为空时给出明确提示
- 文件格式不支持时给出明确提示
- 文档解析失败时给出明确提示
- 模型或 Workflow 异常时给出统一降级提示
- 前端展示失败状态、重试建议和空状态

完成标准：

- 演示中即便误操作，也不会出现难看的报错或空白页面

### 3.5 固化演示样本与演示脚本

目标：

让演示结果可控、稳定、可复现。

代办事项：

- 固定 1 组高风险围标样本
- 固定 1 组合规或低风险样本
- 为每组样本准备预期结论
- 准备标准演示顺序
- 准备每一步讲解口径

完成标准：

- 每次演示结果一致，不依赖临场发挥

### 3.6 修复基础测试与环境稳定性问题

目标：

让系统具备“敢演示”的工程底线。

代办事项：

- 修复当前测试环境依赖配置问题
- 让最核心测试可在本地稳定运行
- 校验演示环境中的模型 key、数据库、对象存储配置
- 准备一份演示环境启动说明

完成标准：

- 演示前可以快速自检环境状态
- 不因配置缺失导致现场启动失败

## 4. P1 应尽快完成

P1 的定义是：完成后会显著提升投资人对产品完成度和平台潜力的判断。

### 4.1 任务看板真实化

目标：

把任务看板从“静态展示”升级为“真实任务入口”。

代办事项：

- 接入真实任务列表
- 展示任务状态、场景类型、创建时间、风险等级
- 支持从看板进入任务详情
- 能识别刚创建的标书审查任务

### 4.2 对话工作台可用化

目标：

让首页工作台从“有壳子”变成“可真实交互”。

代办事项：

- 打通纯文本问答
- 展示消息记录
- 展示上传记录和结果卡片
- 支持基础 Markdown 渲染
- 增加发送中、处理中、失败中断等状态

### 4.3 实时状态刷新

目标：

让系统更像一个真正执行中的 Agent。

代办事项：

- 优先支持轮询刷新
- 后续再补 SSE 或流式输出
- 展示处理中、完成、失败、待复核等状态

### 4.4 管理摘要与建议动作

目标：

让系统输出更像管理层产品，而不只是技术结果。

代办事项：

- 增加管理摘要
- 增加“建议复核”“建议重点核查技术方案”“建议查看报价异常”等操作建议
- 将结果卡片做成适合展示给投资人的高层视图

---

## 5. P2 可延后

P2 的定义是：对长期平台价值重要，但不是当前投资人演示的阻塞项。

包括但不限于：

- 合同预审真实 workflow
- 风险预警真实数据链路
- Tool Calling 编排增强
- 通用多场景文件中心
- 复杂 OCR
- 高级 RAG 能力
- 协作、评论、权限体系
- 导出 PDF/Word 正式报告
- 多租户与组织隔离

---

## 6. 技术路线建议

当前阶段建议采用以下路线：

### 路线一：先产品闭环，后平台增强

顺序建议：

1. 打通标书审查真实链路
2. 做好结果页与任务页
3. 固化演示数据与演示环境
4. 修复测试和关键异常
5. 再继续推进 Tool Orchestrator 化和多场景扩展

原因：

当前最缺的不是底层想象力，而是上层“产品完成度”。

### 路线二：对外讲“平台方向”，对内按“单场景成品”开发

对外可以讲：

- 这是医药监管与合规审查 Agent 平台
- 当前先落地标书审查
- 后续沿同一架构扩展合同预审与风险预警

对内必须执行：

- 不同时并行深挖三个真实场景
- 研发资源优先给标书审查演示闭环

---

## 7. 推荐开发顺序

建议你严格按下面顺序推进：

1. 修复真实上传与标书审查主链路
2. 前端关闭 mock，打通真实结果展示
3. 增加任务详情页/结果详情页
4. 固化高风险与低风险样本
5. 补齐失败提示与空状态
6. 修复测试环境和关键用例
7. 任务看板真实化
8. 工作台对话体验优化
9. 再考虑合同预审与风险预警的演示包装

---

## 8. 里程碑定义

### 里程碑 M1：可内部稳定演示

判定标准：

- 标书上传可用
- 审查结果可返回
- 页面可展示风险结论与证据
- 基本异常路径可控

### 里程碑 M2：可正式对投资人演示

判定标准：

- 前端主路径不依赖 mock
- 有标准样本、标准结果、标准话术
- 任务页、结果页、工作台三者协同完整
- 环境稳定，演示成功率高

### 里程碑 M3：可开始讲平台扩展

判定标准：

- 标书审查形成稳定标杆场景
- 合同预审和风险预警有明确落地计划与原型支撑
- 架构层开始向 Orchestrator 和多场景能力收敛

---

## 9. 一句话执行准则

**当前阶段，所有开发工作都优先服务于“把标书审查做成一个投资人看完就觉得真实、可信、可扩展的 MVP 产品”。**
